# 51 · 有线交互卡顿归因与视频接收窗调优（CS11 点火实测，2026-10-10 晚）

> 触发：用户在有线 CarPlay 会话里反馈**"滑动反应迟钝、滑动过程中声音偶发卡顿，比无线差很多"**。
> 本文给出**实测归因**（不是推断）、一次**已落地的调优**（提交 `37a05abb`）、以及**剩余优化清单**。
> 设备：CS11 `0123456789ABCDEF`（i.MX6Q 四核 @996MHz / Android 4.4.3 / 逻辑屏 1280×720@160），
> 会话：**有线**（`wireless_enabled=false`）、`display_fps=30`、`usb1` 已起（`fe80::2`）、音乐播放中（LPCM）。
>
> **§9/§10 为同日追加**：应"无线为什么比有线顺"的追问，做了**有线 vs 无线的链路与传输方式对照**，
> 并用一个新开关做了**决定性实验**（结论：有线音频负载不可协商）。

---

## 0. 一句话结论

**卡顿不是"有线链路坏了"，而是"交互突发把车机 CPU 打满 → 收包核被挤 → 内核丢包"**：
有线音频是 iOS 指定的**实时 LPCM over UDP（137 包/秒、无重传）**，丢了就是可听见的卡顿 ✗；
视频是 TCP，靠重传补齐，但补的过程造成 **0.3–1.7 s 的帧间隔尖峰**，被 250 ms 老化规则丢弃
（`dropped`）⇒ 拖动"迟钝、一顿一顿" ✗；触摸上行写事件通道时会撞上 GC/抢占（100–163 ms）⇒ 手感发木 ✗。
**已落地的第一条解药**是把视频发送端的在途窗口从"实际 128 KiB"收到"实际 16 KiB"：迟到丢帧 161→17–28、
`maxGap` 1736→239–331 ms、`touch2frame` 86→51–60 ms（同一注入负载，且小窗那几轮内容强度更高）。

## 1. 症状 → 可判据的指标

| 用户听/看/感的 | 对应指标 | 本次实测（有线交互期） |
|---|---|---|
| 声音偶发卡顿 | `Receive: audio … seqGapEvents/seqGapMax`、内核 `Udp6InErrors` | 单次缺 6–15 包（≈50–110 ms）；60 s 内 +86 个 UDP 错误 |

## 2. 归因一：丢包只发生在交互期，且与 CPU 饱和窗口重合

方法：`work/lossprobe2.sh`（设备侧，0.5 s 粒度记逐核 jiffies + `Udp6InErrors`/`Udp6InDatagrams`/
`Ip6ReasmFails` + loadavg + softnet）＋ `work/analyze_lossprobe2.py`（PC 侧差分与相关性判定）。

**空闲 60 s（无人操作）**：`Udp6InErrors = 0`、`Udp6InDatagrams = +8215`（≈137/s = 音频实时速率）、
`Ip6InReceives` 与 `Ip6InDelivers` 只差 TCP 视频段数、`Udp6RcvbufErrors = 0`、`Udp6NoPorts = 0` ⇒ **不丢** ✓

**注入交互 160 s**（`adb shell input swipe` ×88，与后续 A/B 同一协议）：`Udp6InErrors = +79`（**0.65 %**）、
丢包出现在 **16/160** 个 0.5 s 窗口里、单窗口最大 **17 包**；这些窗口里四核 busy p50 74–74 %、
**max 100 %**，**CPU1 的 `irq+sirq` 尖到 57 %**（CPU1 = USB 硬中断 72/75 的落点，实测
`d(cpu0..3) = 0 135675 0 0` / `0 97419 0 0`）⇒ 判定**假设 A：收包核被交互突发打满**。

**排除项（都在计数上否掉）**：`usb1` 驱动 `rxErr/rxDrop = 0`；`Udp6RcvbufErrors = 0`（不是我们读得慢、
也不是 socket 缓冲溢出）；`Udp6NoPorts = 0`；本机 TCP `RetransSegs = 0`（车机侧没有重传）。
⇒ 丢在**内核收包/投递路径**，与我们应用层的读取节奏无关。

**车机侧调优是否有效**：按 `tools/cs11_tune.sh` 经 rootd 应用并逐项核验（`rps_cpus=2`、
`netdev_max_backlog=4000`、`rmem_max=2097152`、`rmem_default=524288`、app `affinity=d`）。
**结论：对丢包没有可见改善**（丢包窗口数与突发量不变）⇒ 这不再是指向 4.4 NCM RX 路径的旋钮。

## 3. 归因二：有线路上 iOS 只给实时 LPCM，"可靠通道"用不上

doc 41 §12.4 在平板上验证过：把音乐切到 **type 103 缓冲通道**（TCP 预送、1 s 提前量）后"不卡了" ✓。
本次在有线上实测：即使设置里打开 `main_buffered_audio=true`（`/info` 里广播 103 + AAC-LC、
并带上 `mainBufferedInfo`），会话重建后**仍然只有 `audio stream type=100`**、
日志里**没有** `buffered audio stream client=…` ⇒ **iOS 在有线上坚持实时 LPCM** ✗。

后果：那条 1.5 Mbps / 137 pps 的 UDP 常流，与视频突发抢同一个 NCM 队列，
且**没有任何重传或缓冲能补回丢掉的包**（`AudioTrack` 实测占用仅 ≈1500–2800 帧 ≈31–58 ms，
`underruns=+0`、`skipped=0`）⇒ 丢包=可听见的跳过。

## 4. 归因三：GC 是"迟钝"的放大器

`work/wired-finger-F1.log`（真实手指滑动窗口，逐核 36–44 %）：
**125 次 `GC_CONCURRENT` / 170 s**、每次回收 ≈5.8 MB、`total 80 ms`，
且 **`WAIT_FOR_CONCURRENT_GC blocked` 37–67 ms ×80 行**（≈0.5 次/秒的线程级阻塞）。
doc 40 已把这条定性为"帧间隔 80–150 ms 的直接来源"；本次的 `touchSendMax 100–163 ms`
与 `touchQueueMax 155 ms` 与之一致 —— 触摸线程的发包动作被 GC/抢占切碎。

## 5. 已落地：视频接收窗调优（提交 `37a05abb`）

### 5.1 一个被误解很久的事实：**内核把 `SO_RCVBUF` 翻倍**

`ScreenStream.accept()` 一直写 `VIDEO_RECEIVE_BUFFER_BYTES = 64 * 1024`，
但日志里 `getReceiveBufferSize()` 报的是**它自己的两倍**：

```
setReceiveBufferSize(131072) → "video socket accepted rcvbuf=262144 requested=131072"
setReceiveBufferSize(   8192) → "video socket accepted rcvbuf= 16384 requested=   8192"
```

⇒ **"64 KiB 上限"实际一直是 128 KiB**（doc 18 §3 的意图被放大了一倍，一直没人发现 ✗）。

### 5.2 把窗口做成可调属性（一次点火窗口内就能比）

`shared/.../airplay/VideoReceiveWindow.kt`（新）：`debug.diplay.video_rcvbuf`（字节），
夹取到 4–256 KiB，未设/非法/非正数一律回落默认值；`ScreenStream` 每次 accept 读一次并在诊断行里
同时打印 **requested（我们的请求）** 与 **rcvbuf（内核实际）**：

```
adb shell setprop debug.diplay.video_rcvbuf 32768   # 下一次流 SETUP 生效
```

### 5.3 A/B 结果（同一注入协议：88–95 次滑动 / 145 s 探针窗口）

| 请求 | 实际窗口 | UDP 丢包率 | 丢包窗口 | 最大突发 | `dropped` | `maxGap` | `touch2frame` p50 | 单次最大缺包 | 内容强度 kbps(mean) |
|---|---|---|---|---|---|---|---|---|---|
| 64 KiB（旧默认） | **128 KiB** | 0.65 % | 16/160 | 17 | **161** | **1736 ms** | **86 ms** | 15 | 1715 |
| 32 KiB | 64 KiB | 0.60 % | 17/161 | 21 | 53 | 1687 ms | 65 ms | 21 | 2648 |
| 8 KiB | **16 KiB** | 0.20 % | 14/161 | 4 | **28** | **331 ms** | **53 ms** | 6 | 3246 |
| 4 KiB | 8 KiB | 0.26 % | 17/160 | 5 | 17 | **239 ms** | 51 ms | 6 | 3094 |

**读法**：三档更小窗口的**画面侧指标单调变好**，而这几次的 `kbps` 反而更高（1715 → 3094–3246）
⇒ 不是"画面更省"造成的假象 ✓。UDP 丢包在 128→64 KiB 上不动、到 16 KiB 才明显下降，
样本量（每档 1–2 轮）不足以给出统计显著，**故只把它当"顺带收益"而不是结论**。

> **样本有效性**：表中的 `16 KiB` 只采用有效的一轮。另一轮（`work/ab-rcv4k.*`，1.19 %）
> **无效** —— 那一轮进行到一半时 APK 被重装（17:10:53，见 §7 并发会话），会话被打断，
> 剩余窗口是重建后的新会话。这也解释了"同一配置 0.20 % vs 1.19 %"的表观方差。

### 5.4 定稿与验证

- 默认请求 **8 KiB → 实际 16 KiB**（不选略优的 8 KiB，为将来 1080p/60 留余量）；
  属性仍可现场再调（`setprop` 后重连即可）。
- 装包后核验：`video socket accepted rcvbuf=16384 requested=8192` ✓、
  会话健康（`rx=27.0fps shown=26.8fps dropped=0 maxGap=71ms`、音频 `type=100` 正常播放）✓。
- 单测：新增 `VideoReceiveWindowTest`（5 例，含"非法值必须回落、正数越界夹取"）；
  全量 `:shared` **872 例 / 3 失败**、`:common` **590 例 / 6 失败** —— 与 doc 34/39 的既存基线一致，**零新增** ✓。

## 6. 下一步优化清单（按收益/风险排序）

**P0 零代码、立刻可做（车机设置 + 运行态）**
1. 关车机「语音唤醒」（百度助手常驻 16 kHz 采集 ≈11 % 单核）与「应用商店自动更新」（实测 24–38 % 单核）
   —— 直接给收包/解码腾出 0.3–0.7 核（doc 29/40 已定性，`pm disable` 在本 ROM 无效）。
2. 关 `debug.diplay.trace`（交互期 15–25 行/秒的字符串格式化与分配）。
3. 调优脚本保持重放；可把 app 绑核从 `0xd`(CPU0/2/3) 改成 `c`(CPU2-3)，把 CPU0 让给车机内网
   1100 次/秒的中断风暴（doc 29 的无线分区口径）。

**P1 代码（离线可做，收益最直接）**
1. **降 GC**：触摸上行去掉每状态 `contacts.map{copy}`；事件通道命令复用对象；
   用 `Debug.startAllocCounting()` 把"分配字节/秒 + GC 次数/耗时"打进 `VideoStats` 行做验收
   （目标：分配率 ~4 MB/s → <1 MB/s，`WAIT_FOR_CONCURRENT_GC` 从 80 行/170 s 显著下降）。
2. **仪表推送限频**：现在每条 NowPlaying 更新推 3 个 Binder 调用 + 日志（8 行/秒、1413 行/170 s），
   改成"字段变化才推 + 进度类最小间隔"。
3. 触摸上行"只发最新位置"已实现（`TouchDispatchGate`），收益主要来自上面两条的 CPU 下降。

**P2 需要取舍、各做一次 A/B 即可判定**
1. `RENDER_MAX_AGE_US` 250 ms → 350 ms：拖动更顺，代价是突发期触控→画面最多 +100 ms。
2. 主屏请求降档：30→24 fps 或 scale 100 %→90 %（直接砍下行突发，最有效但牺牲画质/流畅度）。
3. `rps_cpus` 2→4/8（把 NCM 软中断从"与 USB 硬中断同核"挪开）、`netdev_budget` 300→600。

**不建议**：TextureView→SurfaceView/IPU overlay（doc 42 有 EasyPlay v71 的反向证据、doc 36 有黑屏风险）；
以及期待"根治"——这颗 2013 SoC + 厂商 NCM RX 路径没有可调项，现实目标是把交互期丢包从 ~1.4/s 压到 <0.3/s。

## 7. 踩过的坑（本轮新增，别再重犯）

1. **`SO_RCVBUF` 会被内核翻倍**：看 `setReceiveBufferSize` 的入参永远猜不到真实窗口，
   必须读 `getReceiveBufferSize()`（本文件已同时打印 requested / rcvbuf）。
2. **有线路上 iOS 不建 103**：`main_buffered_audio` 对有线无效，别再用它解释有线音频问题。
3. **注入滑动本身吃 CPU**：`adb shell input swipe` 每次都起一个 Dalvik `app_process`（doc 40 §4）。
   用注入做负载会放大 CPU 饱和，**判定"是不是 CPU 导致丢包"必须再用真实手指负载复核**。
4. **`adb logcat -d` 会丢窗口**：256 KB 环形缓冲在本项目 250 行/秒的日志量下只够约 1–2 分钟，
   长窗口必须 `logcat > file` 流式抓。
5. **被 kill 的作业会留下孤儿 adb 进程**：`adb … logcat > file` 的子进程不随作业结束而死，
   会一直持有文件句柄/刷 CPU。收工前 `Get-Process adb` 清一遍。
6. **构建中途报"classes.jar 被占用"**：多半是上一个 Gradle 守护/并发构建留下的句柄，
   删掉 `shared/build/intermediates/runtime_library_classes_jar/debug/bundleLibRuntimeToJarDebug`
   后重试即通（本次遇到两次）。
7. **本仓库可能同时有另一个会话在提交**：本轮施工期间 HEAD 从 `d70aecf8` 一路被推到
   `24d6cfa1`/`4c31100c`/`38db460f`（其中 `24d6cfa1` 就是本文件 §5.2 那个文件的中途版本），
   并伴随一次 **17:10:53 的重装**打断了正在跑的测量。**上车前先 `git log --oneline -3`
   确认没有并发写入者**，否则测量与提交都会被污染。

## 9. 追加：有线 vs 无线的链路与传输方式对照

> 数据来源：`_artifacts/car-session-20261010-c.log`（**同一天**、同一台车机上既有无线会话也有有线会话的
> 连续抓取）。按"app pid + `transport=WIRED|WIRELESS`"切段后逐段聚合（脚本 `work/mode_compare2.py`）。
> 音频的包率/码率取自各段 5 秒窗口的 `Receive: audio type=N packets/bytes` 全量统计。

| 维度 | 有线 | 无线 | 证据 |
|---|---|---|---|
| 物理/链路 | USB2 HS（实测 `speed=480`）bulk；内核 `cdc_ncm` → `usb1`，IPv6 link-local `fe80::2`，MTU 1500 | 车机自开热点（802.11n）→ `wlan0` / 192.168.43.1 | `cat /sys/bus/usb/devices/2-1.4/speed`；`WildcardAddress.serverBindAddress()` |
| 中断落点 | USB IRQ 72/75 → **CPU1**（实测 798 + 573 次/秒），NCM 软中断经 RPS 也导 CPU1 | Wi-Fi SDIO IRQ 55 → CPU0（~600 次/秒） | `/proc/interrupts` 160 秒差分 |
| 控制通道 | **两条 USB 通道**：USBMUX/lockdown + iAP2 CSM（读轮询，`result=TIMED_OUT elapsedMs=100`） | iAP2 走 AirPlay TCP 隧道（单通道复用） | `runStack` vs `startWirelessTunnelControl` |
| 音频流 | **type 100 LPCM**：**134.9 包/秒、1565 kbps、1449 B/包** | **type 102 AAC-LC**：**47.8 包/秒、252 kbps、658 B/包** | 有线 681 / 无线 357 个 5 秒窗口 |
| 视频流 | TCP type 110 H.264（`ScreenStream`，**两种形态同一套代码**） | 同 | 代码 |
| 音频解码 | 不解码，只做 BE→LE 交换 | MediaCodec **软件**解 AAC（doc 41 实测 ≈25 % 单核） | 代码/文档 |
| 视频接收窗 | 同一个属性（本次默认改到实际 16 KiB） | 同（同一属性） | `VideoReceiveWindow` |

**三条结论**

1. **视频的传输方式两种形态完全相同**，差别只在链路 ⇒ 有线的视频问题只能是"链路/突发"问题。
   本次接收窗调优已把它大幅压下来（迟到丢帧 161→17–28、`maxGap` 1736→239–331 ms、`touch2frame` 86→51–60 ms）。
   注意同一份日志里**无线段的视频指标并不比调优后的有线段更好**（无线 `dropped` 18–2472、`maxGap` p95 上界
   129–483 ms）⇒ 用户"无线更顺"的观感里，**视频不是主因**。
2. **音频的传输方式由 iOS 按链路类型自己决定**：有线 LPCM 的"过路面积"是无线 AAC 的
   **2.8 倍包率 / 6.2 倍码率**，却和视频突发共用同一条 NCM 队列 ⇒ 有线音频天生更容易被挤掉；
   无线 47.8 pps / 252 kbps 几乎没有与视频争抢的机会。**这就是"有线反而更差"的结构性原因。**
3. 有线还要在同一条 USB 上多养一条控制通道（USBMUX/lockdown + iAP2 CSM），无线没有这一份开销。

## 10. 追加：决定性实验 —— 把有线的音频格式换成 AAC（**失败，已定性**）

**手段**：新属性 `debug.diplay.audio_formats=no-pcm`（提交 `74d5ca89`）。它**只**把 type-100 的
`media` 条目的 `audioOutputFormats` 从 PCM 换成 AAC-LC，保留 102/media 与 103/media（AAC-LC），
麦克风输入 / telephony / speechRecognition 一律不动（避免 doc 27/39 那种"改错就完全没声"的坑）。

**结果（有线会话，实测）**：

```
audio format override by debug.diplay.audio_formats: NO_PCM     ← 我们的开关生效
airplay /info features=418060152546 audioFormats=10 audioLatencies=9   ← /info 正常返回 10 个音频格式
airplay SETUP stream type=110 payload={…}                        ← iOS 只 SETUP 了视频
（全程没有任何音频 SETUP / Receive: audio / audio stats）
```

⇒ **USB/有线会话下 iOS 要求 type-100 media 里必须有 PCM；即使广播了 102/103 的 AAC-LC，它也不会退回 AAC。**
⇒ **有线那 1.5 Mbps / 135 pps 的音频负载，我方无法通过格式协商降低。** 该开关保留为**负结果记录**，勿重试。

**由此收敛出的可行方向（提升有线音频只能走"投递侧"）**

| 方向 | 具体动作 | 状态 |
|---|---|---|
| 降视频突发（音频的直接竞争者） | 接收窗默认改到实际 16 KiB（已做）；必要时 30→24 fps 或 scale 100 %→90 % | 部分已做，降档待决策 |
| 降收包核压力 | 车机设置关「语音唤醒」「应用商店自动更新」（0.3–0.7 核）、关 `debug.diplay.trace`、app 侧降 GC/分配（P1） | 待做 |
| NCM RX 旋钮 | `netdev_budget` 300→600、`rps_cpus` 2→4/8（把 NCM 软中断从与 USB 硬中断同核挪开） | 未试，零成本可 A/B |

**仍待做的对称对照（需切到无线）**：用 `no-aac` 逼无线也走 PCM。
若无线在 PCM 下仍然顺 ⇒ **链路（NCM/USB）是主因**；若无线在 PCM 下也卡 ⇒ **LPCM 负载本身是主因**。
两种结果都指向上面三条投递侧动作，但能把"链路 vs 格式"的归因钉死。

## 11. 追加：硬件层面（中断/GPU/绑核）——**结论未定，附方法论教训**

用户提问："是不是把这些杂活分配到别的核就能缓解？" 先做了硬件清单与中断速率实测（0.5 s/15 s 粒度）：

**中断负载（15 秒采样，次/秒）与落核**

| 中断 | 空闲 | 交互时 | 落核 | 说明 |
|---|---|---|---|---|
| `twd`（每核定时器） | 2170 | 2171 | 四核均摊 | 不可迁 |
| `2188000.ethernet` | **1087** | 1089 | **CPU0** | 车机内网（非我方流量） |
| `2184200.usb` + `2184000.usb` | 667 + 64 | **780 + 149** | **CPU1** | 我方 NCM/USB（此前已迁好） |
| `2010000.ecspi` | 318 | 287 | CPU0 | SPI；**用 `input swipe` 注入测不出它是否触摸**（注入绕过了面板驱动） |
| `mmc1` + `bcmsdh`（Wi-Fi SDIO） | 192 + 25 | 205 + 28 | CPU0 | 有线模式下仍空转 |
| `sdma` / `VPU_CODEC_IRQ` / `2400000.ipu` | 130 / **71** / 23 | 130 / 70 / 22 | CPU0 | **VPU=视频解码、IPU=合成，都在 CPU0** |
| CPU2 / CPU3 外部中断 | **≈0** | ≈0 | — | 几乎是"干净核" |

**结论性事实**：解码是**硬件**（VPU_CODEC_IRQ 385k 次、IPU 139k 次、`OMX.Freescale…avc.v3.hw-based`、HWC 合成），
**不是我们软件解**；而我们 App 整条链路只占 **≈0.65 个核**。四核的其余负载来自车机常驻软件与中断/软中断。

**试过的硬件分工（`work/hw_partition.sh`，经 rootd）**：GPU `initgpu3DMinClock` 1→3、`netdev_budget` 300→600、
`swappiness/dirty`、eMMC `read_ahead`、**VPU/IPU/ecspi/eMMC 中断 → CPU2**、app 绑 CPU2-3（`taskset -p 0xc`）。

**结果：未得出结论。** 分工后连跑三窗口（绑核 / 放开绑核 / 只回退 GPU 时钟）都是 `maxGap` p50 1.6–1.7 s、
`kbps` p50 1970–2170；但**逐轮对比发现这三轮的"内容强度"本身就低**（`rx` 均值 13.8–16.9 对 20.2、
`kbps` p50 1970–2170 对 3015–3392）——CarPlay 是**脏区域流**，屏幕上的对象不同（例如可拖动地图 vs 会"吸附"的列表），
同样的注入滑动就会产生完全不同的帧活动。**因此这三轮的差异不能归因于硬件改动**；GPU 时钟单独回退后指标不变，
也不能证明它无害（同样是内容混淆）。

**方法论教训（重要，勿重犯）**：本项目多次栽在"**用同一套注入 ≠ 同一份负载**"上。
判断任何车机侧旋钮/分工的效果，必须：
1. **交错 A/B/A/B**（而不是先跑 A 再跑 B），并且
2. 先核对**内容强度代理指标**（`rx` 与 `kbps` 的 p50 必须落在同一区间，否则整轮作废），
3. 每侧至少 2 轮、窗口 ≥120 s。
本轮 doc 40 §4 的"`input swipe` 每次起一个 app_process"也会额外扰动 CPU。

**安全边界**：中断迁移对显示管线是**未验证的高风险**动作（本轮 VPU/IPU 挪 CPU2 后画面与音频仍正常 ✓，但
帧间隔数据被内容混淆，不能作为"无害"证据）；GPU 参数语义未核实（`initgpu3DMinClock` 3 是否真等于"更高最低时钟"
未验证）。**下次上车先跑交错 A/B，再决定是否采纳，默认保持厂商原值。**

**下次点火窗口的干净协议（建议照做）**

```
固定内容：Apple 地图 → 连续拖动同一条路线；音乐播放中
每侧 2 轮，交错： 基线 60s → 改动 60s → 基线 60s → 改动 60s
每轮同时抓： video stats(rx/kbps 必须与对侧同区间) / audio seqGap / lossprobe2 / GC 行数
车机侧旋钮在熄火后全部丢失（内存态），只保留 app 侧（接收窗默认 16 KiB ✓）
```

## 12. 追加：降 GC / 降分配（P1，第一批）

**动机（实测）**：车机上的卡顿是**尾延迟**问题——Dalvik GC 每次阻塞线程 **37–67 ms**（doc 40 §1.3），
而这些阻塞正好落在音频写、视频喂解码、触摸上行三条"必须准点"的路径上。GC 频率由**分配速率**决定，
所以先把"每包/每帧都分配"的地方消掉，并把分配速率变成可测指标（doc 40 §6 第 5 条的建议）。

### 12.1 新增计量：分配 / GC 速率进统计行

`shared/.../diag/AllocationStats.kt`（新）：用 Dalvik 的 `Debug.startAllocCounting()` +
`getGlobalAllocSize()/getGlobalFreedSize()/getGlobalGcInvocationCount()` 报"每秒分配 KiB / 每秒 GC 释放 KiB / GC 次数"。
两个要点：
- **只在 `DiagLog.traceEnabled` 时启用**（`adb shell setprop debug.diplay.trace 1`）：Dalvik 逐次分配计数开销很大，不能常开；
- 这些计数是 **32 位且会回绕**（约 8 分钟一次），所以差值用回绕校正（`counterDelta`，有单测钉住）；
  ART（API 21+）上这些计数是惰性的，首次读取返回负值 → 该字段不输出而不是输出 0。

输出挂在主屏的 `video stats` 行尾（仅主屏，避免第二路重复打印）：

```
video stats rx=… kbps=… touch2frame … alloc=4096KiB/s freed=3900KiB/s gc=57
```

⇒ 下次上车就能一眼看出"某项改动是把分配压下来了还是没动"，不必再靠 GC 行数间接推断。

### 12.2 这一批实际消掉的分配（有线热路径）

| 位置 | 改动前 | 改动后 | 省下的量（有线交互期） |
|---|---|---|---|
| `AndroidMediaSink` LPCM 渲染 | 每包 `rtp.copyOfRange(12, size)` 再字节序交换 | **交换进复用的 `pcmSwap` 缓冲**（`byteSwapS16Into`） | 137 包/秒 × 1404 B ≈ **190 KiB/s** |
| `AudioStream` 收包 | 每包 `packet.data.copyOf(packet.length)` | **复用 `wire` 缓冲**（仅在包长变化时重建；LPCM 同尺寸 ⇒ 每首歌只分配一次） | 137 × 1452 B ≈ **194 KiB/s** |
| `UsbMuxFrameBuffer`（有线控制通道） | 每次 USB 读 `bytes += transfer`（**整个积压数组重新分配**）+ 每帧两次 `copyOfRange` | **游标 + 原地压缩**：只在容量不足时增长，消费即回收 | 每次读 16 KiB 级 + 每帧剩余量 ⇒ 交互期 **数百 KiB/s** |
| `AirPlayHid`/`AirPlaySession` 触摸上行 | 每个手指状态 `contacts.map { it.copy(x*w, y*h) }`（列表 + 每指一个对象） | `touchReport(contacts, width, height)` **直接编码**（缩放函数与旧路径逐字节等价，有单测对比） | 60–120 状态/秒 × (1 列表 + N 对象) |

**安全性**：三处复用都先证明了"数组不会逃逸"——
`AudioPacketCapture.record` 是**立即写盘**（不持有 `wire`/`rtp`）；sink 的队列只持有**解密后的 `rtp`**
（所以 `AudioStream` 里那个 `rtp` 仍然保持每包新建，**没有**改它——那是下一批的事）；`pcmSwap`/`bytes`
只在单一渲染线程/USBMUX 锁内使用。

### 12.3 测试

- 新增：`UsbMuxFrameBufferReuseTest`（5 例：200 轮不增长、逐字节喂入不丢帧、最大帧恰好不增长、
  一读两最大帧只增长一次、一读多帧全部取出且缓冲清空）、`AllocationStatsTest`（4 例，含 32 位回绕）、
  `AirPlayHidTouchReportTest`（3 例，**新旧触摸编码逐字节等价**，含负坐标与超量手指）。
- 既有安全网：`UsbMuxFrameBufferTest` **35 例全绿**（各种 padding/分片语义未变）。
- 一处测试适配：`UsbMuxIssue100RegressionTest` 原本用反射读私有 `bytes` 当"剩余字节"；游标化之后
  剩余量是 `[start, end)` 窗口，测试辅助函数改为按窗口取值，**断言语义（只剩未消费的尾部字节）不变**。

### 12.4 下一批（按本次计量结果决定，别盲目动）

1. **`rtp` 每包新建**（≈194 KiB/s）：需要把"队列持有数组"的契约改成**池化缓冲 + 渲染后归还**
   （队列上限 192 包 ≈ 270 KiB，池可预分配）。这是**静默音频损坏风险**的改动，必须先用 §12.1 的计量
   证明它值得，再带单测（归还/复用/队列满三态）落地。
2. **仪表推送**（2–3 次/秒 × 3 个 Binder 调用 + 日志）：只在字段变化时推、进度类限频。
3. **视频侧**：`VideoFramePool` 已在用；剩余可查 `presentPercentiles()` 每 5 秒的一次 4 KiB 数组复制（可忽略）。

## 13. 追加：无线音质上限与决策（2026-10-13）——**维持现状，不改配置**

**问题（用户）**：无线连接时手机端用无损音质，传到车机是否受损？在现有传输方式下，能否靠"提高带宽"提升音质？

**结论**：**会受损；而且提高带宽提升不了音质。** 带宽早已不是瓶颈，瓶颈是 iPhone 为音乐流选择的**编码档位**，
而它给的那一档（AAC-LC 48 kHz）我们**已经在用**。

证据链：

1. iOS 给的音乐流是 `type=102 audioType=media codec=AAC_LC formatBits=0x800000`（doc 41:26），实测
   **47.8 包/s、658 B、252 kbps**（§9 与 `AudioFormatPolicy.kt:21-22`）。`0x800000` 正是我们广告的
   48 kHz AAC-LC（`AirPlayInfoPlist.kt:149,178`）⇒ **没有更高档的位可广告**。
2. 带宽余量实测 **8 倍**：切到 type 103 缓冲通道后，iPhone 预送到达 **2001 kbit/s**
   （`Buffered audio: queued 108 s, received 2001 kbit/s`，doc 41 §12.4）。多出来的带宽变成"提前量"，
   换来的是 `skipped 116/窗口 → 0`、`maxGapMs 400→41`、听感"不卡"——**是完整性，不是编码质量**。
3. "换更高档 / 换编码"已试过，都是负结果：103 缓冲条目 iOS"只肯用 AAC-LC 打开，PCM/ALAC 都不开"
   （`AirPlayInfoPlist.kt:180-181`、doc 41:28）；有线 `no-pcm` ⇒ iOS 根本不建音频流（§10）。
4. 两个"看似能提升、实际不能"：**广告 24 bit PCM**（API 19 播放通路只有 `ENCODING_PCM_16BIT`，
   `AndroidMediaSink.kt:1226/1370/1384` ⇒ 仍降回 16 bit，零收益）；**加宽链路带宽**（改善的是争用与流畅度，
   编码档位不变 ⇒ 音质不变）。

**决策（用户 2026-10-13）：维持当前配置。** 不改代码默认、不改车机设置项——不把「缓冲音乐（实验性）」
改成默认，不广告 24 bit PCM，不动链路带宽参数。（车上现有的设置保持原样。）

**确定有效的音质提升路径（无需任何改动）**：① 走**有线**——type 100 **LPCM 1565 kbps 未压缩**，
且只做字节序交换（`AndroidMediaSink.kt:1012-1015,1806`）；② 手机端**保持"无损"音源**，避免"手机端 AAC →
CarPlay 再 AAC"的级联两次有损（推理，非实测）。

**挂账（唯一未测项；无新证据不要重提）**：103 缓冲通道上**实际协商档位与真实码率**没有做过位级实测。
做法：开「缓冲音乐（实验性）」→ 无线放 Apple Music → 抓 `Receive: audio type=103 packets/bytes` 或
`AudioPacketCapture`，算 `包数/s × 包长` 并记录 `formatBits`。
若显著高于 252 kbps ⇒ 无线音质确有提升空间，再评估把 103 变成默认（代价：约 1 s 音乐延迟 +
`BufferedAudioStream.AUDIO_BUFFER_BYTES = 8 MiB`）；若仍是 252 kbps ⇒ 正式结案：
**CarPlay 无线音乐的音质上限 = AAC-LC 256 kbps**，我们能做的只是"一包不丢地送到 DAC"（已经做到）。

## 14. 追加：有线 AAC(103) vs LPCM(100) 实车 A/B（2026-10-12，**三条旧结论被推翻/更正**）

**动机**：用户问"现有传输方式下能否提高带宽提升音质"，于是同车同时段做了「缓冲音乐（实验性）」开/关对照。
**证据文件**：`_artifacts/car-session-2026-10-12b.log`（含 root 点火与两次会话全程）。

**侧 A —— `main_buffered_audio=true`（缓冲音乐 ON）**

```

Buffered audio: queued 109 s, received 224–280 kbit/s      ← 8 个窗口
audio stats rx=234–244/5s dropped=0 skipped=0 skippedMs=0 underruns=+0
            queue=59–63 maxGapMs=40–113 maxWriteMs=248–276 inputDroppedTotal=0 decoderDroppedTotal=0
video stats rx=26.2–26.6fps kbps=1045–1065 dropped=0 maxGap=90–135ms

**侧 B —— `main_buffered_audio=false`（缓冲音乐 OFF），拔插 USB 重开会话**

```

   ⇒ 135.6 pps、1575 kbps、1452 B/包   （与 §9 的 134.9 pps / 1565 kbps / 1449 B 一致）
audio stats rx=672–679/5s codec=LPCM dropped=0 skipped=0 skippedMs=0 underruns=+0
            queue=0 maxGapMs=15–87 maxWriteMs=0–16

            touch2frame avg=61ms n=40（用户连续拖动地图）
偶发丢失：两个窗口各 1 与 6 个包（seqGapMax=6 ≈ 44 ms），skippedMs 仍为 0

### 14.1 三条更正的结论

1. **§9 的"LPCM 负载导致有线卡顿"归因在本次会话不成立。** 侧 B 的音频负载是侧 A 的 **2.8× 包率 /
   6.2× 码率**（135.6 pps / 1575 kbps vs 48 pps / 250 kbps），且侧 B 的**内容强度更高**
   （视频 kbps 1081–1644 对 1045–1065，且有 n=40 次触摸交互），却**零丢包零欠载**
   （`skippedMs=0`、`underruns=+0`、`dropped=0`）。⇒ 接收窗 16 KiB（§7）+ 短写续写 + 持久 USBMUX 读请求
   + 降分配（§12）之后，"有线音频被视频突发挤掉"不再是当前行为。
2. **§10 的"有线上 iOS 不建 103"需要更正**：当 `main_buffered_audio` 在**会话建立之前**就是 `true` 时，
   **有线会话也会走 103/AAC-LC**（侧 A 实测）。§10 那次很可能是**会话建立之后**才用 `run-as` 打开的，
   `/info` 已经发过，所以看不到 103。
3. **§13 的挂账项结清**：103 缓冲通道的稳态码率是 **220–280 kbps（≈250 kbps）**，与 102 实时通道同档
   （§13 结论成立：buffered 买到的是"提前量/稳定性"，不是音质）；doc 41 §12.4 里的
   `received 2001 kbit/s` 是**灌满 2 分钟缓冲的爆发速率**，不是码率。

### 14.2 由此暴露的改进项（未做，供决策）

「缓冲音乐（实验性）」是**全局**开关（`AirPlayConfig.mainBufferedAudio`，`shared_prefs/xcertplay_airplay.xml`
里的 `main_buffered_audio`），但两种链路的**最优相反**：

| 链路 | 最优 | 理由 |
|---|---|---|
| **有线** | **关**（拿 type 100 LPCM 1575 kbps 未压缩） | §14.1-1：本次实测 LPCM 零丢包；AAC 反而把音质降到 250 kbps |
| **无线** | **开**（走 type 103 缓冲） | doc 41 §12.4：102 实时通道实测 `skipped 116/窗口`、`skippedMs≈2400`、听感"卡顿厉害"；103 后 `skipped=0` |

⇒ 建议把该开关改为**按链路类型生效**（有线会话不广告 103，无线会话广告 103），或另给一个
"有线时禁用缓冲音乐"的选项。改动点应在 `/info` 的 `audioFormats()`（`airplay/AirPlayInfoPlist.kt:179-182`）
按当前会话的传输类型决定是否包含 103 条目。**需要一次构建 + 一次点火窗口验证。**
