## ① 总览：三条链路 + 输入回传

```
[视频 · AirPlay 屏幕流（TCP，本机监听随机端口，iPhone 连入）]
 iPhone --TCP(dataPort)--> ScreenStream(airplay-screen 线程)
    · 128B AirPlayScreenHeader + body；bodySize=header[0..4) LE（ScreenStream.kt:73-77）
    · opcode@offset4: 0=VideoFrame（ChaCha20-Poly1305 密文）1=VideoConfig（明文 avcC/hvcC）
 解密：key=DataStream-Output-Encryption-Key(HKDF-SHA512)，nonce=8B LE 帧计数器，AAD=128B 头
   -> length-prefixed NAL 原地转 Annex B -> sink.onVideoFrame
 VideoDecoder("carplay-video" 线程/流) -> MediaCodec(video/avc 或 video/hevc)
   -> releaseOutputBuffer(index, true) 直接渲染到 Surface（SurfaceTexture / SurfaceView / 镜像 Surface）

[音频下行 · AirPlay RTP（UDP；type 100/101/102；type 103 走 TCP"增强缓冲"）]
 iPhone --UDP(dataPort)--> AudioStream(解密：12B RTP 头 + 密文 + 16B tag + 8B nonce)
   -> AudioRenderer("carplay-audio" 线程) -> MediaCodec(AAC-LC / Opus) 或 LPCM 直通
   -> PCM16 -> AudioTrack(MODE_STREAM)（媒体走 300/500/1000ms 抖动缓冲，其余小缓冲）

[麦克风上行 · UDP 反向]
 AudioRecord(48k PCM16) -> [OpusEncoder | PCM 字节序交换] -> MicrophonePacketizer(ChaCha20 封包)
   -> DatagramSocket -> iPhone 的 stream dataPort（"carplay-mic" 线程）

[输入回传 · 加密 event TCP：RTSP POST /command + bplist]
 MotionEvent -> CarPlayTouchMapper 归一化(≤2 指) -> AirPlaySession.sendTouch
   -> AirPlayHid.touchReport(每指 6B) -> {type:hidSendReport} -> ControlCipher 加密 -> iPhone
 旋钮/媒体键/电话键/触控板：同一通道，HID UID 0x2a2a2a2b / 2c / 2d；Siri=requestSiri 命令
```

## ③ 逐链路详细分析

### 3.1 视频链路（iPhone 屏幕 → Surface）

1. **流协商**：/info 声明 displays（主屏 110，可选附属屏 111），并下发 multitouch HID 描述符（airplay/AirPlayInfoPlist.kt:31-62）。SETUP 中 type=110/111 交由 `CarPlayMediaEngine.onScreen` 建 `ScreenStream`，返回 dataPort（airplay/CarPlayMediaEngine.kt:99-140；airplay/AirPlaySession.kt:683-691 的 STREAM_TYPE_MAIN_SCREEN=110 / ALT=111）。
2. **加密方式**：ChaCha20-Poly1305（BouncyCastle）。key = HKDF-SHA512(pair-verify shared, salt="DataStream-Salt<streamConnectionID>", info="DataStream-Output-Encryption-Key")（airplay/CarPlayMediaEngine.kt:533-591，label 常量 :602）；帧 nonce = 8B 小端计数器（`AirPlayCrypto.nonce64`，airplay/AirPlayCrypto.kt:106-114），AAD = 整段 128B 头（airplay/ScreenStream.kt:93-106、144-146）。VideoConfig 是明文的，靠扫描 "avcC"/"hvcC" fourcc 识别并剥离（airplay/ScreenStream.kt:108-113、178-187）。
3. **解封装**：无 TS/MP4 容器；payload 为 4 字节长前缀 NAL，原地替换为 Annex B（airplay/ScreenStream.kt:154-176）。sink 侧再兜底转换一次（media/MediaCodecSupport.kt:59-95；media/AndroidMediaSink.kt:634），两条路径都会对非法输入返回空并走恢复。
4. **MediaCodec 配置**（media/AndroidMediaSink.kt:485-583）：
   - MIME：H.264=`video/avc`；HEVC=`video/hevc`（仅 config.hevc 时，见 ⑤）；
   - CSD：avcC→首个 SPS/PPS 加 4B 起始码（`MediaCodecSupport.avcParameterSets`，media/MediaCodecSupport.kt:15-23）；hvcC→VPS/SPS/PPS 转 Annex B（:31-56）；
   - "tuned" 参数：`KEY_MAX_INPUT_SIZE=8MB`、`KEY_PRIORITY=0`（media/AndroidMediaSink.kt:545-552）；低延迟标志 `KEY_LOW_LATENCY=1` 仅在 **API≥R 且 codec 声明 "low-latency"** 时设置（:565-568）——CS11 上不会生效；
   - 尝试顺序：默认解码器(tuned) → 默认(untuned) → 软件解码器（软件探测需 API≥Q，media/AndroidMediaSink.kt:519-527、585-590）；**未指定颜色格式**，由解码器决定，输出格式仅记录（:709-727）；
   - `codec.configure(format, surface, null, 0)` 后 `start()`（media/AndroidMediaSink.kt:569-570）。
5. **喂帧与背压**：VideoDecodeQueue 上限 60 帧/8MB，超限丢弃并插入 Resync（media/VideoDecodeQueue.kt:26-51）；单帧接收后若滞留 >250ms 视为积压，丢弃+请求关键帧（media/AndroidMediaSink.kt:455-459；常量 :759）。参考链门控：只有在需要时接受含 IDR/IRAP 的 AU（media/VideoDecodeQueue.kt:16-23、MediaCodecSupport.kt:97-116）。输入缓冲 10ms 超时，等待输入期间持续 drain 输出（VideoInputPump，media/VideoDecodeQueue.kt:54-71）。时间戳 = `System.nanoTime()/1000`（media/AndroidMediaSink.kt:660）。
6. **渲染**：`dequeueOutputBuffer(info,0)` → `releaseOutputBuffer(index, true)` 直接交给 Surface（media/AndroidMediaSink.kt:686-707）；首帧回调 "first frame rendered" 一路传到 UI（airplay/CarPlayMediaEngine.kt:104-107；common/CarPlayHostActivity.kt:3675-3679 用于启动重试预算）。
   - Surface 类型：主屏 TextureView 的 SurfaceTexture（common/CarPlayHostActivity.kt:455-496、1238-1241、4440-4447）；仪表集群用 SurfaceView（common/ClusterMapPresentation.kt:101）；另有"镜像 Surface"机制把 111 流同时解到多个 Surface（media/AndroidMediaSink.kt:208-226；common/MapMirrors.kt）。
   - 尺寸/缩放：不动 Surface 尺寸，用 TextureView `setTransform` 做等比 letterbox（common/CarPlayHostActivity.kt:4149-4175；media/CarPlayVideoLayout.kt:9-17）；letterbox 区触摸被整段忽略（common/CarPlayHostActivity.kt:4501-4511）；view area 模式下按画布坐标裁剪（:4154-4161）。
   - 用户可调"画面"仅对 TextureView 层做 ColorMatrix（亮度/对比度/饱和度/色温）（common/CarPlayPicture.kt:63-86）。
7. **恢复**：解码失败/积压→释放解码器→等新关键帧；关键帧请求经 `forceKeyFrame` 命令（主屏）/ `forceKeyFrame+ALT_UUID`（附属屏），限速 1 次/秒（media/AndroidMediaSink.kt:669-684；airplay/CarPlayMediaEngine.kt:108-119）。
8. **分辨率协商**（与 1280x720 屏相关）：画布尺寸取自宿主窗口像素的偶数对齐值，再乘"分辨率百分比"(30-160%) 与 UI 放大预设(75/85/100/115%)；放大会先查解码器能力（common/CarPlayHostActivity.kt:3307-3341、3271-3305；airplay/CarPlayDisplayScale.kt:33-47；airplay/CarPlayUiScale.kt:19-38）。默认即 1:1 上报屏幕像素（1280x720），画面不再缩放除非用户设置。

### 3.2 音频链路

1. **协议能力宣告**：type 100 "default/alert" 声明 PCM|Opus；100 "telephony/speechRecognition" 声明 PCM(单声道)|Opus + 输入格式；102 "media" 只声明 AAC-LC；开启 buffered 时 type 103 media = AAC-LC（airplay/AirPlayInfoPlist.kt:121-159；audioLatencies 全 0，:104-119）。`disableAudioOutput=true` 时整个音频段从 /info 移除（:28-29、51-54；airplay/AirPlayConfig.kt:82-83）——这是唯一的"总静音"开关。
2. **接收**：每流绑定数据/控制两个 UDP 端口，收包缓冲申请 512KB（airplay/AudioStream.kt:55-76）；整包按"12B 明文头 + 密文 + 16B tag + 8B 小端 nonce"解（airplay/AudioStream.kt:124-146），AAD=头部 [4,12) 字节；解密失败计数并只记首包日志（:133-146）。解码器支持的格式来自 `audioFormat` 位：AAC-LC 48k/44.1k 立体声、Opus 48k 单声道、LPCM 表（:214-252）。
3. **解码/播放**（media/AndroidMediaSink.kt:776-1512）：
   - AAC-LC：给解码器配 `KEY_IS_ADTS=1` + AudioSpecificConfig（media/AndroidMediaSink.kt:907-929、1127-1133），每个 AU 再包 7 字节 ADTS（media/MediaCodecSupport.kt:119-132）；
   - Opus：手写 csd-0/1/2（OpusHead/codec-delay/seek-pre-roll，:1148-1172），跳过 <4B 的短包；
   - LPCM：去 12B 头 + S16LE→大端交换后直写（media/AndroidMediaSink.kt:1178、1450-1457）；
   - 解码 PCM16 → AudioTrack（MODE_STREAM，`write(..., WRITE_BLOCKING)`，:1327）。
4. **缓冲策略**（media/MediaAudioBuffer.kt:21-43；media/AndroidMediaSink.kt:951-1041、1304-1378）：媒体声道 300/500/1000ms + 200ms 余量；非媒体（通话/Siri/导航）用 `minBuffer*4` 小缓冲。压缩包队列 192 个（≈4s AAC，:1507），满则丢最新；PCM 写满启动阈值才 `play()`；媒体轨在"欠载 + 压缩队列空 + 硬件缓冲真正排空"时 pause 等再缓冲（media/AudioBufferProgress.kt:18-20；media/AndroidMediaSink.kt:1362-1378）；首帧做 10ms 淡入（:1438-1448）。
5. **路由/焦点/音量**：AudioChannelMapper 把 audioType 映射为 usage（media→MEDIA、telephony→VOICE_COMMUNICATION、speechrecognition→ASSISTANT、default/alert→导航提示音）（media/AudioChannelMapping.kt:36-90）；可选用 legacy streamType 覆盖（设置项 mediaChannel/navigationChannel；media/AndroidMediaSink.kt:1043-1068）。焦点由 sink 级 AudioFocusCoordinator 统一申请，按优先级选代表通道，临时丢失时降到 0.2 音量，**不放弃**永久丢失（media/AndroidMediaSink.kt:39-118）；导航音不申请焦点（media/AndroidMediaSink.kt:1093-1101）。音量只有"降音"用 `setStereoVolume`（:102-104），没有独立静音接口。
6. **type103 增强缓冲**（airplay/BufferedAudioStream.kt:70-127）：TCP 收 2 字节长度帧，8MB/120 秒上限，满则 TCP 背压（:107-119、319-320）；SETRATE/GETANCHOR/SETRATEANCHORTIME/FLUSHBUFFERED 控制与锚点 plist（:198-217、357-365）；只把帧"提前约 1s"喂给同一个 MediaSink，使焦点/路由与普通媒体一致（:152-186、321-323）。默认关闭（实验项）。
7. **/feedback**：每 5s 汇报各流"当前样本位置"（首样本 + 已播时长 - 上报的 playout latency），时钟用 NtpClock 同步（airplay/CarPlayMediaEngine.kt:415-443；airplay/NtpClock.kt）。

### 3.3 麦克风（Siri/通话）采集与回传

- 触发条件：仅主音频流(type 100)且 audioType=telephony/speechrecognition、且宿主拿到 RECORD_AUDIO（common/CarPlayHostActivity.kt:549-558、3652；airplay/CarPlayMediaEngine.kt:537-576）。配置含：phone 的 dataPort、remoteAddress、输入密钥（DataStream-**Input**-Key）、帧长（framesPerPacket 换算，5-60ms，缺省 20ms）、Opus 码率（按格式位 48k/64k/96k）。启动时机 = 首包下行到达（onStarted，airplay/CarPlayMediaEngine.kt:176-183 → media/AndroidMediaSink.kt:291-305）；telephony 会先把 AudioManager.mode 切到 MODE_IN_COMMUNICATION 再建 AudioRecord（media/AndroidMediaSink.kt:315-325）。
- 采集：AudioRecord.Builder + PCM16；source 按类型选 VOICE_COMMUNICATION / VOICE_RECOGNITION / MIC（media/MicrophoneUplink.kt:62-105）；缓冲 `max(minBuffer*2, frameBytes*4)`（media/MicrophoneUplink.kt:78）；telephony 附加 AEC + NS（可用则启用，不可用不阻塞，:141-170）。读循环 4 参 `read(..., READ_BLOCKING)`，按帧长切包（:180-225）。
- 编码：Opus 可用时走 MediaCodec 编码器（48k 单声道、20ms、`INPUT_DURATION_US=20000`）（media/OpusEncoder.kt:12-73）；否则 PCM 大端化（`toWirePcm`，airplay/MicrophonePacketizer.kt:104-115）。RTP 时间戳步长按 `opuClockRate`（Siri 观察值 24k、通话 48k）（airplay/MicrophonePacketizer.kt:6-49）。
- 打包/发送：12B RTP 头（seq 递增、ts 按步长）+ ChaCha20-Poly1305 封包（AAD=头部[4,12)），8B nonce 附在 tag 后；UDP 发往 phone（airplay/MicrophonePacketizer.kt:71-102；media/MicrophoneUplink.kt:227-264）。失败仅计数不打断下行走廊（media/AndroidMediaSink.kt:294-305 sink 侧也兜住异常）。

### 3.4 触摸/按键回传

1. **采集**：整个视频面上的透明"gesture layer"接收 MotionEvent（common/CarPlayHostActivity.kt:1243-1248）；`onHostTouch` 先处理"多指下滑打开设置"手势（可配手指数，触发时先发空触摸清零，:4452-4499），再按 `contentRect` 判断 letterbox 外触摸丢弃，最后 `CarPlayTouchMapper.contacts` 把坐标归一化到画布空间（≤2 指，正确处理 ACTION_POINTER_UP，media/CarPlayTouchMapper.kt:13-32）。
2. **发送**：`CarPlayController.sendTouch` 用单线程 touchExecutor 串行化（orchestration/CarPlayController.kt:457-466、196）→ `AirPlaySession.sendTouch` 先把归一化坐标乘回协商显示像素（airplay/AirPlaySession.kt:333-336）→ `AirPlayHid.touchReport` 生成 2 指×6B（slot、down、x/y 各 u16 LE，airplay/AirPlayHid.kt:43-54）→ `hidSendReport` 组 `POST /command` bplist `{type:"hidSendReport", uuid, hidReport}`（airplay/AirPlaySession.kt:426-433）→ 经事件通道（HKDF "Events-Salt" 读写密钥 + ControlCipher 加密、TCP_NODELAY，:836-878、842-843）。失败（事件通道未就绪）只记一次日志并返回 false（:348-350）。
3. **触点上限/描述符**：HID 描述符声明 2 指、xMax/yMax=协商分辨率（airplay/AirPlayHid.kt:88-103、AirPlayInfoPlist.kt:57-62）；HID UID：触屏 0x2a2a2a2a、旋钮 …2b、媒体 …2c、电话 …2d（AirPlayHid.kt:23-26）。
4. **按键**：旋钮/方向/确认/返回→knobReport（4B：select/home/back 位 + x/y/wheel 有符号轴，:56-67）；物理媒体键→CarPlayMediaButton 映射（含 BYD 专用键码，airplay/CarPlayMediaButton.kt:48-58；common/CarPlayMediaKeys.kt:326）；接/挂电话→telephony hook/drop（CarPlayController.kt:557-572）；Siri→`requestSiri` 命令（siriAction 2/3，airplay/AirPlaySession.kt:372-375）。down/up 成对发送实现"瞬时"按压（AirPlaySession.kt:354-370）。
5. **延迟观测**：触摸发送时刻写入 TouchLatencyProbe，下一帧到达时由 VideoStats 5s 窗口输出 "touch2frame avg/max"（media/TouchLatencyProbe.kt:4-19；media/VideoStats.kt:26-32、48-54）。

### 3.5 androidx.media3 / ExoPlayer 的实际用途

**不是 CarPlay 主链路**。全仓库 media3 仅出现在 `common`：`CarPlayVideoActivity.kt`（ExoPlayer.Builder + PlayerView，common/CarPlayVideoActivity.kt:88-89、111）与 `IphoneResolvingDataSource.kt`，服务于 iOS 27 "video in car"（停车时播放 iPhone 下发的媒体 URL，含 HLS；依赖声明在 common/build.gradle.kts:42-44，版本 media3=1.11.1，gradle/libs.versions.toml）。CarPlay 的镜像视频/音频/麦克风全部走自研 MediaCodec/AudioTrack 路径，与 media3 无关。注意：media3 1.11 要求 API≥21，若 CS11 保留该功能则需要替换播放器（可用框架 MediaPlayer，或直接砍掉此附加功能）。

## ④ 线程与缓冲模型

| 线程/执行器 | 归属 | 职责 | 备注 |
| --- | --- | --- | --- |
| `airplay-control` | AirPlaySession | RTSP 收/回（含 SETUP/TEARDOWN/命令） | 单连接读写循环 |
| `airplay-screen`（每屏一路） | ScreenStream | TCP 收帧→解密→Annex B | 收满即处理；统计见 StreamReceiveStats |
| `airplay-audio-rx` / `airplay-rtcp-rx` | AudioStream | UDP 收包解密 / RTCP 丢弃 | 8B nonce+16B tag |
| `airplay-buffered-rx` / `-feed` | BufferedAudioStream | TCP 预收 / 按 ~1s 前导喂 sink | lock 内串行化 pause/flush/close |
| `airplay-event-accept` + 事件读线程 | AirPlaySession | HID/命令下发 + 响应 | 写操作由 eventWriteLock 串行（airplay/AirPlaySession.kt:288-331、913-916） |
| `carplay-video`（每解码器，含镜像） | VideoDecoder | configure/喂帧/drain/恢复 | 队列 60 帧/8MB，250ms 老化（media/AndroidMediaSink.kt:414-459） |
| `carplay-video-recovery` | 单线程 Executor | 发送 forceKeyFrame | 去重标志 recoveryPending（media/AndroidMediaSink.kt:172-193） |
| `carplay-audio`（每流） | AudioRenderer | 解包→解码→AudioTrack 写 | 队列 192 包；写阻塞在 writePcm |
| `carplay-mic`（每上行） | MicrophoneUplink | 读→编码→封包→UDP | close join 500ms |
| `touchExecutor`（单线程） | CarPlayController | 触摸/旋钮/命令串行发送 | 防止输入乱序（orchestration/CarPlayController.kt:196） |
| `airplay-ntp-rx/-tx`、`airplay-keepalive` | NtpClock / Session | 时钟同步与保活 | /feedback 用 |

缓冲要点：视频"丢帧只丢到下一个关键帧"（Resync+forceKeyFrame ≤1/s）；音频媒体流用 300ms 级抖动缓冲 + pausal 再缓冲，其余低延迟；type103 用 8MB/TCP 背压保音乐；麦克风不排队（读多少发多少）。

## ⑤ CS11 适配观察（API 19 风险与硬件解码）

### 5.1 阻塞级：API>19，会抛异常/无法工作（最小改动 = 逐处门禁 + 替代实现）

视频/解码：
- `MediaCodec.getInputBuffer/getOutputBuffer`（**API 21**）：media/AndroidMediaSink.kt:656、1231、1287（OpusEncoder 亦用 :56、93）→ 低版本需改用 `getInputBuffers()/getOutputBuffers()`（API 16）。
- `MediaCodec.setOutputSurface`（**API 23**）：media/AndroidMediaSink.kt:622。该调用只捕获 `Exception`（:625），NoSuchMethodError 属 LinkageError，会被 run() 的 LinkageError 分支（:473-476）上报后重抛 → **解码线程直接死亡**。API19 上改 Surface 必须走"释放+重组"路径。
- `MediaCodecList(MediaCodecList.REGULAR_CODECS)/codecInfos/isSoftwareOnly`（**API 21/29**）：media/AndroidMediaSink.kt:587-590（有 SDK≥Q 门禁，功能上安全，但 API19 下"软件解码回退"不可用）。
- `MediaFormat.MIMETYPE_VIDEO_HEVC`（API 21 常量）+ HEVC 解码在 4.4.3 无实现：media/AndroidMediaSink.kt:505、593-608。
- `KEY_PRIORITY`/低延迟键：media/AndroidMediaSink.kt:549、567（低延迟本身已有 R 门禁；KEY_PRIORITY 属"tuned"尝试，失败可回退 untuned，见 media/AndroidMediaSink.kt:519-527）。

音频/采集：
- `AudioTrack.Builder`（**API 23**）：media/AndroidMediaSink.kt:978-983（默认路径！）、999-1004。CS11 必须全程改走旧构造器 `AudioTrack(streamType,...)`（代码已有此路径 + `LegacyAudioFallback`，:987-1006；media/LegacyAudioFallback.kt:4-17）——但旧构造器只接受 streamType，需要给每个 usage 选定一个流类型（现有 `mediaChannel/navigationChannel` 覆盖机制可复用）。
- `AudioTrack.write(..., WRITE_BLOCKING)` 4 参重载与常量（API 21）：media/AndroidMediaSink.kt:1327 → 用 API 3 的三参 `write()`（其语义即阻塞）。
- `AudioTrack.getUnderrunCount`（**API 24**）：media/AndroidMediaSink.kt:1357、1365、1385；`AudioTrack.getRoutedDevice`（**API 23**）：:1397；`AudioRecord.getRoutedDevice`（**API 23**）：media/MicrophoneUplink.kt:266。前者需要替代欠载判据（如仅靠 playbackHeadPosition/写超时），后两者纯诊断、可直接停用。
- `AudioFocusRequest` 全套（**API 26**）：media/AndroidMediaSink.kt:48-100 → 旧版必须换 `requestAudioFocus(listener, streamType, gain)` 老接口（或者 CS11 先关闭 audioFocusEnabled）。
- `Context.getSystemService(Class)`（**API 23**）：media/AndroidMediaSink.kt:145、common/CarPlayHostActivity.kt:515 → 换字符串版。
- `AudioFormat.Builder`（**API 21**）：media/AndroidMediaSink.kt:1107-1111、media/MicrophoneUplink.kt:83-87；`AudioAttributes.Builder`（**API 21**）：media/AndroidMediaSink.kt:1059-1067；旧版需要在 legacy 构造器里直接给 streamType。
- `AudioRecord.Builder`（**API 23**）+ 4 参 `read(..., READ_BLOCKING)`（**API 23**）：media/MicrophoneUplink.kt:80-90、189 → 换 `AudioRecord(source, rate, mask, fmt, bufSize)` 与三参 read。
- `MIMETYPE_AUDIO_OPUS`（**API 29**）+ 平台 Opus 解码/编码（API 21+，4.4.3 无）：media/AndroidMediaSink.kt:872、918、media/OpusEncoder.kt:15、22。**后果**：若 iPhone 协商了 Opus 的 telephony/Siri 流，下行无声、上行也编不了 → 适配时应在 /info 只宣告 PCM（去掉 opus 位，airplay/AirPlayInfoPlist.kt:140-143），或自带软编解码。
- `AtomicLong.accumulateAndGet`（Java 8 API，Android 需 API 24 或 desugar）：media/AndroidMediaSink.kt:847。

其它（越界但已顺带确认）：`java.util.Base64` 需 API 26（airplay/VideoInCar.kt:113）；media3 需 API 21（见 3.5）；当前 minSdk=28（shared/build.gradle:9、common/build.gradle.kts:13、mobile 18、automotive 14）。

### 5.2 适配现状可复用点
- 视频侧 API 19 可用的部分：`createDecoderByType/configure/start/dequeueInputBuffer/dequeueOutputBuffer/releaseOutputBuffer(render=true)` 均为 API 16，CSD 走 `csd-0`/`csd-1` 也是 16 时代约定 → **只要换掉 getInputBuffer/getOutputBuffer 与 setOutputSurface，H.264 硬解链路在 API19 上有机会直接跑通**。
- `AudioTrack.getBufferSizeInFrames`（API 19 起）可用（media/AndroidMediaSink.kt:1012、1400）——缓冲计划逻辑本身不越界。
- 代码里已有大量兼容痕迹：LegacyAudioFallback、tuned/untuned/软件三级尝试、`audioTrackAttributesForFocus` 的 Q 门禁（media/AndroidMediaSink.kt:34-36，注释称 AudioTrack.audioAttributes 取用需 Android 10，待验证——但反正有门禁）。

### 5.3 硬件解码适配点（Freescale VPU）
- CS11 上应固定 H.264、关闭 hevc 开关（/info 不宣告 hevcInfo，airplay/AirPlayInfoPlist.kt:75），让 iPhone 送 avcC 流；HEVC 在 4.4.3 无软件解码，必然失败。
- `OMX.Freescale.std.video_decoder.avc.v3.hw-based` 属老式 OMX 组件：对 `KEY_PRIORITY` 等"tuned"键的容忍度未知（**待验证**），但代码已有 tuned→untuned 回退，预期能把配置期失败吸收（media/AndroidMediaSink.kt:519-527）。
- 解码器解析 avcC 时用的是"首个 SPS/PPS + 4B 起始码"，这是 4.4 时代的标准做法（media/MediaCodecSupport.kt:15-23）——与 CS11 兼容性预期良好。
- 能力查询 `videoCapabilities.isSizeSupported/areSizeAndRateSupported` 属 API 21（common/CarPlayHostActivity.kt:3283-3286），API19 需要改写（用 `getCapabilitiesForType` + 自行判断，或直接跳过 enlarge 检查）。
- 1280x720/160dpi：默认画布=窗口像素（1280x720），与面板 1:1，无需放大；建议 CS11 默认关闭 UI 放大与"分辨率>100%"设置，避免触发额外解码负载。
- Surface 类型：TextureView 在 API19 可用，但 i.MX6 上 SurfaceView 的合成开销更低；仓库已有 SurfaceView 方案（common/ClusterMapPresentation.kt:101）可参考切换主屏渲染（**待实机验证**收益）。

## ⑥ 未决问题 / 待验证

1. **CS11 实测**：Freescale 解码器对 tuned 参数的接受度；MIME `video/avc` 上 `csd-0/1` 是否需要同时提供（当前代码只给 csd-0/csd-1 两个 ByteBuffer，标准做法）。
2. **getInputBuffer 替代**：低版本 `getInputBuffers()` 的索引复用与 `dequeueInputBuffer` 返回值的对应关系需实测（老 API 下 buffer 数组在 flush 后会失效，视频恢复路径要重取）。
3. **`track.audioAttributes` 真实可用版本**：源码注释称 Android 10（media/AndroidMediaSink.kt:34-36），与官方文档描述可能有出入——不影响适配（有门禁），但标注待验证。
4. **Opus 降级策略**：需要确认 iPhone 在 /info 只声明 PCM 时是否必定回落到 LPCM（telephony/speech 是否仍能工作）——建议上机抓 /info 与 SETUP 验证。
5. **音频焦点（API19 老接口）**语义差异：老 `requestAudioFocus` 传入具体 streamType，与本项目"usage 优先"的设计不完全对齐，需要设计映射表（media→STREAM_MUSIC 等）。
6. **type103 buffered audio** 依赖 HTTP/AirPlay 特性较新（iOS 27），在 CS11 有线时代无意义，建议移植时直接关掉（默认本就关闭）。
7. **触摸延迟**：现有统计表明链路完整（touch→HID→iPhone→新帧），但 CS11 上 1280x720 编码端（iPhone）与解码端帧率能否支撑 <100ms 未测。
8. 麦克风与通话：AudioRecord 在 4.4.3 上以 48kHz 采集 + (可选)Opus 编码的实际可用性未测；若不可用，退化为 PCM 采集（MicrophonePacketizer 已支持）。
