## 5. 性能采样（用新增指标判读，doc 27 §7）

在 CarPlay 里**连续滑动 30~40 秒**（地图拖动最敏感），期间：

```bash
adb -s 0123456789ABCDEF logcat -c
# 滑动期间保持抓取
adb -s 0123456789ABCDEF logcat -v time > cs11_perf.log
# 滑完后 Ctrl-C，然后提取统计行
grep "video stats" cs11_perf.log
```

每 5 秒一行的判读表：

| 字段 | 含义 | 判读 |
|---|---|---|
| `rx` / `shown` | 收到 / **上屏**帧率 | 两者接近=管线跟得上；`shown` 明显低于 `rx`=丢帧 |
| `maxGap` | **到达**间隔峰值 | 远大于 33ms（如 >100ms）= 空口成批到达（省电/DTIM 特征） |
| `shownP50` / `shownP95` | **上屏**间隔分位 | p95 ≫ p50（如 33ms vs 150ms）= 上屏节奏不均，**此时才值得做节奏器** |
| `dropped` | 因迟到 >250ms 被拒绝上屏的解码帧 | >0 且持续 = 下游跟不上（该降档/降帧率） |
| `queueMax` | 解码队列峰值 | 持续贴上限（60 帧/8MB）= 积压，接近 `recoveries` 触发 |
| `recoveries` | 重建解码器的次数 | **必须为 0**；>0 就是肉眼可见的卡死 |
| `touch2frame avg/max` | **手指→上屏**（含排队） | avg 目标 <100ms；max 反映最坏卡顿 |
| `touchQueueMax` | 触控等待写入的最长时间 | 接近 200ms 的整数倍 ⇒ 疑为上行排队/DTIM，非 app 逻辑问题 |
| `touchSendMax` | 单次写事件通道耗时 | 与上表对照，区分"写慢"还是"排队久" |

## 7bis. 画布 / UI 缩放 与 **CarPlay 图标行数**（2026-10-08 发现，待复核）

**现象**：用户记得做分辨率实验**之前** CarPlay 主页是**三行图标**，1080p 实验回退到 720p 之后变成**两行**。
**已查明的事实**：今晚所有会话广播的画布都是 **1280×641 / negotiated 1280×640**，而**首亮时是 1280×650**（doc 27 §6）——即**画布在你做 1080p 实验之前就已经少了 10px**，所以行数变化不是 1080p 直接造成的。

**决定行数的两个持久化项**（都在 app 设置里，都会改变我们向 iOS 广播的显示配置）：

| 偏好键（`xcertplay_airplay.xml`） | 作用 | 默认 |
|---|---|---|
| **`ui_scale_percent`** | `CarPlayUiScale.apply()`：当它 ≠100（预设 75/85/115）时会把**广播画布整体放大** `width×100/scale` 并等比缩放安全区 → **iOS 据此重排图标布局** | `CarPlayUiScale.DEFAULT = 100` |
| `display_scale_tenths` | 画布像素比例（"分辨率百分比"），`DEFAULT_TENTHS = 10`（=100%） | 10 |
| 顶部/底部系统栏隐藏开关 | 改变窗口 inset → **画布高度**（650→640 的 10px 差正好是系统栏级别）与广播的安全区 | 见 app 设置 |
| `safeAreaRects`（按 `DisplaySize` 分键） | 1080p 那一轮可能写入了按 1920×1080 的条目 | 无 |

**下次上车 1 分钟复位（推荐先走 app 设置，最直观）**：
1. DiPlay 设置 → **UI 缩放**：确认是 **Default（100%）**，不是 Small/Smaller/Large；
2. DiPlay 设置 → **状态栏/导航栏**开关：恢复到"首亮时"的状态（用于把画布从 640 拉回 650）；
3. 若仍不对，root 下核对并复位这三处（属主 10034/660 要保持）：
   ```
   busybox grep -E "ui_scale_percent|display_scale_tenths|safe_area|hide_(top|bottom)_bar" \
       /data/data/com.shihab.diplay.hudtest/shared_prefs/xcertplay_airplay.xml
   ```
   把 `ui_scale_percent` 改回 `100`、`display_scale_tenths` 改回 `10`，并删掉 1080p 尺寸下的 `safeAreaRects` 条目，然后重启 app + iPhone 重连。
4. 若三者都已是默认、广播也回到 1280×650 而仍是两行 → 判为 **iOS 侧缓存**，按首亮的办法在 iPhone 上**删掉本车 CarPlay 记录再连**（历史上这一步解决过"陈旧状态"）。

**验证口径**：每次会话日志第一行 `starting controller display=WxH negotiated=WxH scale=N%` 就是我们所广播的画布，**先比这个数，再谈行数**。


**结束提醒**：不需要 adb 时及时**熄火**（怠速费油）；把结果写回 doc 27，避免下次重复点火。

## 8. 2026-10-09 增量判据（本次会话新增，建议与上面各项**同一次点火做完**）

> 新增代码：`cs11-api19` @ `5863dd7c`（本会话 17 个提交）。以下每项都给了**可执行的判据**，其中标注「平板无法验证」的项已确认在平板上做不了，只能在车上做。

### 8.1 音频修复实机复测（最高优先，**必须**）
本轮修掉的根因是我引入的 16 B AEAD tag 长度错误（doc 43）。车机（API 19 / `OMX.google.aac.decoder`）上的同一路径**尚未实机复测**。
```bash
adb -s <车机> logcat -d -v time | grep -E "audio decoder output codec|0x4004|audio stats audioType"
```
**通过判据**：`audio decoder output codec=AAC_LC … bytes=4096`（**不是 8192**）、`0x4004` 命中 **0**、`skippedMs=0`、平台计数 `Qin` ≈ 47/s（不是 118/5s）。
同时采一次音频侧 CPU（`top -H -p <pid>` 或 `dumpsys cpuinfo`）记录 `carplay-audio` / `gle.aac.decoder` / `MediaCodec_loop` —— doc 41 记的 ~25% 单核是 10-08 旧数据（那时还没有这个 bug，但也没有本轮的日志门控与就地解密）。

### 8.2 USB 读队列策略是否真的生效
```bash
adb -s <车机> logcat -d -v time | grep -E "read queue compatibility fallback|USBMUX|NCM read"
```
**通过判据**：出现 `USBMUX|NCM read queue compatibility fallback api=19 …` 说明 API<28 的 16 KiB 天花板已被策略接管；若未出现（vendor 接受 16 KiB），则看阶梯是否落到 8/4/2 KiB 且吞吐可接受（不出现 `IllegalArgumentException`）。

### 8.3 `TcpLiveness` 的 API 19 反射分支（**唯一只在 4.4 才走到、从未实机验证过的代码**）
```bash
adb -s <车机> logcat -d -v time | grep -E "TCP peer health configured|keepalive"
```
**通过判据**：出现 `keepalive=true userTimeout=true`；若为 `false` 或不出现 ⇒ 反射路径失败（`sun.nio.ch.SelChImpl` / `libcore.io.Libcore` 在该 ROM 上不可用），需要回退方案。修复前该函数在 API19 **直接 return**（空操作），所以这是新代码。

### 8.4 F7：`bulkTransfer` 在 4.4 是否有 16 KiB 上限（本机判不了，doc 44 §F7）
**一次性实验**：debug 构建临时发一次 **16420 B** 的 frame（或把 `MAX_TCP_SEND_PAYLOAD_BYTES` 临时改回 `16 * 1024`），打印 `bulkTransfer` 返回值。
- 返回 `-1`（或 < 请求长度）⇒ 天花板对**写**路径成立 ⇒ 本轮的分块（16348+16+20=16384）**必需**，不要为大包做优化；
- 返回 `16420` ⇒ 写路径无此限制，分块只是 0.22% 成本，建议保留但可重议。
顺带记录连续 16 KiB 写的吞吐，确认多出的 transfer 没推高 NCM 写延迟。

### 8.5 F1 现场验证：畸形 NAL 长度不再打断视频（旧版必断）
从笔记本对数据口发一个「128 B 头 + 8 B body（`7F FF FF FF` + 4 个 0）」的 clear 帧。
**通过判据**：画面**不断**（旧版：`ArrayIndexOutOfBoundsException` 被 `run()` 吞掉 ⇒ 视频流关闭并进入恢复循环）。同时日志中不应出现 `video frame plaintext mismatch`。

### 8.6 「假重连」修复：设置菜单与方形画布（**平板无法验证**——设置菜单只有一个入口＝三指手势，而平板上三指被系统截屏吃掉）
前提：`CarPlayRotation` 打开（方形画布）+ 适配 PiP 分辨率 打开。
1. 三指打开设置菜单、**不碰任何开关**，按返回/「放弃更改」× 关闭 ⇒ **不得**重连（旧版：画面停顿 + `Display changed 1920x1080 -> 1920x1080` 紧跟 `Settings changes discarded; reconnecting`）；
2. 顶部/底部状态栏开关**来回拨回原状态**再放弃 ⇒ 同上；
3. 切到环绕/倒车窗口再切回满屏 ⇒ 保持连接（只有**真正**窄窗口才按设计重连）。
**通过判据**：日志出现 `keeping CarPlay session canvas=…`，不出现 `restart`/`reconnecting`。

### 8.7 三指手势容错（**平板无法验证**：Android 15 的系统三指截屏会先吃掉手势）
1. 三指**一次性**按下并**连续**下滑（不停顿）⇒ 应开设置菜单（旧版会漏）；
2. 三指下滑到一半**先抬一指**再继续 ⇒ 抬指那一刻即判定（旧版会丢）；
3. 三指**横向**滑 / 三指**向上**滑 / **两指**在画面上慢慢滚 ⇒ **不得**开菜单（防回归）；
4. 设置里改 **2/4 指**后重复 1–3 的同构动作 ⇒ 行为随配置同步。

### 8.8 流 12 导航音量 + vendor AAC 解码器枚举
- 导航播报时看 `audio route type=12`（`streamType=12` 归属正确），且**不应**出现新的兜底行 `Audio: stream rejected preferred=12`（出现即走兜底）。
- 枚举车机解码器：`adb shell dumpsys media.codec | grep -i aac` 或让 app 打 `MediaCodecList`（doc 41 §1 头号优化项）——若存在**厂商** AAC 解码器，优先它（平板只有 AOSP 那一个，无选择余地）。

### 8.9 有线 vs 无线音质 A/B（同曲同段落，离线比对）
有线抓 `type=100`（LPCM 48k/16bit 立体声，1.536 Mbps，零解码）与无线抓 `type=102/103`（AAC-LC ~245 kbps，软件解码）。
**比对三项**：频谱（AAC 高频截止）、相关性/信噪比（量化失真量）、丢包/间断计数（"滋啦"倾向）。离线用 `_analysis/` 现有脚本 + ffmpeg。
已知权衡（doc 18/20）：**有线保真度更高但无缓冲掩蔽**（链路抖动直接可闻）；**无线有缓冲/抖动免疫但损耗真且吃 ~25% 单核**。

### 8.10 仪表投屏收尾（doc 38）
换歌后封面是否正确重写；转向点是否走厂商 `INavigationDI.turnByTurn`（而非我们自绘）。

### 8.11 例行回归（每轮点火都值得扫一眼）
- 音频回归：`bytes=4096`、`0x4004=0`、`skippedMs=0`；
- 日志**每行只出现一次**（`Receive: audio/video …` 不再双写，本轮修复 `83d064b4`）；
- 麦克风上行走 native：`Microphone: encoder … implementation=libopus`（若显示 `software` ⇒ `.so` 未加载，纯 Java 编码在 A9 上会吃 25–55% 单核）；
- 不应出现：`audio AAC skipping oversized access unit`、隧道 `package size out of range`、`video frame plaintext mismatch`；
- 视频：`recoveries=0`、`dropped=0`、`queueMax` 不贴上限；解码队列深度**不得为负**；
- iAP2 封面传输回归（本轮加了 32 文件 / 256 KiB 独立配额，超配额**丢积压不回包、不打死链路**）：连续切歌 20 次看封面是否都能出、控制是否不卡。

## 9. 2026-10-09 夜增量：仪表投屏与组网拓扑（由三份审计派生，doc 45/46/47）

> 背景：指标仪表（**液晶仪表 = 方向盘后那块真仪表**）只有「DIM 原生注入」这一条路能画上去（中控卡片是另一条路，无关）。审计已确证我们这台车的 DIM 推送**导航那一半从未生效**（反射分发器丢弃装箱原始类型，doc 46 G1），并给出可观测判据。

### 9.1 仪表导航：厂商服务端自带的验收日志（**首要判据**）

**开关已改为持久化设置（2026-10-10，提交 `f77c179c`）**：安装后**默认开、重启仍生效**，因此**不再需要 `setprop`**。设置里新增一行
**「仪表盘投屏 · 媒体与导航」**（`cluster_bridge_enabled`，默认 true；描述里写明"本车没有抬头显示（HUD）"）。
`setprop` 仍可作**临时覆盖**做台架对照：`debug.diplay.cluster 1` 强制开、`0` 强制关、未设置则由设置决定。

```bash
adb -s <车机> shell setprop debug.diplay.trace 1     # 仅为让 call() 的 trace 行打出来（设置里的"调试日志"等效）
adb -s <车机> logcat -c
adb -s <车机> logcat -s DiPlay-Cluster:I DiPlay-Dim:I NavigationDimInteraction:D DiServer:I DimInteractionImpl:D
```
用 Apple 地图开始导航（要有转向指令），然后看：
- **P0 开关状态**（每次启动一行）：`cluster push setting=true property=unset enabled=true` ⇒ 这就是"重启后无需 adb 即生效"的判据；
  关掉设置里的开关应是 `setting=false`；`setprop … 0` 应是 `property=0 enabled=false`（此时**完全没有推送日志**，属预期）。
- **P1 绑定成功**：`DiPlay-Cluster` 出现 `cluster navi interaction=com.ecarx.xui.adaptapi.diminteraction.NaviInteractionImpl`；`DiServer` 出现 `appType = com.ecarx.di_server`。
  （`getNaviInteraction()` 首次可能为 null —— 厂商异步绑定，会留到下一次更新重试，属正常。）
- **P1b 调用真的发出**（`f77c179c` 的判据）：trace 行**带所选签名**，例如 `cluster updateETA(int) args=[…] -> null`、
  `cluster updateCurrentProgress(long) …`、`cluster updateDistanceToNextGuidancePoint(int) …`、`cluster updateTurnByTurnArrow(int) …`。
  **括号里的 `int`/`long` 就是修复的证物**（修复前这些调用根本不会执行）。若写成 `… -> skipped: no overload matches`，或出现
  `cluster updateETA has no matching overload: args=[…] candidates=[…]`（同名只打一次），说明匹配仍有问题，把这两行原样留给开发者。

### 9.9 API 19 越界审计的实机判据（2026-10-10，doc 49）
