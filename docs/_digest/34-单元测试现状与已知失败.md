## 九个既存失败：真正的原因与修法（2026-10-11 定案）

> ⚠️ **本文 2026-10-08 写的根因有两条是错的**，下面是查清后的版本（错误判断保留在括号里，避免下一位接手者再被误导）。

### 1) `:common` × 3 `CarPlayControllerUsbServiceTest` —— **真缺陷**（API-19 兼容清扫引入的回归）

```
java.lang.NullPointerException
    at com.shilapi.xcertplay.compat.Cs11CompatKt.systemService(Cs11Compat.kt:21)
    at com.shilapi.xcertplay.orchestration.CarPlayController.<init>(CarPlayController.kt:173)
```

- **❌ 2026-10-08 的判断**："测试给 `CarPlayController` 传了 null context"。**错**：测试用的是
  `RuntimeEnvironment.getApplication()`，context 非空。
- **真根因**：`CarPlayController.kt:173` 原文是
  `private val usbManager: UsbManager? = context.systemService(UsbManager::class.java)`，
  作者**期望"没有 USB 服务时得到 null"**（2387/2391 行确实写了
  `usbManager ?: throw IOException("USB service is unavailable on this device")` 的可重试失败态）。
  但 `compat/Cs11Compat.kt` 的 `systemService` 返回类型是**非空** `T`，于是"服务缺失 → null"在函数
  返回处被 Kotlin 的空检查变成 NPE（API≥23）/ `IllegalStateException`（API<23，即车机）。
- **回归时点（提交证据）**：10-05 的 `6e577504`（"Handle unavailable USB service when starting
  CarPlay"）用平台类型 `context.getSystemService(UsbManager::class.java)`（`UsbManager!` 允许 null），
  当时这三个用例是**绿**的；10-06 的 `51c7a44c`（API19 wave-1 `systemService` 兼容清扫，45 处）
  把它换成非空扩展 ⇒ 从那天起一直红。
- **修法**：在 compat 层新增**显式可空**的 `Context.systemServiceOrNull(...)`，`CarPlayController` 的
  `usbManager` 改用它；随后**扫掉全仓其余同类死守卫**（第二批，合计 **21 处 / 11 个文件**，清单见本文末节）。
  `systemService` 的非空签名**不动**（改成可空会波及约 25 个"必需服务"调用点）。
- **反向对照**：把 `usbManager` 改回 `systemService` ⇒ 这三个用例**原样红回去**（NPE），第 4 个
  "USB 存在"的用例仍绿。

### 2) `:common` × 3 `UsbPermissionSetupTest` —— **生产命令是对的**，是测试的"运输层"在 Windows 上吃掉了引号

```
expected:<UNCHANGED> but was:<sh: -c: line 7: syntax error near unexpected token `;;'
sh: -c: line 7: `( current=$(settings get secure enabled_accessibility_services) || exit 1; case $current in null|") current=";; esac; ...
```

- 现象指纹：**双引号整整少一层，单引号没动**（原文 `case "$current" in null|"")` → 收到
  `case $current in null|")`）。
- **真根因**：测试用 `ProcessBuilder("sh","-c",script)` 在 Windows 宿主上跑脚本；JVM 把整段脚本当作
  **一个 Windows 命令行参数**交给 `sh.exe`（本机 `D:\Dev Environment\msys64\usr\bin\sh.exe`），
  MSYS2 的命令行→argv 转换吃掉一层双引号。不是 PowerShell 的锅（Java 直接 spawn）。
- **判决实验（离线，可复现）**：把同一份命令文本写进脚本文件、用同一个 `sh` 执行（绕开 Windows
  命令行），6 个用例全部返回预期值（追加、去重、`null`、空值、非法字符拒绝、读取失败 → `UNCHANGED`）
  ⇒ **`UsbPermissionSetup.command()` 正确**。
  脚本：`work/_probe/usbperm_probe.sh`（用 `D:\Dev Environment\msys64\usr\bin\sh.exe` 直接跑；文件头写了
  期望输出与做法说明）。
- **修法（测试侧）**：`runShell` 改为把脚本字节写进临时文件、用 stdin 喂给 `sh`
  （`ProcessBuilder("sh").redirectInput(file)`），断言一个不改。
- **反向对照**：改回 `sh -c <script>` ⇒ 这三个用例原样红回去。
- ⚠️ 注意这个坑的**影响面**：这段命令是"经 ADB 自动授予无障碍服务"用的，语义是"读现有
  `enabled_accessibility_services` → **追加**自己而不是覆盖"；写错会**破坏用户已启用的无障碍服务
  列表**。在 Windows 上它的测试等于长期没跑。

### 3) `:shared` × 3 `HotspotJoinNormalizedTransactionTest` —— 宿主平台做不到 rename 覆盖，产品代码**正确**地拒绝了这次写

```
expected:<APPLIED>            but was:<STORAGE_FAILED>
expected:<RECOVERY_REQUIRED>  but was:<STORAGE_FAILED>
expected:<FAILED_ROLLED_BACK> but was:<STORAGE_FAILED>
```

- **探针实测（本机）**：
  - `File.renameTo` **不能覆盖已存在的目标文件**（`plainRenameOverExisting=false`；而
    `Files.move(..., REPLACE_EXISTING)` 成功）；
  - `HotspotJoinJournal` 用 `android.util.AtomicFile` 提交，其 commit 就是
    `mNewName.renameTo(mBaseName)`；rename 失败时 **AtomicFile 只写日志、静默吞掉**，把 `.new`
    留在盘上（实测：`base(旧一代) + journal.new(新一代)`）；
  - 且 `AtomicFile.openRead()` 会**删掉残留的 `.new`**（所以只能在 `load()` **之前**发现它）。
- **产品行为正确**：`HotspotJoinJournal.save()` 结尾有"强制复读校验"（注释原文 "Verification is
  mandatory even if an OEM AtomicFile implementation silently fails"），它读到的是上一代 ⇒ 抛
  `IOException` ⇒ 事务返回 `STORAGE_FAILED`，**拒绝把没落地的字节报成成功**。真机 Android=Linux，
  `rename(2)` 原子替换，这条路径是通的（doc 27 有车机上成功写入热点口令的记录）。
- **修法**：
  - 生产侧：把"提交是否落地"变成**显式判定**——`syncDirectory()` 之后若发现 AtomicFile 的
    `<journal>.new` 仍存在，就说明这次提交没落地；此时**没有**注入替换手段的调用方（＝生产）依旧
    抛 `IOException`（行为与修复前一致：仍然是 `STORAGE_FAILED`），只是不再依赖"下一次 `load()`
    恰好把旧一代读回来"这条间接路径；
  - 新增可选的 `replaceUncommittedFile` 注入点（生产默认 `null`，车机行为一字不改）；
    `HotspotJoinNormalizedTransactionTest` 注入 `Files.move(REPLACE_EXISTING)`，于是**三条断言
    原样保留**并在这台机器上真正跑起来（Linux 上该注入点永远不会被用到，仍然测真 AtomicFile）。
  - 新增一条不依赖平台的用例 `HotspotJoinJournalTest.aLeftoverUncommittedTemporaryFileIsNeverReportedAsDurable`
    （用 `syncDirectory` 钩子模拟"提交没落地、`.new` 残留"），把"**残留未提交写永远不得报成功**"
    这条安全性质钉死。
- **反向对照**：只装 `replaceUncommittedFile` 注入点、但不做上面的"显式判定"（即旧实现）⇒
  这三个用例仍然 `STORAGE_FAILED`（本轮实测过这个中间态）。

## 全部"不可达的空守卫"已清掉（2026-10-11 第二批，21 处 / 11 个文件）

`systemService` 的**非空**签名让 `?:` / `?.` 兜底永远不生效（服务缺失时是崩，而不是按作者原意跳过）。
本批把**所有写成空安全的调用点**改成 `systemServiceOrNull`（一词之差；服务存在时行为完全相同）：

```
common/CarPlayMediaKeys.kt:280,293          common/CenterMapOverlay.kt:98,281
common/DiPlayBluetooth.kt:10                common/PhoneMediaAudioWatchdog.kt:79,114
common/DiPlayActivity.kt:1826,1884          common/ProcessExitDiagnostics.kt:25
shared/network/LegacySoftApControl.kt:41,105,177,187
shared/network/WifiP2pGroupManager.kt:716,722,728,734
shared/network/CarHotspotStatus.kt:26       shared/media/AndroidMediaSink.kt:187
shared/orchestration/CarPlayController.kt:176
```

其中 3 处是**上一版 doc 34 没列出来、本轮复查才发现的**：`CarHotspotStatus.kt:26`（`wifi?.let`）、
`LegacySoftApControl.kt:105`（`if (wifi == null)` 打出 "WifiManager unavailable" 后返回 false）、
`DiPlayActivity.kt:1884`（`if (manager == null)` 提示"本车机不支持 Wi-Fi Direct"）——这三条提示/降级
路径此前**永远不会被执行**。

**刻意保留为"必需服务"（fail-fast）的调用点**：其余约 20 处 `systemService(` 的返回值是**直接当非空用**
的（如 `private val wifiManager = …systemService(WifiManager::class.java)`，随后 `wifiManager.xxx`），
没有写任何 `?:` / `?.` 兜底。它们**不是死守卫**——本机缺这个服务时应当立刻报错，而不是静默降级；
要改成可空需要逐个设计"没有它怎么办"，属另一件事。已核对：**全仓再无"带空守卫的 `systemService` 调用"**
（`getSystemService(...)` 平台调用不受影响）。

**本批的测试覆盖与残留缺口**：
- 新增 `shared/.../compat/Cs11CompatSystemServiceTest`（2 例）：可空访问器在服务缺失时**返回 null**、
  非空访问器**不静默返回 null**（抛异常即算通过）。
- 新增 `shared/.../network/ServiceAbsenceGuardsTest`（1 例）：**行为级**证明新修好的守卫真的活了——
  `LegacySoftApControl.requestEnable` 在没有 `WifiManager` 的 Context 上返回 false 并打出
  "WifiManager unavailable"（此前会直接抛异常），`readStoredConfiguration`/`apState` 返回 null。
- ⚠️ **只覆盖 API≥23 分支**：API<23（车机 API 19 走的那条）需要 `android-all` 的 21/22 包，本机离线
  缓存里没有（只有 API 25+），因此**那一条分支只能在车机上验证**（与项目其它 API-19 专用路径同一处境）。
- 其余 18 处**没有逐处单测**：它们的"服务缺失→优雅跳过"分支需要为每个类单独造 fake Context，成本高、
  收益低。它们靠**两道结构性保证**守住：① 服务存在时的行为与改动前逐字节相同（全量 927 + 590 用例与
  构建）；② Kotlin 类型系统——`T?` 只可能被赋给"已经写了空守卫"的位置，**没有守卫的调用点改用它根本
  编译不过**（这也是本轮能确认"21 处全部有守卫、其余 20 处是没有守卫的 fail-fast"的依据）。

## 历史记录：`d756cb3` 已修 —— `android.util.Log not mocked`

`:shared` 原有 16 例失败，其中 **13 例**根因相同：生产代码在测试覆盖的路径上调用 `Log.w`，JVM 单测
直接抛 `java.lang.RuntimeException: Method w in android.util.Log not mocked`，断言根本没跑。
修法：两个模块都开 `testOptions { unitTests.returnDefaultValues = true }`（`shared/build.gradle`
Groovy、`common/build.gradle.kts` Kotlin DSL）。
⚠️ 代价：其它未 mock 的框架调用也会静默返回默认值，若某个测试依赖真实框架实现，它会"假通过"。
