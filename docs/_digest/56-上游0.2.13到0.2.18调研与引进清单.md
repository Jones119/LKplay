## 1. 两个必须先记住的结构性前提

1. **上游已把 minSdk 降到 API 25**（`faea3d3e`）。上游新代码会越来越多直接用 API 25+ 的写法；
   **照抄会砸我们的 API 19/Dalvik**。反过来，有些"上游已经不需要"的兼容分支我们仍需要。
2. **有线路径的架构不同**：上游是**用户态 NCM 桥 + VpnService**；我们车机走**内核 `cdc_ncm` 网卡**
   （`shared/.../orchestration/CarPlayController.kt:1766` 的 `directNetdev`；`rawNcmDecision`）。
   ⇒ 上游那批 NCM 修复作用在他自己的桥上，**对 CS11 的数据路径不生效**（见 §4）。

## 4. 明确不引进（含两条**对子代理结论的纠正**）

| 项 | 结论 |
|---|---|
| **`java.util.Base64` / `Base64Compat`** | **不是缺口，不要移植**。我们三个模块都开了 core library desugaring（`shared/build.gradle:24,63`），`shared/src/test/.../airplay/ForbiddenLibraryApiTest.kt` 把 `java.util.Base64` 明确列入 **DESUGARED**（"covered on purpose"）；AGP 的 desugared-API 清单里 `java/util/Base64`（含 `$Decoder/$Encoder`）是**类级**覆盖，`desugar_jdk_libs-2.1.4.jar` 内确有该类。更硬的反证：用它的有线链路（`LockdownPairRecord`/`AdbKeys`/`LockdownPlistChannel`）**在车机上跑通** |
| **NCM resync / claim ×5 重试 / `515bc9ec` 分帧** | **对我们不适用**（上游修的是用户态 NCM 桥；CS11 走内核网卡，见 §1.2）。`UsbReadQueuePolicy` 我们已**故意做得更宽**（16 KiB 上限从"仅 API 26/27"扩到 API<28，见该文件注释）。`NcmUsbBridge.kt:213` 的短包 pad 仍写死 512 —— 对 High Speed 的我们正确，仅全速 64 字节链路才错 |
| `1c93dc9b` USBMUX "恰好超时完成" | 上游 #610/#301：`cancel()` 失败被当作致命错误 → **整条有线会话结束**。我们**旧代码有同样形态**（`drainCancelledRead`），但已在 `2525fa43` 改成持久请求、超时不再 cancel ⇒ 无需移植；**建议把这条上游根因记入 B1"有线会话莫名结束"那一族** |
| `f5452c5a`+`2f12d483`、`a4b8900d`、`764e0ba1`、`da113e4a`/`66179feb` | **已逐字/等价移植**：`AudioBufferProgress.kt:19`（直接标注上游提交号）、`BufferedAudioStream.kt:25/135-144`、`UsbReadQueuePolicy.kt`、`OpusEncoderSupport.kt:34` |
| `564f8d3f`（Android 7 USB read reaper） | 我们有等价形态（`SDK_INT>=26` 分流 + 持久请求），**但不可超时中断**；等有线卡死日志指向它再按 reaper 重写 |
| compat/加密系列（`e59f6025`/`3a93823a`/`d729cd89`/`54113a78`/`9506fdd4`/`faea3d3e`） | 已被 desugaring + `ForbiddenLibraryApiTest` + 平台 ChaCha→BouncyCastle 双路覆盖；`PendingIntent`/`NotificationChannel`/`clearCapabilities` 我们也已各自守卫。**不移植** |
| BYD/DiLink/FCE/MTK/高通/Leapmotor 专用、WorkManager 后台更新（需 API 23+）、Wi-Fi 扫描暂停、环境灯、side panel、Android 13 本地网络权限、无障碍自动确认 | 不适用（与我们平台/架构无关或需要新 API） |

## 9. 工程教训（第三次出现同一课）

1. **子代理结论必须复核**：本轮两路把"上游已解决/不适用"的东西判成了缺口（Base64、NCM），
   根因都是**只看上游代码、没看我们自己的机制**（desugaring、内核网卡架构）。
2. **"上游文档/发布说明 ≠ 上游代码"**：0.2.18 的发布说明描述的行为，部分只存在于 `release/*` 分支或后续提交；
   引用必须落到 `origin/main` 的 sha + 行号。
3. **上游 minSdk 25 之后，"能不能移植"要先问 API 19**：同一个改动在上游是清理，在我们是退化。
