### 2.3 协议要点（以 `docs/PROTOCOL.md` 为准；README §5 的 16 字节表是早期阶段产物，**已过时**——`AGENTS.md` §7 明言"不要退回 Autobox 协议（0x55AA55AA）"，代码 `hu/.../protocol/OemFrames.java` 实现的是 28 字节 OEM 协议）

- 帧结构：**28 字节头 + payload**：`type(4LE)` + `param0..4(20B)` + `payloadLen(4LE)`；type 取 `0xAA55AA5X`；接收校验 `(type >>> 8) == 0xAA55AA`。
- 类型表：`55` 控制/文本（双向）、`56` 麦克风、`57` **鉴权/防伪**、`58` 视频 H.264、`59` 音频（5 param 带格式）、`5A` **心跳**、`5B` 元数据 JSON、`5C` 封面、`5D` 二路/仪表视频、`5F` 服务状态 JSON。
- **心跳（最关键）**：车机端必须每 **1000ms** 发 `0xAA55AA5A` 空帧，否则盒子固件 **~10.8s 看门狗复位重枚举**（`docs/PROTOCOL.md` §2.1；`hu/.../session/OemSession.java:165` `scheduleWithFixedDelay(tick,1000,1000)`）。
- 握手：连上发配置突发（`get_sw_ver` / `carplay_report_resolution`+宽高 / `set_video_fps` / `set_right_hand_driver` / `set_night_mode` / `start_work`×2 …，完整命令清单见 `docs/PROTOCOL.md` §3）；触控 = `carplay_report_hid` + int16(x,y,action)，**坐标 0–10000**（README）。
- 鉴权链：`0xAA55AA57` 帧 → `com.u.j.U.p()`（`apk_orig/libu.so` 黑盒，native）→ 回调 `com.juyou.p.P.s()` 发应答；必要时 `P.m(challenge)` 走 `U.a()` 签名 + HTTP `http://aufnplay.com/auth`（`AGENTS.md` §3、`docs/PROTOCOL.md` §5）。
- 实测关键坑：不能用 Autobox 协议（`0x55AA55AA`），此固件不认；libu.so 读包名/签名（原证书 `CN=krabs`），包名须 `com.hyphp.playkeytool`（`AGENTS.md` §2/§7）。
- 材料性质：**无抓包文件**（仓库无 pcap）；协议来自原 App 脱壳 dex（`apk_unpacked/dex/`，头损坏需 jadx 关校验）+ 运行实测（`proxy/grab_v3.py` 等）。

### 2.5 对"纯软件在 CS11 上实现同样效果"的启示与硬性限制

**可学到（方法/参照层）**
1. **可行性佐证**：同族车机端 App 实测 **minSdk 19**，且 CS11 实机上已安装 HY Link（同包名同证书，并被授予盒子 DeviceFilter）→ "视频解（MediaCodec）+ 音（AudioTrack）+ 触控回传 + SurfaceView"这套纯软件栈在 CS11 级别设备上没有系统级硬伤（05 档案已证 CS11 有 H.264 硬解器）。
2. **参数参照**：分辨率/fps 上报、左右舵、夜间模式、HID 坐标空间 0–10000、音频格式走 5×param —— 可作自研接收端在 CS11 上 bring-up 的"车机侧期望值"对照。
3. **工程手法**：透明字节管道 + 独立实验脚本（`proxy/grab_v3.py`）、固定周期心跳维持链路 —— 逆向与联调方法论可复用。
4. 老设备低分配习惯：固定缓冲复用、固定线程（`hu/.../OemSession.java`、`media/H264Decoder.java`）。

**硬性限制 / 不能学**
1. 仓库**不含** Apple 侧协议（AirPlay/iAP2/MFi 细节全在盒子固件闭源库：`libcarplay/libAirPlay/libiap2link`）→ 纯软件接收端**无法**从本库获得 CarPlay 实现材料；MFi 身份依旧走 04 §4（xcertplay 离线身份）。
2. 盒子路线自身依赖：盒子硬件 + `libu.so` 鉴权（CS11 **无 root**，LSPosed 钩签名不可行；实测"仅包名"就够，但 **CS11 上 `com.hyphp.playkeytool` 已被 HY Link 占用，同名安装冲突**，替换会顶掉原应用——待验证影响）+ 云端 `aufnplay.com` 依赖 + 每 1s 心跳义务。
3. USB 口角色限制：盒子/iPhone 都需要车机 USB 口是 **host**；CS11 上调试口开 USB 调试时被锁为 gadget，需用 USB2 口（`docs/05-CS11实机档案.md` §11/§12）。
4. 无线侧无参考价值：盒子自载 RTL8821CS + 自有 BT 栈；CS11 是 nFore 私有蓝牙栈，无线可行性仍是未决项（沿用 04/05 结论）。

### 3.2 不建议直接搬 / 必须替换或裁剪

1. A 库"只改 minSdk 到 26"的下探策略**不适用于 19**：Compose（官方最低 API 21）、Media3（21+）、androidx 版本下限、通知渠道等需要真正的依赖替换与条件化（以 07d 阻塞清单为准）——A 库恰好绕过了这一层。
2. `APP_PLATFORM=android-26` 的改法**不能照抄**到 19：新版 NDK 最低只到 API 21；到 19 需旧 NDK 或删 JNI（04 §3 已列）。
3. A 库的 LocalOnlyHotspot 家族及其 26/27 workaround（`HotspotReservationRetirement.kt`、`HotspotBssid.kt`、WifiP2p `channel.close` 门禁）在 API 19 **不可用/无意义**——整块裁掉；仅保留其"按 SDK 分派 + 防御性 close"思路。
4. `WifiP2pGroupManager.checkPrerequisites` 用了 API 21+ 的 5GHz/能力检查（A 库只加了 `@RequiresApi` 注解）；到 19 必须重写而非注解。
5. B 库的 libu.so / 包名伪装 / 云端鉴权链**不要**作为软件路线依赖（灰色地带，且与"纯软件、不依赖盒子"的目标无关）；仅当"盒子在手、要自研车机端"时才参考。

### 3.3 待验证清单（不得当结论使用）

1. CS11 / Android 4.4.3 上 USB bulk 与异步读的真实上限（16KB？或更小）——A 库数值来自 AOSP 行为，未在 4.4 实测。
2. 4.4 的 i.MX6 OMX 解码器对 `KEY_MAX_INPUT_SIZE` / configure 的容忍度，及 MediaCodec→SurfaceView 输出在 4.4 的实际行为。
3. 车机 HY Link（26091401）与仓库 APK（26082601）的协议差异。
4. CS11 上 `com.hyphp.playkeytool` 同名冲突的处理策略（替换/共存的影响）。
5. CS11 WiFi 频段/双频能力、nFore 蓝牙对无线方案的可行性（沿用 04/05 未决项）。
