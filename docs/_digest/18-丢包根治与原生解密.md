# R.10.53-18 丢包根治战：USB IRQ 迁移 + 原生解密 + 零丢包达成

> 日期：2026-10-06 深夜 ｜ 状态：**空闲态零丢包实录达成**；交互（滑动）态丢包降 2-3 倍且退化为单包级（miss=1）；音频回归原始流（用户要求，撤销全部补洞）。

## 1. 用户定性要求

> “既然是丢包导致的，那为什么不从根源上解决丢包？”
> “我期望的是 0 丢包，声音不做修补处理。”

→ 作战目标：**根因消除**（不再用 conceal 遮挡症状），音频恢复原始流。

## 2. 根因链（最终定论）

```
① USB 控制器 IRQ 被默认钉死在 CPU0（实测 IRQ 72: 2,846,638 次中断全在 CPU0，cpu1/2/3=0）
        ↓
② CPU0 最忙 → 中断处理/URB 补位延迟抖动 → 内核 NCM 接收迟滞
        ↓
③ 手机 NCM 发送队列溢出 → 丢包
        ↓
④ 交互时视频突发（3-4.4 Mbps H.264 洪峰）使 i.MX6 负载飙至 ~8（≈2 倍超载）
   —— 其中视频帧解密为纯 Java BouncyCastle ChaCha20，是最大单一耗电源 ——
        ↓
⑤ 内核网络处理被应用线程饿死（nice 反转：app 线程 URGENT(-19)/DISPLAY(-4) vs ksoftirqd(0)）
```

**证据链（60 秒精确账目，逐层）**：

| 层 | 计数 | 判定 |
|---|---|---|
| usb1 驱动 | rx_packets +23,636，rx_dropped/errors=0 | ✅ 驱动不丢 |
| IPv6 | InReceives +23,631，HdrErrors=0，Discards=0 | ✅ IP 层不丢 |
| UDP6 | **Udp6InErrors +217（唯一窟窿）** | ❌ 丢在内核投递或手机发送侧 |
| TCP6 侧 | RetransSegs ~3%（视频流同比例） | ❌ 双协议同损 → 链路级 ~1-3% |

**空闲 vs 滑动对照（决定性）**：

| 状态 | 内核 Udp6InErrors | 应用侧 |
|---|---|---|
| 空闲 | +2/+3/+2 每 60 秒 ≈ 0 | seqGaps=0 全零 |
| 滑动 | +261~405 / 90s（2.9-4.5/s） | 2-25 事件/5s，gapMax 至 21 包（≈168ms 整段崩塌） |

## 3. 修复作战（按落地顺序）

| # | 动作 | 效果 |
|---|------|------|
| 1 | **USB IRQ 亲和性迁移** CPU0 → CPU1+（`echo e > /proc/irq/{72,75}/smp_affinity`，实测中断全部迁移到 CPU1） | 丢包 10/s → ~1/s（**10 倍**） |
| 2 | 撤销音频 conceal v1/v2（补静音/PLC-lite 重复波形） | 音频回归原始流；“滋啦”随丢包减少自然消退 |
| 3 | 视频/BufferedAudio TCP 接收窗口 64KiB 上限（`ScreenStream`/`BufferedAudioStream`） | 发送端节拍化（低 RTT 下窗口非瓶颈，作保险） |
| 4 | **视频帧解密换 Conscrypt 原生（BoringSSL）ChaCha20-Poly1305**（`AirPlayCrypto` 原生优先 + BC 兜底） | 滑动期丢包 4.5/s → **2.0/s（-55%）**，同条件注入对照 |
| 5 | RPS 全导 CPU1（`rps_cpus=2`）+ ksoftirqd 提权 -5 + app 钉核 CPU0/2/3（`taskset 0xd`，CPU1 专供 USB IRQ+软中断） | 结构性消除优先级反转 |
| 6 | 内核旋钮：`netdev_max_backlog=4000`、`rmem_max=2MB`、`rmem_default=512KB` | 缓冲保险 |

**复合效果**：丢包模式从「9-21 包整段崩塌」退化为「单包级 miss=1」；空闲态实测 60s×3 窗口全零；重交互期 ~0.5-2/s 且为单包。

## 4. 关键实现（代码）

- `Cs11NetdevBootstrap.kt`：网卡拉起脚本内自动迁移 USB IRQ（每次引导自动应用）。
- `AirPlayCrypto.kt`：`chachaSeal/chachaOpen` 原生优先路径 ——
  - `org.conscrypt.Conscrypt.newProvider()` 已激活日志：`AirPlayCrypto: native ChaCha20-Poly1305 active`；
  - 与 BC 字节级兼容（同为 RFC 7539 combined 格式：ciphertext‖16B tag、12B nonce、AAD）；
  - `AEADBadTagException` 原样上抛（不触发回退重试），仅初始化级错误回落 BC。
- `tools/cs11_tune.sh`：重启后一键重放全部调优（IRQ/RPS/renice/taskset/内核旋钮）——**全部为内存态，重启丢失**。
- 提交 `dd79bcd`（8 文件）。

## 7. 附：为什么 CarPlay 盒子"没有这个问题"（架构对照）

依据 `_upstream/cs11-carplay-dongle`（盒子路线开源工程）实勘：盒子 = 独立 Linux SoC（USB gadget `0525:A4A*`），**CarPlay 全栈（iAP2/AirPlay/解密/网络/缓冲）全部跑在盒子里**；盒子用 **USB 可靠传输**把"已煮熟的" H.264 + PCM 喂给车机；车机 APK（`cn.carplay.hu`）只做**解码 + 显示 + 回传触控**。

| 维度 | 盒子方案 | 自研直连（我们） |
|---|---|---|
| 协议栈运行在 | 盒子的专用 SoC | **i.MX6 自己** |
| 到车机的传输 | **USB（可靠传输，物理层重传，结构上无丢包）** | NCM 网络（UDP/IP，丢包是协议特性） |
| 流解密 | 盒子消化 | 车机 CPU 全帧 ChaCha20 |
| 音频 | 盒子输出 PCM（盒内缓冲节拍化） | 有线=LPCM 实时裸流 |
| 车机 CPU 负荷 | 轻（解码+显示+触控） | 重（全栈） |
| 延迟/画质档位 | 通常更保守（透传+缓冲，百毫秒级延迟） | 更低延迟（触控 28–84ms）、画质可调 |

**结论**：盒子的"不卡不丢"本质是**把难题外包给一台专用小电脑 + 用可靠传输送达**；我们的丢包/性能问题在盒子架构里**结构上不存在**。而我们在平板 bench（性能充足）上零丢包零问题，证明**软件栈本身完全健康**——CS11 的挣扎纯粹是"把盒子那台小电脑的活全塞进 2013 年 i.MX6"的物理约束。自研路线的收益（无硬件、低延迟、全链可审计、用户明确不要盒子/改造版）正是拿这份性能账换的。

## 8. 软件优化空间清单（回答"能否从软件层面继续优化"）

现状基线：空闲 0 丢包；交互期残余 ~0.5–2/s 单包级。剩余空间与手段：

### A. 零成本（设置旋钮，下次上车即可 A/B）
| 旋钮 | 可选值 | 预期 | 代价 |
|---|---|---|---|
| **帧率** | **30–60（步进 5）** | **最大杠杆**：30fps 直接砍 ~40% 解码/渲染/位速负载 → 突发超载与交互丢包同步下降 | 流畅度下降（30fps 即无线 CarPlay 标准档） |
| 音乐缓冲 | 300（默认）/ 500 / **1000（更稳定）** | 掩蔽"到达抖动"类顿挫（readMaxMs 尖峰），对真丢包无效 | 音频延迟 +0.2–0.7s |
| 分辨率 | 100% 起可调低 | 像素量降 → 解码负荷降 | 清晰度损失（次优先） |

### B. 中等成本（PC 端代码，做完上车验证）
1. **视频管线零拷贝/缓冲池**：现状每帧多次 JVM 分配（网络读→copyOf→解密→再拷贝进 MediaCodec）≈1MB/s 分配量 → Dalvik GC 抖动正是 `processMaxUs 65–75ms` 尖峰的候选来源；改=复用缓冲池 + 解密直入复用区 + 少一次 copy。
2. **音频路径同法**（每包 copyOf；量小、顺手做）。
3. **渲染路径评估**：TextureView 在 GC2000 上的 GPU 合成成本 → SurfaceView/IPU overlay 可省 GPU（工程量大，留后手）。
4. **视频接收流水线**：读/解密/投喂两级队列已有；可再加"只投最新帧"（低延迟优先）微调。

### C. 不建议/不可行
- HEVC（无 VPU 硬解）、继续 native 化（收益递减）。

### D. 预期管理（诚实）
- 空闲=0 已达成；交互期残留在"手机发送侧 + USB/NCM 突发调度"边界，软件优化目标是把 ~0.5–2/s 压向 ~0.2–0.5/s——**在这颗 2013 SoC 上不保证归零**。
- **首推动作：帧率 30 + 音乐缓冲 500ms 跑一轮交互对照**（一个设置开关就能 A/B），不够再做 §B 的缓冲池改造。

## 9. 架构层评估：CarPlay 官方架构 vs CS11 残余空间

### 9.1 CarPlay 官方（Apple）推荐的架构形态
- **官方路径 = 车机本体原生化（native integration）**：车机 SoC 自身实现 CarPlay 全栈（iAP2/认证/音视频接收/AirPlay 播放），走 MFi 认证；有线=USB 直连；无线=BT 配对握手 + **车机提供 WiFi AP（5GHz 推荐）** + AirPlay over WiFi。
- **Apple 的隐含性能假设**：车机 SoC 能实时 720p/1080p H.264/HEVC 解码 + 触控低延迟 + 音频连续——现代车机 SoC（高通 8155 级）轻松满足。**Apple 的架构从未假设"老 SoC 扛全栈"**。
- **盒子（dongle）不是官方架构**：它是"假车机"中介——盒子当车的替身跑全栈，车机降为轻终端（解码+显示+触控），USB 可靠传输送达。我们此前实勘 `cs11-carplay-dongle` 即此形态。

### 9.2 CS11 的架构残余空间（分层评估）
| # | 手段 | 层级 | 收益/成本 | 判定 |
|---|------|------|-----------|------|
| a | **显示路径 offload 到 IPU overlay**（SurfaceView 族路线，视频显示绕开 GPU 合成） | 架构级 | 解放 GC2000；工程中上 | 候选（§B3） |
| b | **无线化的音频红利**：无线形态下音频自动切 AAC+buffer（§已证），**CS11 无线体验在音频稳定性上可能优于有线 LPCM** | 架构级 | 免费（协议决定）；但需 4.4 适配+WiFi 实测 | 注记：无线化的意外收益 |
| c | **线程级拓扑微调**：video/audio/网络三路各钉专核（TID 级 taskset via rootd） | 调度级 | 小-中；低成本 | 可试 |
| d | **应用层 NCM（usbfs 直读绕内核栈）** | 传输级 | 已分析：省下的内核算力会被 Java/Dalvik 解析吃掉，不划算 | **否决（有记录）** |
| e | **软件盒子（自托管接收器）**：CarPlay 栈放另一台设备（平板/RPi 级），CS11 降为终端；与盒子同形但代码自研可审计 | 架构级 | 彻底解决算力（平板 bench 即证明）；代价=额外硬件，违反"不用盒子"约束 | 备选逃生门 |

### 9.3 诚实结论
CS11 的优化已进入**边际收益递减区**：官方形态本就要求现代车机 SoC，i.MX6（2013）是被塞进远超其年代的协议要求。当前状态（空闲 0 丢包 / 交互单包级）≈ 这块 SoC 的实际天花板；后续要么吃 §A/§B/§9.2a/c 的余量，要么走向 §9.2e 的架构逃生门。

## 10. 为什么 IRQ 必须"手动"迁移：Linux 调度分层问答

**Q：i.MX6 四核，正常情况不该动态调节吗？USB 真的被默认钉死在 CPU0？**

**A：都对——"动态"存在于部分层，唯独中断亲和这一层默认是静态的，且无人来救。**

| 层 | 机制 | 默认行为 | 我们的处理 |
|---|---|---|---|
| 任务（线程）调度 | CFS 负载均衡 | **动态 ✓**（线程自动迁移到空闲核） | 主动 `taskset 0xd` **收窄**（防漂移抢走 CPU1 的中断预算） |
| 频率 | DVFS/cpufreq | **动态 ✓**（@996MHz 档位） | 未动 |
| **硬中断亲和** | IRQ affinity | **静态：默认 CPU0 ✗** | 手动 `smp_affinity=e` → CPU1+2+3（刻意排除 CPU0） |
| 网络收包软中断 | NAPI/ksoftirqd | 老内核**跟 IRQ 所在核**跑；RPS 默认关闭 ✗ | `RPS=2`（收包软中断导 CPU1）+ ksoftirqd `renice -5` |

**为什么没人自动挪**：
1. 内核**从不自动迁移**非托管 IRQ（3.10 年代无 managed IRQ，那是 4.8+ 才有的多队列机制）；
2. 动态均衡 IRQ 是用户态守护 `irqbalance` 的活——**Android 从不部署它**（桌面/服务器发行版才有）；
3. 车厂 BSP 默认把 IRQ 亲和留成 `1`（只含 CPU0），此后无人改动。

**实测证据**：IRQ 72（2,846,638 次）/ IRQ 75（242,930 次）计数全在 CPU0 列（cpu1/2/3=0），默认真空掩码=CPU0。

**为什么钉 CPU0 在这颗芯片上最致命**：CPU0 是全系统"杂活核"（app 主线程、系统服务、最多其它中断都在这）。硬中断 + NAPI 全挤在已超载的核上 → URB 补位延迟 → NCM 接收迟滞 → 手机 TX 队列溢出 → 丢包。迁移后实测 **10×**，验证了归因链。

**为什么我们反而选择"静态分区"而不是等动态**：irqbalance 类动态均衡的粒度是秒级、且不理解实时性需求（它会平等看待"读 UART"和"收 8Mbps 视频"）；而我们的负载是持续、可预测的流式管线——**给数据路径划专用核（IRQ 核/应用核分区）是实时系统的标准做法**，"可控的静态"优于"抖动的动态"。

**边界说明**：仅实测了 USB 的 IRQ 72/75；其余 IRQ（定时器按核本就有、GPU/SDMA 等）未全查。IRQ 亲和为内存态，重启丢失——由网卡引导脚本自动重放。
