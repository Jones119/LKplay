# 35 · CS11 导航音量通道的真相（2026-10-08 车上实测）

## 现象
CarPlay 里导航播报时调方向盘音量，**车机显示"媒体音量"**而不是"导航音量"（用户的盒子经验：这类车机要**为每个功能指定通道**）。

## 关键证据（车机日志，一次按键的完整链路）

```
XCInputService(1447): >>>in: key 200024 doAdjust 1, ECarXRVolumeUpAction     ← 厂商键码 → 音量+
AudioManager(1447): adjustVolume direction:1 … activeStreamType:3
MediaFocusControl(471): getCurMasterStream curStream = 3                     ← 车机判定的"当前主音量流"= 3
AudioService(471): adjustSuggestedStreamVolume streamType: 3
```

**结论**：车机方向盘音量键调的是 **`getCurMasterStream`（当前主音量流）**，而它由 **`MediaFocusControl`
（谁持有音频焦点）** 决定 ⇒ 那一刻是 **3（STREAM_MUSIC）**，因为**只有媒体渲染器请求了焦点** ✗。

我们此前的状态：导航提示**确实走在流 12** ✓（`audio track prepared type=101 … route=streamType=12` ✓、无"被 ROM 拒绝"回退 ✓），
但导航渲染器**从不请求焦点**（代码里 `requestFocus` 对 `NAVIGATION` 是显式 `return` ✗，且 app 的"音频焦点"开关默认
**关闭** ✗，日志 `focus=off` ✓）⇒ 车机始终认为主音量流是媒体 ✗ ⇒ 显示"媒体音量" ✓ 完全自洽。

## 附：HYLink（车机自带投屏应用）源码里的原话
```
AudioPlayer.java: "导航声道使用 legacy stream=3(STREAM_MUSIC)，将与媒体共用音量；部分车机的独立导航流为私有 stream=12/13"
AudioSessionController.java: private int desiredStream = 3;
```
⇒ 连车机自家的 HYLink 都退回了 `STREAM_MUSIC` ✗，并把 12/13 称为"**部分车机的私有导航流**" ✓ —— 与我们的判断一致：
12/13 是**存在但需要正确"进入方式"**的私有流 ✓，而"进入方式"就是**持有焦点** ✓。

## 修复（本轮实现）
1. `DEFAULT_NAVIGATION_STREAM_TYPE = 12`（vendor `STREAM_NAVI_TTS`）+ 通道映射默认开启（`b7f50f8`）✓；
2. **导航提示在"真正播放"期间请求 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`，并让遗留焦点请求带上流 12**
   （`requestAudioFocus(listener, streamType, gain)`）⇒ 播报期间车机的 `getCurMasterStream` 应变为 12 ✓，
   播报结束立即交还媒体 ✓（不长期霸占音量键 ✓）；
3. 焦点协调器里**导航优先**（仅在它活跃时 ✓），并按 `Entry.streamType` 发起遗留请求 ✓；
4. app 的"音频焦点"设置**默认改为开启** ✓（否则整条机制不生效 ✗）。

## 验收（上车）
- 播报时按音量键 ⇒ 车机音量条应显示**"导航"**；播报结束后按 ⇒ 回到**"媒体"** ✓；
- 日志应出现 `Audio: focus requested channel=NAVIGATION gain=… streamType=12`（新增诊断）✓
- 若仍显示媒体 ⇒ 说明车机不是按焦点、而是按**它自家的"功能"状态**决定 ✗，那就只能
  在 DiPlay 里放"呼出导航音量"之类的替代交互（或接受与媒体共用音量）。
