# 41 · CarPlay 代码层优化清单（编解码 / 触摸 / 日志 / GC / 渲染）

> 目标：回答「我们自己的代码还能怎么优化，比如更高效的编解码」。
> 方法：只读源码 + 复用本轮实机证据（doc 40）与历史真机日志（`_analysis/applogs/*.log`）。**未改任何代码。**
> 结论先说：数据面已经没有"算法级"的坑（视频已是硬件解码、ChaCha20 已走 native、AudioTrack 缓冲充足），
> 剩下的钱集中在三处：**① 解码器的选择与参数、② 每帧/每事件的分配与日志、③ 渲染路径**。

## 1. 先确认"现在到底在用什么编解码"

| 项 | 有线（历史日志 `_analysis/applogs/*.log`） | 无线（本轮实测，doc 40） |
|---|---|---|
| 视频解码器 | `OMX.Freescale.std.video_decoder.avc.v3.hw-based`（**硬件** ✓） | 同左（同一 ROM 同一 MIME） |
| 视频画布 | `1280x650` / `1280x594`（协商 canvas，输出=canvas） | 同左 |
| 音频 | **`codec=LPCM`**，`outputBuffersTotal=0`（**完全没有解码器**） | **`codec=AAC_LC`** + `OMX.google.aac.decoder`（**软件**） |
| 音频写阻塞 | `maxWriteMs=0~14ms` | `maxWriteMs=249~255ms`（每窗口） |
| 音频线程占用 | — | `carplay-audio` 11.7% + `gle.aac.decoder` 6.5% + 音频 `MediaCodec_loop` 4.6% + `airplay-audio-rx` 2.8% ≈ **25% 单核** |

**两条硬事实（决定了优化方向）：**
1. **HEVC 在 CS11 上不要碰**：i.MX6 的 VPU 只支持 H.264/MPEG-4/VC-1 一类，
   `MediaCodecSupport.hevcCodecSpecificData`（MediaCodecSupport.kt:31）这条路在本机只会落到**软解**——
   `softwareDecoderName()`（AndroidMediaSink.kt:696-699）在 `SDK_INT < Q` 直接返回 null，
   而 `tryConfigure` 的兜底会一路枚举到 `OMX.google.*`。→ 建议 CS11 上直接禁掉 HEVC 协商（或按 §2.4 明确上报）。
2. **PCM vs AAC：当前广告下是 AAC；「能不能换 PCM」是*未验证*项，不是已证伪项**：
   `AirPlayInfoPlist.audioFormats`（:121-159）里 `type=100 media` 报的是 PCM（:150），
   而 `type=102 media`**只报 AAC-LC**（:154）。实测（2026-10-07/08 CS11 无线日志，数百条）
   音乐流**全部**是 `type=102 audioType=media codec=AAC_LC formatBits=0x800000`，
   `type=100` 只用于 speechRecognition/alert/telephony 且都是 OPUS。
   ⚠️ 那条「iOS 27 只肯用 AAC-LC 打开它，PCM/ALAC 都不开」的注释挂在 **103（buffered）** 上
   （`BufferedAudioStream.STREAM_TYPE=103`，默认关），**不能推广到 102**；102 从未广告过 PCM。
   有线会话实测音乐是 **LPCM（零解码）**，但老日志未记录流类型，只能证明「我们的 PCM 播放路径是通的」。
   → 因此「给 **102** 加 PCM / 干脆不广告 102」是一个**未验证**的低成本实验（一行广告 + 上车 20 分钟，
   看日志 `airplay audio format type=… codec=…` 即可判定）：成功则省 ~11 点单核（代价 +1.5 Mbps），
   失败（iOS 坚持 102/AAC 或不推流）则回到「让 AAC 解码更便宜」的路线。
   **先验概率：低**（2026-10-08 追加核查）——无线会话里 `airplay audio format` 全量统计为
   `type=102 media AAC_LC` 248 次、`type=100/101 speech/telephony/alert/default OPUS` 272 次、**LPCM 0 次**；
   而 `codec=LPCM` 只出现在有线期日志（`_analysis/applogs/diplay*.log`，含 `netdev usb1 ready`）。
   两个反证：① `type=100 "media"` 只广告 PCM（:150），iOS **从不选它**，宁愿用只广告 AAC 的 102；
   ② `speechRecognition/telephony/alert` 广告 `pcmMono or opus`，iOS **全选 Opus**（该项受上行麦克风需求干扰）。
   → 结论：**LPCM 在这套实现里事实上是"有线专用"**，不是协议限制而是 Apple 的空口权衡
   （音乐 AAC ~256 kbps vs LPCM 1.536 Mbps）。另需注意：即便换到 LPCM，+1.5 Mbps 会在 2.4 GHz 空口上
   与视频突发争时间，可能把视频 `maxGap` 拉大——净收益未必是 11 点。

## 2. 编解码可改的 6 条（按收益/风险排序）

### 2.1 音频解码器优先 vendor（**收益最高、风险低——但先要确认本机到底有没有第二个候选**）
音频路径只有一句 `MediaCodec.createDecoderByType(mime)`（AndroidMediaSink.kt:1088-1101），
**没有**视频那样的枚举/回退链（对比 AndroidMediaSink.kt:597-609、:640-654）。
做法：把视频那套 `enumeratedCodecNames(mime)`（:641-654）抽出来复用 + 在音频侧按同样顺序尝试，
并记录实际选中的 name（`audio decoder configured … name=`，:1098 已有日志口）。

**⚠️ 前提核实（2026-10-08，用真机日志与属性反查，未上机）——本机大概率"没有 AAC 硬解"：**

| 证据 | 结论 |
|---|---|
| `_artifacts/cs11_port/{vendor-bt-api-test,carplay-1080p-stats,carplay-mic-test,a2dp-watchdog-test}.log` 四份会话全部是 `audio decoder configured mime=audio/mp4a-latm name=OMX.google.aac.decoder` | `createDecoderByType` 解析到的就是 **Google 软解**，从未变过 |
| `_artifacts/cs11_getprop.txt:169-176`：`ro.FSL_AAC_PARSER=1`（另有 ASF/AVI/FLAC/FLV/MKV/MPG2 解析器） | FSL 件是**解析器（拆帧）**，不是解码器 |
| 日志里 OMXMaster 注册到的 Freescale 组件只有 `…parser.fsl.sw-based`、`…parser.streaming.sw-based` 与 `…video_decoder.avc.v3.hw-based` | 没见过任何 `OMX.*.audio_decoder` |
| 全工作区 grep `audio_decoder\|libfslaacp\|aac_dec\|AACDecoder\|lib_aacd` → **零命中** | 没有厂商 AAC 解码器的任何痕迹 |
| i.MX6 的多媒体硬件只有 VPU（视频/JPEG）、IPU（图像 CSC/缩放）、GPU（GC2000）；音频侧只有 SSI/ESAI/SPDIF/ASRC（接口与重采样） | **SoC 层面就没有音频编解码单元**，"AAC 硬解"在这颗芯片上不存在 |

→ **改法要分叉**：
- 若上车枚举**存在**厂商 AAC（需一次 `MediaCodecList` 实测，约 10 分钟）：按 §2.1 原方案切过去，
  同时删掉 `KEY_IS_ADTS=1`（:1073）改喂裸 AU（:1305,:1315 的 ADTS 重封装一并去掉）。
- 若枚举**为空**（按上表，这是大概率）：唯一能把音频从 ~11 点单核打到个位数的办法是
  **绕开 MediaCodec 层，JNI 直连一个更快的 AAC 软解**（如 FDK-AAC），照项目既有先例
  `LegacyNativeOpus.kt:15-118` + `libdiplay_opus.so` 的模式替换 `feedCodec/drainCodec`
  （AndroidMediaSink.kt:1065-1107、:1341-1454）。收益同时来自两处：软解本体更快 +
  干掉 ACodec 层「每包 4 次 JNI 往返 + API19 每包 2 次缓冲数组获取 + 每帧 direct buffer 往返」。
  风险：新增 native 依赖（BSD 许可可控）、需实机验证。
- 与它正交、且**无论有没有厂商解码器都该做**的两条：把阻塞写从解码线程剥离（§2.1b）、
  ADTS 去掉（省 3 分配/3 拷贝/包）。

**§2.1b 把阻塞写从解码线程剥离（-3~5 点，低风险）**：`carplay-audio` 线程同时干"解码循环 + 写
AudioTrack"（AndroidMediaSink.kt:1028-1039、:1456-1510），实测 `maxWriteMs` **恒定 249~255ms**
（代码里没有这个常量，是真实阻塞：500ms track 满后等平台抽走一步）。这 250ms 内不喂解码器、
不取输出，`queue` 因此在 0~15 包间摆动。加一个写线程 + 有界 PCM 交接即可消除该停摆，
并顺带把 PCM 缓冲缩到一个抽水周期（输出延迟降 300~500ms）。
附带安全项：`AndroidMediaSink.kt:1175-1176` 在 API<23 用**请求容量**冒充实际容量，
与「达到阈值才 `play()`」（:1502-1508）组合，若 ROM 实给缓冲偏小会**永久阻塞在 write**（同线程、无超时）；
修法：4.4 上先 `play()` 再写，或给预缓冲加硬上限/看门狗。

### 2.1c 若要走 JNI 软解，选哪个开源 AAC 解码器？（**许可证在这里是决定性的**）

本项目 `CarPlay-CS11/LICENSE` = **GPL-3.0**（README 亦声明基于 xcertplay GPL-3.0），这直接把候选砍掉一半：

| 候选 | 速度/质量（公开对比的普遍结论） | 许可证 | 对本项目 |
|---|---|---|---|
| **FDK-AAC**（Fraunhofer） | **LC 下通常最快、质量最好**，公认嵌入式首选；有 ARM/NEON 优化 | FDK AAC License（BSD 风格，但含附加限制） | ✗ **与 GPLv2/v3 不兼容**——FFmpeg 自己的许可证文档就写着「Fraunhofer FDK AAC … incompatible with the GPLv2 and v3」（`DiAuto/app/src/main/cpp/ffmpeg/FFMPEG_LICENSE.md:127-129`） |
| **FFmpeg libavcodec 的 AAC** | 与 FDK 接近（LC 下差距通常在 ~10–30%），NEON 优化齐全 | **LGPL-2.1+** → 与 GPL-3.0 兼容 ✓ | ✓ **首选**：DiAuto 已 vendored FFmpeg 7.1.1（LGPL 声明 + `ffmpeg_hevc_decoder.cpp` 是现成 JNI 范式），但只编了 **arm64-v8a**，CS11 需按它 README 的 configure 形状**重编 armeabi-v7a**（注意 32 位 Android 用 **softfp**：`-mfloat-abi=softfp -mfpu=neon`，i.MX6Q 有 NEON） |
| **Helix AAC**（RealNetworks） | 体量最小（~50–100 KB），手写 ARM 汇编，ARMv7 时代很强 | RPSL/RCSL（BSD 风格 + 专利条款） | ⚠️ 需法务判断；备选 |
| **FAAD2** | 明显慢于上两者 | **GPL-2.0-only** | ✗ 与 GPL-3.0 不兼容（GPLv2-only 与 GPLv3 不能合并） |
| AOSP `OMX.google.aac.decoder`（OpenCORE/PacketVideo） | 就是现在跑的基准线 | Apache-2.0 | 现状，无许可问题 |

> **若只自用、不发布 APK（用户已确认）**：GPL 的义务只在**分发**时触发，上面的许可证筛选全部失效，
> 于是只剩「性能 / 集成成本 / 质量」三项，**FDK-AAC 升为第一选择**（最快 + 质量最好 + decoder-only
> 编出来 ~200–300 KB/ABI），FFmpeg 退为第二（已有现成构建与 JNI 范式），Helix 第三（最小），
> FAAD2 仍淘汰（慢，与许可无关）。若将来要公开发布，FDK 的附加条款（nuclear 限制）与 GPL-3.0
> 的冲突会重新出现——届时应换回 FFmpeg（LGPL）。注意本项目还有比许可更硬的既有问题
> （APK 内含提取自 Carlinkit 固件的 Apple MFi 私钥），文档已如实披露。

**但要先认清杠杆大小**（实测口径见 doc 40）：| 杠杆 | 省多少（单核） | 代价 |
|---|---|---|
| **① 让 iOS 别发 AAC（改回 LPCM）** | 理论上 **≈11 点**，但**期望值低**（见上「先验概率：低」的反证） | +~1.5 Mbps，且会与视频抢 2.4 GHz 空口时间；入口是「给 type 102 加 PCM / 不广告 102」（102 目前只广告 AAC-LC，`:154`）——顺手花 20 分钟验证即可，**不要押注** |
| **② 绕开 MediaCodec，JNI 直连** | ≈4.6 点（ACodec 每包 4 次 JNI 往返 + 2 次缓冲数组获取 + 每帧 direct buffer 往返） | 新增 native 依赖 |
| **③ 换更快的解码库** | ≈2–3 点 | 上表的许可证约束 |
| **④ 把阻塞写从解码线程剥离** | ≈3–5 点（正交，不依赖上面三条） | 低 |

→ **顺序建议（2026-10-08 按新证据修正）：主线 =「④ 剥离阻塞写」→「②+③ JNI 直连 FDK/FFmpeg」；
「上车枚举解码器（10 分钟）」保留为决定②③做法的探针；① 降为顺手验证、不押注。**
若②③都要做，选 **FFmpeg（LGPL）**而不是 FDK（GPL 冲突）；实测方法是同一段 60s AAC-LC 48k/2ch，
各候选各跑一遍，比 `% of one core` 与实时倍率（当前 AOSP 软解 ≈6.5% 单核 ≈65 MHz ≈ 15× 实时）。

### 2.2 PTS 语义修正（**直接改善"卡顿观感"**）
`feed()` 用"入解码器的时刻"当 PTS（AndroidMediaSink.kt:776 `System.nanoTime()/1000`），
`drainOutput()` 用 `now - pts` 判断 250ms 老化（:814-817, 常量 :887）。
⇒ **在 `VideoDecodeQueue` 里排队 900ms 的帧，出队后 age≈0，会被当"新鲜帧"立刻上屏**（画面滞后但不丢）。
改法：`feed(job: VideoJob.Frame)` 把 `job.receivedNs`（VideoDecodeQueue.kt:10）带进来当 PTS，
让既有 250ms 规则真正度量"相机→送显"年龄——卡顿时会**只显示最新帧**而不是补播旧帧。

### 2.3 给 vendor OMX 补解码器参数（低风险）
`buildFormat`（AndroidMediaSink.kt:656-663）目前只设 `KEY_MAX_INPUT_SIZE` + `KEY_PRIORITY=0` + csd。
可补字符串键：`operating-rate`（目标帧率）、`frame-rate`、`priority`——4.4 的 vendor OMX 是从 format 读这些键的
（ExoPlayer 在 API<23 也走字符串键）。作用是让解码器按目标帧率进入高性能档而不是省电档。
失败会落回 `tuned=false` 的 attempt（:599），无回归风险。

### 2.4 软件解码器必须被当"失败"上报（避免静默退化）
兜底枚举（:600-604）可能选到 `OMX.google.h264.decoder`，而目前只在 `report("decoder=<name>")`（:617）里记一行。
→ 若 name 命中 `OMX.google.` / `c2.android.`，应在 `DiPlay-VideoStats` 行里带 `decoder=sw` 并报一次告警。
否则"忽然特别卡"时无法一眼判断是不是掉进了软解（720p30 软解在 A9 上必然崩）。

### 2.5 AAC 路径省一次分配（小钱）
`MediaCodecSupport.adtsFrame`（:119-132）每帧 `header + accessUnit` 复制一次；
`aacAccessUnit`（:135-145）每包 `copyOfRange` 一次。→ 复用缓冲；若 vendor 组件接受裸 AAC（不要 ADTS），
还能省掉 ADTS 封装与解析（现在 `KEY_IS_ADTS=1`，AndroidMediaSink.kt:1073）。

### 2.6 协商画布护栏（保持不变）
`videoWidth/Height` 取的是**协商 canvas**（CarPlayHostActivity.kt:3596-3600 ← `airPlayConfig.main.*`），
即解码器输出 = canvas，放大由 GPU 做。**不要**把 canvas 抬到 1080p——
doc 27 已实测 1080p 时 `recoveries=1~2 / maxGap=1.8s / shownP50 33→50ms`（VPU 每帧多干 1.5× 活）。

## 3. 触摸上行（滑动时 `touchExecutor` 单核 27.5% 的那条）

| 位置 | 现状 | 改法 |
|---|---|---|
| `AirPlaySession.sendTouch` :337-339 | 每个手指状态 `contacts.map { it.copy(...) }` → 新列表+新对象 | 复用数组/就地改坐标 |

## 4. 日志（纯浪费，而且吃掉了调试窗口）

- `CarPlayController.debugLog`（:2400-2407）**无条件 `Log.i`**：UI 转发才受 `debug_logs_enabled` 控制，logcat 不受控。
- iAP2 逐帧 trace 走 `Iap2FrameFormatter.format`（Iap2FrameFormatter.kt:29-72）：
  **每条消息**做 TLV 解析 + 每个参数 `"%02x".format(...)`（每次分配一个 `Formatter`）+ 多行 `buildString`。
  实测 **37 行/秒**（`xcertplay-usb`），**30 秒写满 256KB 环形缓冲**——本轮两次采样窗口就是这样丢的。
- 触摸/事件的 `trace(...)` 同理（AirPlaySession.kt:322、:489、:515、:802、:948）。
→ 改法：所有调试向字符串**先判开关**；打开时用查表 hex（避免 `String.format`）；高频 trace 支持"每秒最多 N 条"。

## 5. GC / 每帧分配（"不够顺滑"的直接来源）

实测（doc 40 §1.3）：滑动时 GC **每 1.2–3s 一次**、每次 `WAIT_FOR_CONCURRENT_GC blocked 37–67ms`，
正好对应视频 `maxGap 122–151ms / shownP95 80–94ms`。每帧分配清单与改法：

| 位置 | 现状 | 改法 | 风险 |
|---|---|---|---|
| `ScreenStream.readFully` :129-139 | 每帧 `ByteArray(128)`（头）+ `ByteArray(N)`（体） | 头缓冲复用；帧缓冲池（读入→解码器→归还） | 低 |
| `AirPlayCrypto.nativeAead` :62 | `doFinal` 每次返回**新** `ByteArray(N-16)` | `doFinal(ByteBuffer, ByteBuffer)` 写进复用 direct buffer（每线程独占） | 中 |
| `VideoDecodeQueue.offer` :35-36 | **每帧** `filterIsInstance` + `sumOf` → 一个 ArrayList，且持锁 | `AtomicInteger/AtomicLong` 计数 | 低 |
| `VideoDecodeQueue.pendingFrames` :51 | 每帧 `count{}`（被 AndroidMediaSink.kt:521 每帧调用） | 直接返回计数器 | 低 |
| `drainOutput` :804 | 每帧 `MediaCodec.BufferInfo()` | 提为字段 | 低 |
| `MediaCodecSupport.adtsFrame` :131 | 每 AAC 帧一次数组拼接 | 复用缓冲 | 低 |

**验收工具**：`android.os.Debug.startAllocCounting()`（API 19 可用）+
`getGlobalAllocSize() / getGlobalAllocCount() / getGlobalGcInvocationCount()`，
把「分配 KB/s + GC 次数/总耗时」打进 `DiPlay-VideoStats` 行——这样"GC 抖动"从"猜"变成"可量测、可回归"的指标。

## 6. 渲染（收益最大，风险也最大）

- 现在是 `TextureView` + `isOpaque=false`（CarPlayHostActivity.kt:986-996），全屏 1920×1080。
  每帧 HWUI 要写一整张 1920×1080×4 ≈ **8.3MB** 的窗口缓冲，再混合读 + SF 合成读；
  且 4.4 没有 RenderThread，GL 提交在 UI 线程——这就是滑动时 **main 20.7% 单核**的主因。
- 改 `SurfaceView` / IPU overlay 可省掉那 8.3MB/帧并把 UI 线程解放出来；
  但**必须保留回退开关**：本机 vendor 解码器在 Surface 重建时会掉进 client-side buffer 黑屏（doc 36）。
- 零风险的小赢：先把 `isOpaque` 改回 `true`（少一次混合读）。

## 7. 建议落地顺序（每一步都能单独 A/B）

1. **日志门控**（零风险，立刻回收 CPU + 恢复 30 秒的调试窗口）
2. **GC 表里的 3 个低风险项**：队列原子计数、`BufferInfo` 提字段、`readFully` 头缓冲复用
3. **音频 vendor 解码器枚举**（收益最高：~6.5% 单核）
4. **PTS 语义修正**（最直接改善卡顿观感）
5. **解码器 `operating-rate`/`frame-rate` 参数** + 软解告警（低风险）
6. **触摸上行去分配 + 写线程分离**
7. **TextureView → SurfaceView / overlay**（最大收益、带回退）

## 9. 对标：EasyPlay 与 HYLink 各自用的是什么方式（2026-10-08 反编译核查）

> 证据：`_analysis/easyplay/src/sources/**`（EasyPlay = `com.shilab.diplay.legacy`，DiPlay 的领克适配 fork）、
> `_analysis/hylink_src/UP_*/sources/**`（HYLink = `com.hyphp.playkeytool`，app_name「HY Link」）、
> `_upstream/cs11-carplay-dongle/{README.md,docs/PROTOCOL.md,AGENTS.md}`、`_artifacts/cs11_packages.txt`。

**先纠正一个身份问题**：HYLink **不是**车机自带的 CarPlay 宿主，而是 **CarPlay USB 盒子（dongle）的配套 App**：
盒子是 USB Device（gadget `VID_0525&PID_A4A9`，吉利/ECARX 定制固件、juyou/hyphp 方案），`PROTOCOL.md` 明确写
「参考 App：`com.hyphp.playkeytool`」；`README.md` 的拓扑也写着「手机：连 127.0.0.1:17321，**解码 H.264、播 PCM**、回传触控」。
HYLink 的 Java 里 `dongle` 出现 3076 次。它确实装在 CS11 上（`/data/app/com.hyphp.playkeytool-1.apk`）。

| 维度 | **EasyPlay** | **HYLink（盒子 App）** | **我们（CarPlay-CS11）** |
|---|---|---|---|
| 类别 | 纯软件 CarPlay 接收端（与我们同源） | CarPlay 盒子配套 App | 纯软件 CarPlay 接收端 |
| 协议栈位置 | 自己实现（AirPlay + iAP2 + MFi 全在 App 内） | **在盒子里**；App 只做 USB 通信 + 解码 + 显示 + 触控回传 | 自己实现 |
| 视频解码 | MediaCodec 硬解（`LegacyVideoDecoder`、`LegacyCodecFactory` 枚举解码器名） | 自己的 `H264Decoder`：`createDecoderByType/createByCodecName`，**3 次 configure 回退**（csd+指定名 → 只 csd → 裸），`setParameters` 里 **`operating-rate = 流帧率+15`** + QTI vendor 键 + 标准 `low-latency`，并打印用的是「vendor键/标准键」 | MediaCodec 硬解，**只设** `MAX_INPUT_SIZE` + `KEY_PRIORITY` |
| 视频渲染 | `LegacyActivity`（TextureView 系）+ **`VideoFramePool` 帧池** | `DualSurfaceRenderer`（主屏 + 仪表**双 Surface**） | TextureView 单面（+ 仪表另开解码器） |
| 音频格式广告 | **与我们逐条一致**：100 media=PCM、100 default/alert=PCM\|OPUS、telephony/speech=PCMmono\|OPUS、**102 media=AAC-LC(0x800000)**（`AirPlayInfoPlist.java:150`） | App 内不做 AirPlay 广告（盒子决定） | 同左 |
| AAC 解码 | **MediaCodec + `is-adts=1` + 每包 `adtsFrame()`**（`LegacyAudioRenderer.java:221/229/499`）——**和我们一模一样** | **不解 AAC**：`AudioPlayer` 只吃 **PCM** → AudioTrack（盒子输出 PCM） | MediaCodec + ADTS（现为 `OMX.google.aac.decoder` 软解） |
| Opus | 自带 native `libdiplay_opus.so` + **Concentus 纯 Java 兜底**（`LegacySoftwareOpusDecoder`） | — | 自带 `libdiplay_opus.so`（从 EasyPlay 借来） |
| 加解密 | **native 原地解密**：`libdiplay_crypto.so` 的 `openIntoNative` → **视频直接解进帧池缓冲**（`ScreenStream.java:311` `opener.openInto(body,…,frame.getBytes())`）、**音频在收包缓冲里就地解**（`AudioStream.java:297`，带 offset 参数） | 在盒子里 | Java Conscrypt `doFinal`，**每帧/每包新数组** |
| 音频监控 | — | **低延迟 AudioTrack（performance mode）+ `getUnderrunCount()` + PCM 帧对齐校验 + 每 15s 健康日志** | 有 stats，但无欠载计数/对齐校验 |
| 其他 native | `libdiplay_lwip.so`（用户态 TCP/IP，用于有线绕内核 TUN） | `libu/libfg/libwm/libbaiduprotect.so` = 加固/工具，**不是**编解码 | 仅 opus |

**四条结论（直接影响本清单的排序）**

1. **两家都没换 AAC 解码器**：EasyPlay 与我们同样走 MediaCodec+ADTS；HYLink 干脆不做 AAC（盒子做）。
   → 「换更快的 AAC 软解库」不是这条产品线的做法；**真正的行业做法是「少拷贝」**——
   EasyPlay 的 `openInto`（视频解进帧池、音频就地解）+ `VideoFramePool` 才是它的性能来源。
   ⇒ 本清单 §2.1 的排序应插入一条**低成本前置项**：先把「解密输出到调用方缓冲」这个改造搬过来
   （对应 §5 表里的 `AirPlayCrypto.doFinal` 那行），风险低于换解码器，且我们有 `libdiplay_opus.so` 证明 native 路可行。
2. **HYLink 的 `operating-rate` 写法可作 §2.3 的参考实现**：它是「标准键 + vendor 键」都试、还打印命中哪种，
   正是我们缺的（我们目前只设 `MAX_INPUT_SIZE`/`KEY_PRIORITY`）。
3. **HYLink 的音频监控值得抄**：`getUnderrunCount()`、PCM 帧对齐校验、15 秒一次的 PCM 健康日志——
   补上我们 AudioStats 缺的那几项（能直接回答「卡是解码慢还是播放欠载」）。
4. **盒子路线（USB dongle）在生态里确实存在**，但与本项目「不用盒子、纯软件直连」的既定方针冲突，
   只作协议对照（其协议蓝图在 `_upstream/cs11-carplay-dongle/docs/PROTOCOL.md`）。

### 9bis 那么 EasyPlay 会不会比我们更流畅？（**代码级推断，非实测**）

**前提**：项目铁律是「不安装/运行第三方改版 APK」，所以**从没在同一台 CS11 上跑过 EasyPlay**，
以下全部是逐行核对代码得出的推断，不是 A/B 测量。

**EasyPlay 明确更强的地方（直接决定流畅度）**

| 项 | EasyPlay（实证行号/形态） | 我们 |
|---|---|---|
| 视频解密 | `VideoFramePool frames = new VideoFramePool(...)` + **`opener.openInto(body, bodySize, nonce, header, frame.getBytes())`** —— 解密**直接写进池化帧缓冲**，再用 `lengthPrefixedToAnnexB(frame.getBytes(), frame.getLength())` **原地**转 Annex B | `readFully` 每帧 new `ByteArray(128)`+`ByteArray(N)`，`AirPlayCrypto.doFinal` 再 new 一个 `ByteArray(N-16)` |
| 帧复用 | **`VideoFramePool`**（3 帧池） | 无池 |
| 解码队列记账 | `offer` 只判 `frames.size() < maxFrames`，**无每帧全表扫描** | `offer` 每帧 `filterIsInstance`+`sumOf`，`pendingFrames()` 每帧 `count{}` |
| 音频解密 | `chachaOpenInto(key, wire, 12, len, wire, 4, 8, rtp, 12)` —— **在收包缓冲里带 offset 就地解密** | `doFinal` 产出新数组 |
| 解码器重建 | 1 秒冷却反复重建（**同一台车机上不会黑屏**，见 doc 36） | 移植了它的做法（`a14dedb`），但是我们后来才补的 |
| 其他 native | `libdiplay_crypto.so` / `libdiplay_opus.so` / `libdiplay_lwip.so`（有线走用户态 TCP/IP） | 仅 opus |

→ 这几条**正好命中我们实测的第一大抖动源**：doc 40 测得 GC 每 1.2–3s 一次、每次
`WAIT_FOR_CONCURRENT_GC blocked 37–67ms`，对应视频 `maxGap 122–151ms / shownP95 80–94ms`。
每帧少 2 个 N 字节新数组 + 少一次拷贝，GC 频率与阻塞都会下降。

**两家一样烂的地方（不要以为换了就有质变）**

- 触摸上行**同样无条件拼 hex**：`AirPlaySession.java:354`
  `"airplay event tx headers=" + head + " bodyHex=" + toHex(body)` —— 与我们一字不差。
- AAC 仍走 **MediaCodec + `is-adts=1` + ADTS 重封装**（`LegacyAudioRenderer.java:221/229/499`）。
- 音频广告策略**逐条一致**（102 media = AAC-LC）；同样没有 LPCM 可换。
- 同样 30 fps 上限、同样 TextureView 路线、同样要跟这台车机的 CPU0 中断风暴抢核。

**我们更强的地方**

- **无线在 CS11 上跑通**：热点自动化（4.4 反射 `setWifiApEnabled`）、控制通道同址绑定、RFCOMM/Bonjour、
  30fps 妥协、1080p 否决——这些都是针对这台 ROM 实测调出来的。EasyPlay 的无线相关符号是
  `WifiP2p`(215)/`LocalOnlyHotspot`(210)/`ManualHotspot`(204)/`Bonjour`(167)，而 `setWifiApEnabled` 只有 **1** 处
  → 它在本 ROM 上能否自动开热点是**未验证**的。
- **指标体系**：`shownP50/P95`、`dropped`、`queueMax`、`touch2frame/touchQueueMax`、AudioStats 全套——
  它只有 `LegacyConnectionTrace`（脱敏白名单），没有这些分位/队列指标。
- 系统级调优（IRQ 亲和 / RPS / 绑核）与「本机实测结论」都只在我们这边。

**结论**：**稳态静止时两家差不多；连续滑动/长时间交互时 EasyPlay 更可能更顺**（差距来自少分配/少拷贝 → GC 抖动更小），
**断连后回到 CarPlay 时它更稳**（解码器重建）——但这是「一档」的差距，不是代差，因为 30fps 上限、
AAC 软解、触摸 hex 日志、TextureView 这些大头两家共享。
⇒ **不建议装它来验证**（违反铁律且有供应链风险）；**建议直接移植那 3 件（帧池 + `openInto` + 便宜的队列记账），
再用我们自己的指标做改前/改后 A/B** —— 收益等价、可量化、不引入第三方依赖。

`Receive: video … seqGapEvents=0 lateOrDuplicate=0` 说明复用读缓冲没有破坏帧边界。

**日志量**：会话中本进程日志 ~35 行/秒，但**我们自己的 tag 只占 ~10 行/秒**（`xcertplay-usb`）；
其余是平台/ROM 噪声（`FPS-BOOST` 500 行、`MediaCodec/CCodec*` ~680 行——**在进程内但不属于我们，门控不了**）。
被门控的 iAP2 逐帧 dump 已完全消失 ✓。

**顺带发现的两个真问题（都不是本次移植引入的）**：
1. **同一行日志被写两次**：`Receive: video packets=…`、`airplay command type=…` 都是**逐字重复、同毫秒**两条。
   （`iAP tunnel iap2 rx=0x5001` **不是**重复，它是真高频 ~3.8 行/秒，且**未门控**。）
   ⇒ 下一批：查这条双路径 + 把 iAP tunnel progress 也纳入门控。
2. **音频卡顿**：见 §12.2。

### 12.2 音频卡顿的定位（用户反馈：连接正常但「声音卡顿厉害」）

**先排除本次移植**（字节级证据）：`authFailures=0`（AEAD 错一位就整体认证失败）、解码器 `inputDroppedTotal=0`、
`writtenFrames≈48300 帧/秒`（≈实时）、`playbackHeadFrames` 同步推进、`underruns=+0`（AudioTrack 从未欠载）。

**真正原因（平板实测）**：

| 观测 | 数值 | 含义 |
|---|---|---|
| 渲染侧队列 | `queue=192`（**打满**，容量 192 包 ≈ 4.1 s） | 抖动队列长期顶在硬上限 |
| 丢包 | 平时 `dropped` +0.25/s；**卡顿窗口 +73（≈1.6 s 音频）** | 满队列时整批拒绝 |
| 写阻塞 | **`maxWriteMs=3097`** | 一次 `track.write` 被卡 **3.1 秒** |
| 网络 | `readMaxMs=396`、`readsOver250Ms=14/窗口`、`interArrivalMaxMs=396` | 音频**每 ~400 ms 来一批**（平均包率正确） |
| 平台 | 音频解码器 **2 分钟重建 3 次**；微信/SystemUI 反复抢音频焦点；Xiaomi freezer（`GrezeManager`）+ `FPS-BOOST` | 路由/焦点切换 + 进程限流 |

机理：400 ms 突发 → 4.1 s 队列灌满 → 系统把 `track.write` 卡住 2–3 s（焦点/路由切换、进程被冻结）→
满载队列只能**丢最新包**（原代码原话 `audio queue full; dropping newest packets to bound latency`）→ 一个窗口丢 1.6 s → 听感即"卡顿厉害"。

### 12.3 音频队列加固：**一次失败的尝试 + 最终做法**

**第一版（错误，已撤回）**：按「每次到包都修剪到目标深度 750 ms（≈35 包）」实现。
平板实测立刻暴露：`skippedMs≈2415~2646 ms / 5000 ms 窗口` —— **每 5 秒跳掉约一半音频**，
用户听感从"卡顿厉害"恶化成"严重"。机理：链路是**每 ~400 ms 来一批 ~19 包**，
"每次到包都往固定目标砍"等于**每批到货都被砍掉、只留最新一小段**，抖动缓冲被彻底废掉。
⇒ 结论：**抖动缓冲不能在每次到包时修剪到固定目标**；突发型链路下这会把缓冲变成"只播最新"。

**最终做法（保留）**：
1. 队列**保持原来的硬上限 192 包**，不引入目标深度；
2. 唯一策略改变：**队列真的满时丢"最旧"的包**（skip forward），而不是原来的"拒绝最新包"——
   原来是在突发到货的瞬间成串丢包（平板实测单窗口丢 73 包 ≈1.6 s），改成丢最旧可让最新音频连续；
3. **指标保留**：stats 行新增 `skipped=` / `skippedMs=`（窗口内为腾空间丢掉的包数与音频时长），
   "丢包到底是不是问题"以后在车上一眼可见；
4. `AudioJitterTarget` 只保留**包时长学习**（`packetFrames`/`packetMillis`，把包数换算成毫秒）——纯逻辑、可单测。

**验证**：`:shared` **622 例 / 3 失败**（仍全是既存 `HotspotJoinNormalizedTransactionTest`）。

**教训（写在这里免得重犯）**：任何"修剪抖动缓冲"的改动，必须先在**突发型链路**上量 `skippedMs`；
对健康缓冲的修剪只能带**间隔 + 滞回**，并且要先证明"到达率长期大于消费率"，否则只会把音质砍掉。

**互补措施（不改代码）**：设置里的「**缓冲音乐（实验性）**」(`main_buffered_audio`，默认关) 让 Apple Music 这类 App
**提前约 2 分钟经 TCP 预送**音乐（`BufferedAudioStream`，1 s 提前投喂）——它针对的是"链路按突发送音频"这个**根因**，
与队列修剪互补（一个治本、一个治标）。

### 12.4 结论（2026-10-09，用户听感确认「不卡了」）

**根因**：无线下 iOS 把**媒体音频提前推送**（实测到达 ≈ 2 倍实时：46.8 包/秒到达，而消费侧只能 23.6 包/秒），
而 **type 102（普通 UDP 通道）没有任何节流能力**——播放按实时走，多出来的那一半只能成段丢弃
（实测 `skippedMs≈2400 ms / 5000 ms`，即每秒丢约半秒音频）⇒ 听感"卡顿厉害"。
**与本次移植无关**（改动前 `dropped≈116/窗口`，同样是丢一半）。

**解法（已生效、已验证）**：改用 **type 103 缓冲通道**（设置 →「显示与性能」→「音乐缓冲」与「帧率」之间的
「**缓冲音乐（实验性）**」；本次用 `run-as` 直接写 `main_buffered_audio=true` 打开）。
`BufferedAudioStream` 把预送的音频**按 1 秒提前量喂给播放器**，而不是丢弃。

**开/关对照（同一台平板、同一首歌）**：

| 指标 | type=102 UDP | **type=103 缓冲** |
|---|---|---|
| 队列 | `queue=185~192`（打满，≈4.1 s） | **`queue=37`** |
| 丢弃 | `skipped=116~120/窗口`，`skippedMs≈2400~2520` | **`skipped=0`、`skippedMs=0`** |
| 到达突发 | `maxGapMs≈400`、`readsOver250Ms=14/窗口` | **`maxGapMs=41`** |
| 其它 | `underruns=+0 dropped=0` | `underruns=+0 dropped=0` |
| 日志证据 | `Receive: audio type=102 …` | `buffered audio stream client=com.apple.Music rate=48000 port=34325`、`audio track prepared type=103 …`、`Buffered audio: queued 108 s, received 2001 kbit/s` |
| 听感 | 卡顿厉害 | **不卡**（用户确认） |

**代价**：音乐额外约 1 秒延迟，且需要 iOS/App 支持预送（Apple Music 这类可以）；通话/Siri 走其它流，不受影响。

**遗留代码项（可选，优先级低于上面的结论）**：type 102 路径缺"节流/自适应缓冲"能力是设计缺口——
若以后要在**不支持 103 的 App**上也顺畅，需要给 102 做真正的时间轴节流（而不是丢包），
实施前必须用 app 自带的 `AudioPacketCapture` 把送达结构抓清楚。
**注意别重犯 §12.3 的错误**：不要用"每次到包就修剪到固定目标"这种朴素做法。
