## 1. 七条发现的处置

### 1.1 F1 视频 NAL 长度整型溢出（原样应用，最高优先级）

- 文件/行：`shared/src/main/java/com/shilapi/xcertplay/airplay/ScreenStream.kt:255`
- 改法：`if (nalLength <= 0 || nalLength > length - offset) return payload`（减法形式，`offset` 已 +4，所以不会与 `length - offset` 的语义冲突）。
- 机制复核（读代码确认）：`nalLength` 是线上市 u32；`offset + nalLength` 在 `0x7FFFFFFF` 时回绕为负 → 旧检查放行 → `offset += nalLength` 变负 → 下一轮 `offset + 4 <= length`（`:249`）仍为真 → `readU32Be(payload, 负)` 抛 `ArrayIndexOutOfBoundsException`。该异常逃出 `onMessage`，被 `run()` 的 `catch (error: Exception)`（`:116`）接住 → `listener.onClosed(failure)` → 整条屏幕流结束。
- 可达性复核：清帧分支（`bodySize < ScreenCodec.TAG_SIZE`，`:130-136`）不校验发送方，也不需要密钥；128 B 头部 + 8 B body 即可命中（body 前 4 字节 `7F FF FF FF`）。审计的"任何局域网主机可打断视频"成立。
- **反向验证（本次实测，非推断）**：把该行临时改回 `offset + nalLength > length` 后跑 `ScreenCodecTest` + `ScreenStreamTest`：
  - `ScreenCodecTest.anOverflowingNalLengthLeavesThePayloadUntouched` → `ArrayIndexOutOfBoundsException`（精确复现，不是断言不符）
  - `ScreenCodecTest.anOverflowingLengthAfterAValidNalAlsoLeavesThePayloadUntouched` → `ArrayIndexOutOfBoundsException`
  - `ScreenStreamTest.aClearFrameWithAnOverflowingNalLengthIsDeliveredWithoutClosingTheStream` → 断言失败（流被畸形帧关闭）
  随后恢复补丁并重跑：`8 tests completed, 0 failed`。结论：这 3 个测试是真回归测试，不是"跟着实现写的空测试"。
- 第二个循环（`:261-268` 的就地改写）未加固：它只在第一遍全量校验通过后才执行（`if (offset != length) return payload`，`:258`），读到的长度必然合法（与审计第 6 条的判断一致）。

### 1.2 F2 池化帧明文长度守卫（应用）

- 文件/行：`ScreenStream.kt:135-170`（新增字段 `plaintextMismatchLogged` 在 `:49`）
- 改法：接住 `chachaOpenInto` 的返回值，与池化帧申请长度比较：

```kotlin
val frame = frames.acquire(bodySize - ScreenCodec.TAG_SIZE)
val plaintextLength = try { AirPlayCrypto.chachaOpenInto(...) } catch (e: Throwable) { frame.close(); throw e }
frameCounter.incrementAndGet()
if (plaintextLength != frame.length) { frame.close(); <一次性 onDiagnostic(...)>; return }
```

- 三个细节与理由：
  1. **nonce 计数器仍前进**：视频流每帧消耗一个自增 nonce，帧确实收到了（tag 也已通过校验），只有"写出长度"异常；不前进会让后续帧 nonce 与发送端错位，变成持续性认证失败。音频路径的计数器来自 RTP 包头，不受此影响。
  2. **只报一次**：与 `AudioStream` 的 `if (failureNumber == 1)` 口径一致，避免坏流刷日志。
  3. **不解码**：直接 `frame.close()` 归还池化 buffer，不把脏尾巴交给解码器。
- 覆盖面局限（诚实记录）：`chachaOpenInto` 在任何实现下都返回 `ciphertextLength - 16`（`AirPlayCrypto.kt:221-250`），所以这条守卫**在当前实现下不可达**，是纯防御。能测的是它依赖的性质：`AirPlayCryptoIntoTest.aShortOpenLeavesTheReusedTailOfThePooledBufferAlone` 把池化 buffer 预填 `0xA5`，断言写入长度 = `sealed.size - 16` 且**其后所有字节仍是 `0xA5`**；`ScreenStreamTest.aSealedFrameIsDeliveredWholeAndWithoutADiagnostic` 用真实 socket 跑完整密封帧，断言"长度守卫没有误伤正常帧"（诊断里不出现 `plaintext mismatch`）。

### 1.3 F3 ADTS 13 位 frame_length（调整：不抛异常，改为丢包 + 让越界不可能）

- 文件/行：`media/MediaCodecSupport.kt:129-153`（守卫 `:137`，`and 0x3` 掩码 `:146`，常量 `:212-225`）；调用点 `media/AndroidMediaSink.kt:1448-1461`（新增字段 `:1019`）
- **决策：拒收/丢弃，不用掩码截断。** 理由：
  1. ADTS 的 `frame_length` 同时描述"这一帧有多长"，是解码器切帧的唯一依据。把 9000 B 的 AU 掩码成 8191 会生成一个**自洽但错误**的头：头声明 8191，调用方仍按 `payload.size` 提交 9000 B，解码器会按头去读不存在的下一帧。截断（真的丢掉尾部字节）则会解出一帧坏音频。两者都比"不提交这一帧"更差。
  2. 调用点是 `AndroidMediaSink.handle()` → `feedCodec()`，跑在音频解码线程上。抛异常会沿着 `run()` 结束整条音轨；而同一函数对"过短的 Opus 包"（`:1476-1486`）本来就是"计数 + 只打一行日志 + return"。丢包路径与既有坏包处理完全一致。
  3. 真实的 AAC-LC access unit 只有几百字节（1024 采样），8184 B 的上限比它大两个数量级，丢包只可能发生在畸形/敌意输入上（只有 type-103 缓冲路径的 u16 帧长能送到这么大；4096 B 数据报路径物理上到不了）。
- 改法两层：
  - 调用点先判 `accessUnit.size > MediaCodecSupport.ADTS_MAX_ACCESS_UNIT_BYTES` → `inputDropped++`（复用既有"丢包"计数器，它已经出现在 `decoderDroppedTotal` 与两条统计日志里）+ 一次性 `Log.w`（`oversizedAacPacketLogged`）+ `return`。
  - `adtsFrame` 自身对超长 AU 返回 `ByteArray(0)`（与同文件 `toAnnexB`/`hevcCodecSpecificData`/`aacAccessUnit` 对畸形输入的契约一致），并把 `header[3]` 的高位写成 `(frameLength ushr 11) and 0x3`。这样"`adtsFrame` 永不产出畸形头"成为无条件不变量，也才让单测可以在不改 `AndroidMediaSink` 可见性的前提下证明它。
- 为什么不去测调用点：`AudioRenderer` 是 `private class`（`AndroidMediaSink.kt:978`），要测它得把整个类改成 `internal` 并绕过 MediaCodec/AudioTrack；投入产出比不合理。调用点的丢包逻辑由阅读复核（它是 6 行、与 Opus 分支同形），"不可能产出畸形头"由单测钉住。

### 1.4 F4 iAP 隧道明文尾巴无界保留（调整：抛 IOException 终止隧道）

- 文件/行：`airplay/IapTunnel.kt:222-249`（`IapPackageParser`，抛异常在 `:229`），接线在 `:47`、调用在 `:165`
- **决策：抛 `IOException` 终止隧道，不给保留量设上界。** 理由：
  1. **APTransportPackage 的 size 字段不自同步**：没有任何冗余校验能告诉你"真正的下一个头"在哪。设上界只能保证内存不涨，代价是**永久卡死**：非法 size 永远停在 offset 0，之后每次读都在同一处 break，`onIap` 再也不会被调用，而且没有任何日志。一个"活着但再也不工作"的隧道的可诊断性比失败更差。
  2. **与同一条循环里已有的失败口径一致**：`decryptFrames()`（`:176-193`）遇到 tag 校验失败时抛 `AEADBadTagException` → 同一个 `catch (Exception)` → `listener.onClosed(failure)`。垃圾数据本来就会终结隧道，`size` 非法只是同一类事件的另一个入口。
  3. 上游有能力恢复：失败走的是既有的 `onClosed(cause)` 路径，会话层按既有的隧道失败流程重建。
  4. 顺带堵住 O(n²)：`run()` 的 `plaintext += decrypted.first` 之所以会退化成平方，是因为尾巴可以无限增长；长度非法时立刻失败，正常路径的尾巴上界是"一个未完成的包"（≤ `MAX_PACKAGE` = 4 MiB + 一个 16 KiB 读块）。
- 可测性改造：把解析从 `IapTunnel` 抽成同文件的 `internal class IapPackageParser`（`IapTunnel.kt:222`，约 30 行），回调 `(messageType, body)`；`IapTunnel` 只保留"过滤 `comm` + 打诊断 + 转发"三行（`:47-53`）。测试无需 socket、无需密钥：`IapPackageParserTest` ×4 覆盖"size < 32 抛"、"size > 4 MiB 抛"、"完整包投递 + 只保留不完整尾巴"、"非 comm 包同样上报（过滤是隧道层的事）"。
- 未动的地方：`decryptFrames()` 仍会保留"半个 NetSocket 帧"（上界 65535+18 B），`ciphertext +=` 仍是拼接。它们有界，本次不动（见 §2 说明与 §4 遗留清单）。

### 1.5 F5 `VideoDecodeQueue` 计数与队列不一致（调整：不加锁整个 `poll`）

- 文件/行：`media/VideoDecodeQueue.kt:55-76`（`offer`，顺序改为"先计数后入队"）、`:99-113`(`poll`，只有计数变更进 `synchronized(this)`)
- **为什么不用 `@Synchronized fun poll(...)`**：`poll` 会在 `jobs.poll(timeout, ...)` 上**阻塞等待**，调用点是解码线程每轮 `queue.poll(5)`（`AndroidMediaSink.kt:563`）。给它加实例锁意味着等待期间一直握着 `offer()`/`discardFrames()` 需要的同一把锁：屏幕接收线程每帧都会被拖住最多 5 ms。这个计数器的存在意义恰好是"别让接收路径为了队列花时间"（`VideoDecodeQueue.kt:49-51` 的注释），所以把 5 ms 的阻塞搬进锁里是拿性能换统计精度，不划算。
- 真正的根因与改法：
  1. `offer` 原来是"先 `jobs.offer(job)`，后 `frameCount++`"。消费者在两者之间把该帧取走并减一，就会把计数减成负数；同一窗口里另一个 `offer` 读到的是偏低的计数，于是漏掉一次本该触发的溢出回收。
  2. 改成**在同一把锁内先计数、后入队**：任何被消费者看到的帧必然已经被计数过，"移除必然抵掉一次自增"。计数上限也随之成立（检查与自增之间不再可能被并发减一插队）。
  3. `poll` 只在减计数时进 `synchronized(this)`，锁内不做任何阻塞操作，生产者不会被拖住。
- 测试：`VideoDecodeQueueTest.concurrentOfferAndPollKeepTheDepthInsideItsBudget`——两个生产者 + 两个消费者热跑 200 ms（`poll(1)`），主线程尽量密集采样 `pendingFrames()`，断言 (a) 采样到的深度永远在 `0..maxFrames`，(b) 线程停稳后把队列抽干，`pendingFrames() == 0` 且抽出的帧数 ≤ `maxFrames`。**诚实说明**：这是压力测试而非确定性复现（窗口是纳秒级），修好后它恒过，修之前不保证必挂；它的价值是把"计数负值/超预算"这类回归变成可见失败。已连续跑 3 次全绿，无抖动（不 flaky）。

### 1.6 F6 设置通道包长切片（部分应用：审计前提与工作树不符）

- 文件/行：`airplay/VideoSettingsChannel.kt:86-101`（新增 `SEQUENCE_OFFSET/SEQUENCE_END` 在 `:133-136`）
- **复核结论：审计描述的触发路径在当前工作树不存在。** 依据有三条，缺一不可：
  1. 循环条件是 `while (buffer.size - offset >= HEADER)`（`:88`），`HEADER = 32`（`:130`）——要进入循环体，`offset` 处至少有 32 个字节可读；
  2. 包内声明 `size < HEADER` 会被 `:90` 直接拒绝（审计以为这里是 `>= 20`）；
  3. 只有 `buffer.size - offset >= size` 才会继续（`:91`）。
  三者合起来保证切片 `[offset+20, offset+28)` 一定落在 buffer 内，`size ∈ [20,27]` 早在第 2 条就被拒，抛的是 `IllegalStateException("bad package size 20")`，不是 `IllegalArgumentException`。
- **仍然做的小加固**：把"实际读取的字段"写成显式守卫 `if (size < SEQUENCE_END) throw IllegalStateException(...)`（`:97`），并把 `20`/`28` 换成命名常量。它今天被 `size < HEADER` 蕴含（HEADER=32 > 28），因此**当前不可达**；存在的意义是：切片点自我保护，不依赖"遥远的 `HEADER` 恰好大于 28"这一隐式耦合（将来有人把 HEADER 调小、或把 type 字段从 12 字节改短时，越界会变成显式拒绝而不是 `copyOfRange` 抛 `IndexOutOfBounds` 关掉通道）。
- 测试：`VideoSettingsChannelTest` ×3——声明 20..27 且 buffer 有 64 字节（真正要触发的是"声明小、缓冲多"这个形状）时被 `IllegalStateException` 拒绝且**不写任何 reply**；合法 36 B `sync` 包被回 `rply` 且 seq 8 字节原样回显（解密验证）；声明 36 但只到 34 字节时原样保留尾巴不回复。
- 保留的既有行为：声明 `size < 32` 仍然抛异常关闭通道。这是有意的（该通道的 framing 不可信 → 让 iPhone 侧的设置流按既有语义结束），本次不动。

### 1.7 F7 USBMUX 写路径 16 KiB 上限（应用）

- 文件/行：`transport/Iap2UsbMuxHost.kt:277-299`（常量）+ `:364-375`（`send` 分块）
- 改法：`MAX_TCP_SEND_PAYLOAD_BYTES = USBFS_BULK_URB_CEILING_BYTES - MUX_HEADER_BYTES - TCP_HEADER_BYTES` = `16384 - 16 - 20` = **16348**；`MUX_HEADER_BYTES`/`TCP_HEADER_BYTES` 从 `private` 提升为 `internal` 以便派生与测试；删掉连接类里那个只算 payload 的 `MAX_SEND_PAYLOAD_BYTES = 16 * 1024`。复用读路径已有的 `USBFS_BULK_URB_CEILING_BYTES`（`transport/UsbReadQueuePolicy.kt:9`），不再引入第二个魔数。
- 影响与代价：一帧 USBMUX 最大 `16348 + 36 = 16384` B，正好贴住上限；每 16 KiB 数据多发一次 `bulkTransfer`（payload 少 36 B，0.22%），换来"不会因为超限而整整一条有线链路失败"——`Iap2UsbSession.write` 在 `bulkTransfer` 返回 `-1`（≠ `data.size`）时抛 `IphoneUsbException.DeviceUnavailable`（`transport/IphoneUsbHost.kt:397-407`），`sendFrame` 会 `fail(error)` 并关闭整个 USBMUX host。详见 §3。
- 测试：`Iap2UsbMuxSendChunkTest` ×2——(a) 一个满 chunk 连同两个头 ≤ 16384，且 `MAX_TCP_SEND_PAYLOAD_BYTES == 16384 - 36`；(b) 记录旧形状（16384 payload ⇒ 16420 B 帧）确实超限。测试同时钉住"派生而非硬编码"：将来若有人把 payload 改回 16 KiB，第 (a) 条会失败。

## 2. 看着可疑但实际正确（15 条，避免后来人重复审计）

> 行号已按本次改动后的工作树复核（未改动文件的行号沿用审计原值）。带 javap 字样的结论来自审计当时的 `javap -p -c` 反汇编（`bcprov-jdk18on-1.85`），本次未重跑反汇编，结论保留，并由新增单测间接覆盖。

### ScreenStream / VideoFramePool

1. **视频长度算术本身正确（两个 provider 都）**：`ScreenStream.kt:135` 按 `bodySize-16` 申请、`:142` 传 `ciphertextLength = bodySize`、`outputOffset = 0` ⇒ 明文恰为 `bodySize-16`，而 `VideoFramePool.kt:56` 把容量按 2 的幂向上取整，恒 ≥ 申请长度。BC 回退路径（`AirPlayCrypto.kt:246-250`）：解密态 `getOutputSize = max(0, len+bufPos-16)`；`processBytes` 按 64 B 块写出并保留最后 16 B；`doFinal` 只算 `count = bufPos-16`、只校验 `outOff+count <= out.length` 再写 `count` 字节 ⇒ 合计恰好 `ciphertextLength-16`，且**不要求输出容量覆盖 tag**。Conscrypt 侧（JCE 5 参 `doFinal`）由 `AirPlayCryptoIntoTest` 覆盖。
2. **别名问题不存在**：`body` 是接收线程私有的复用数组，从不外传——清帧分支 `:132` 与 config 分支 `:190` 各自 `copyOf`；池化 buffer 只有在 `OwnedVideoFrame.close()`（`VideoFramePool.kt` 的 `AtomicBoolean`，双释放安全）后才回 free list，而释放发生在 `VideoDecoder.feed` 的 finally（`AndroidMediaSink.kt:852`）、在 `input.put(annexB, 0, annexBLength)` + `queueInputBuffer`（`:841-842`）之后，也就是字节已经拷进 codec 输入 buffer；`discardFrames`/`poll` 只能拿到"仍在队列里"的帧；`VideoFramePool.close()`（`:88`）置 `closed` 后 `recycle` 直接丢弃。

### AudioStream / BufferedAudioStream

3. **复用的 12 B nonce 不会跨包污染**：`AudioStream.kt:156-157` 每包 `fill(0,0,4)` + `copyInto(nonce,4,...)`；BC 的 `AEADParameters` 对 nonce 与 associatedText 都 `Arrays.clone`（javap 确认），`KeyParameter` 亦然；JCE 侧 `IvParameterSpec` 构造即 clone、`init` 立即消费 IV。
4. **type 103 与修好的 102 语义完全一致，不是"恰好能跑"**：`BufferedAudioStream.kt:383-386` 用 `sealedEnd = body.size - NONCE_BYTES` 排除 8 B nonce，再把含 16 B tag 的 `body.copyOfRange(RTP_HEADER, sealedEnd)` 交给 AEAD ⇒ 明文 = `sealed-16`；最小长度双重校验在 `:99`（`2+12+16+8 = 38`）与 `:379`（`12+16+8 = 36`）。关键是它用的是**分配式** `chachaOpen`（`AirPlayCrypto.kt:189-195`：`getOutputSize` 后 `copyOf(outputLength)`），**结构上不可能留下未写的尾巴**——这正是 103 从未中招的原因。`MicrophonePacketizer.sealPacket` 对称（packet = 12 + sealed + 8）。
5. **`chachaOpenInto` 的 BC 回退语义正确**：`AirPlayCrypto.kt:241-251`，AAD 全等走快路径、否则 `copyOfRange`；`processBytes`+`doFinal` 返回值 = `processed+finalized` = `ciphertextLength-16`；失败抛 `InvalidCipherTextException`/`AEADBadTagException`，而所有调用方在异常路径都丢弃输出 buffer（`ScreenStream.kt:136-152`、`AudioStream.kt:174-187`、`BufferedAudioStream.kt` 对应 catch）⇒ 半截明文不外泄。

### MediaCodecSupport

6. **`toAnnexB`（`:59-95`）**：两遍扫描；第一遍用**减法** `length > lengthPrefixed.size - inputOffset`（不会溢出）+ 显式 `length > Int.MAX_VALUE - outputSize - 4`（`:75`）防输出累加溢出；第二遍只在第一遍全量验证后执行 —— 与 `ScreenCodec` 的写法正好形成对照。这也解释了为什么 `ScreenCodec` 的第二遍同样安全。

### 传输/链路层

9. **`Ntb16Codec.parse`**：`require(offset >= 0 && length >= 0 && offset <= block.size - length)`（`:56`）；切片前 `datagramStart >= offset && datagramStart <= end && datagramEnd <= end`（`:79`）；`hops < maxHops`（`:66`）防指针环；长度字段 u16 ⇒ 无溢出。`NcmUsbBridge.drainFrames` 的 `blockLength < 28` 拒绝（`:199`）+ `bufferedSize < blockLength` 等待（`:200`）正确。
10. **iAP2 框架层**：`iap2/wire/Iap2CsmFramer.kt` 的 `offer/drain`（`:19`/`:35`）以 `receive.size < length` 等待完整帧（`:45`）、`length < HEADER_BYTES` 丢 1 字节重同步（`:41`）、`check(count > 0)` 防死循环（`:27`）；`encodeFrame` 写入的 length 含 6 B 头，与解析端一致。`transport/Iap2LinkEngine.kt` 的 `parseAvailable`（`:264`）有 `header.length < HEADER_BYTES` 早退（`:301`）、`> MAX_WIRE_FRAME_BYTES` 判死（`:302`）、`room == 0` 分支（`:183`）保证进度（`die` 而非空转）；`payloadWithChecksum.size - CHECKSUM_BYTES`（`:286`）最小为 0，不会负数 `copyOf`。`iap2/wire/Iap2Wire.kt` 的 `decodeBody` 用 `length > encoded.size - offset`（`:102`，减法，安全）。`transport/UsbMuxFrameBuffer.takeFrame`（`:24`）的 "optional reply padding" 看着最险但成立：候选校验同时验证了后一帧的 protocol/length/magic（`:37-41`），跳 4 B 后重读的 length 就是已校验过的值；`bytes.size < PADDING_BYTES + HEADER_BYTES`（`:36`）与更长的 `+ TCP_HEADER_BYTES`（`:42`）都在读取相应 offset 之前 return null。
11. **`Iap2FileTransferReceiver`**：声明长度先校验（`size < 0 || size > maximumArtworkBytes` → rejected，`:59`）再分配；写上限校验防超写；`readU64`（`:100`）有心符号保护 ⇒ 负/超大声明长度都安全。
12. **`UsbReadQueuePolicy`**：每条失败/早退分支都 `buffer.limit(originalLimit)` 还原（`:37`、`:55`）；成功路径**有意**保留 `position + size` 给调用方；`submitUnchanged` 的 `check(...)`（`:67`）是对"vendor 拒绝时不得改动 buffer"契约的**有意断言**（抛 `IllegalStateException` 是设计）；`successfulLimit` 由调用方在 pipe 的 state lock 内串行使用，无竞争。

### AndroidMediaSink

13. **没有重演音频那个"tag 被算进明文长度"的 bug**：`drainCodec` 用 `val size = info.size`（真实解码字节数，不是 capacity，`:1580`）+ `position(info.offset)`/`limit(info.offset+size)`/`get(pcm,0,size)`（`:1593-1599`），`pcm` 只在需要时扩容；`feedCodec` 用 `payload.size`（`:1523`）；`bufferProgress.written(count)` 用的是 AudioTrack 的**实际返回值**（`:1654`）；`queuedBytes(head)` 第二次调用 delta 为 0；`applyFadeIn` 的 `data[position+1]` 在范围内。API 19 的 `outputBufferCompat = getOutputBuffers()[index]` + 显式设置 position/limit 正是旧 API 的正确读法。`VideoDecoder.feed` 的 `input.put(annexB, 0, annexBLength)` + `queueInputBuffer(index, 0, annexBLength, ...)`（`:841-842`）一致。

### Opus 与其他

14. **`OpusEncoderSupport`（`media/OpusEncoderSupport.kt:25`、`:43`）**：`private val cached: Boolean by lazy` 默认 `SYNCHRONIZED`（线程安全，不会构造出两个 encoder）；初始化块调用的是**两参**重载，且软件探测链里没有任何路径回调 `OpusEncoderSupport` ⇒ **不会递归**，失败一律收敛为 false。`SoftwareOpusEncoder.encode` 校验 `pcm.size == FRAME_BYTES`、`length > 0` 才 `copyOf(length)`，异常收敛为空列表。

## 3. 未能在本机闭环的平台问题：USBMUX 写路径的 16 KiB 上限

**问题**：`Iap2UsbMuxHost.send` 分块后，单次 `bulkTransfer` 最坏 16420 B（16384 payload + 16 B MUX 头 + 20 B TCP 头），而读路径（`UsbReadQueuePolicy`）一直在 16384 B 单 URB 天花板下工作。写路径没有等价守卫。

**为什么本机判不了**（逐条实测，不是推测）：
- 本机 SDK 是 `D:/Dev Environment/android-sdk`，`platforms/` 下只有 `android-35` 与 `android-37.0`，**没有 android-19**，无法直接对照目标 ROM（4.4）的 `android.jar`；
- **没有 `sources/` 目录**，装不到 framework 源码；
- 本机唯一的源码包 `platforms/android-35/android-stubs-src.jar` 是签名 stub（方法体全是 `throw new RuntimeException("Stub!")`，且**完全没有 javadoc**），拿不到 `bulkTransfer` 的长度约束说明；
- **无网络**：`web_fetch` 取 AOSP 的 `UsbRequest.java`（代码注释里引用的那个 URL）直接 `fetch failed`，所以连"读路径 16 KiB 是 `UsbRequest.queue(ByteBuffer)` 在 API < 28 的行为"这条也**无法在本机重新取证**，只能沿用仓库内既有注释与上游 commit 764e0ba1 的结论；
- 没有 USB 设备/head unit 可跑，也没有 host 端可复现 usbfs 的 URB 限制。

**做了什么保险**：无论上限是否对写路径成立，一律按 16384 分块（§1.7），派生自 `USBFS_BULK_URB_CEILING_BYTES` 与两个头长度，并有单测钉住"payload 若是 16 KiB 就会超限"。最坏代价是每 16 KiB 多一次 `bulkTransfer`（payload 少 36 B），最坏收益是避免 `bulkTransfer` 返回 `-1` 时 `Iap2UsbSession.write` 抛 `DeviceUnavailable` → `sendFrame` 的 `fail(error)` → 整条 USBMUX/有线链路失败。

**点火时的一次性判据**（建议列入 CS11 点火验收清单，用 debug 构建跑一次、打印一行即可）：
1. 临时在写路径构造/发送一次 **16420 B** 的 frame（或把 `MAX_TCP_SEND_PAYLOAD_BYTES` 临时改回 `16 * 1024`），打印 `UsbDeviceConnection.bulkTransfer(...)` 的返回值与耗时；
2. `-1`（或 < 请求长度）⇒ 天花板对写路径同样成立，本次分块是**必需**的，保留并且不要为大包做任何"优化"；
3. 返回 16420 ⇒ 写路径没有这个限制，本次分块是无害的成本（0.22% 的额外 transfer），可以保留（推荐）或在有实测依据后放宽——但**不要**在无线/有线混用场景下放宽到超过 16384，因为读路径的证据说明该 ROM 的 usbfs 是按单 URB 计的；
4. 顺带记录一次"连续 16 KiB 写"的吞吐，确认多出来的 transfer 没有把 NCM 写路径的延迟推高（这是唯一可能的负面影响）。

## 5. 方法论（为什么这轮审计有效）

这轮审计的产出质量不是来自"把代码再读一遍"，而是来自四条被明确要求的口径，值得作为后续同类审计的模板：

1. **区分"已确证"与"疑似"**。7 条发现全部给了触发条件和受影响路径（哪条分支、哪个调用者、谁能触发）；反之，"看着可疑"的 15 条被单独列出来并给出**为什么正确**。两者混在一张清单里，最贵的代价是后来人反复重新审计同一段代码——本文件 §2 的存在就是为了让下一次审计能直接跳过这 15 条（除非代码变了）。
2. **给结论配"可证伪的机制"**，而不是"这里可能有问题"。F1 能一次说清"u32 溢出 → 检查放行 → 负下标 → AIOOBE → 逃出 onMessage → 关流"，所以补丁可以精确到一行，回归测试也可以精确构造（`7F FF FF FF` + 几个 0 字节），甚至能在本机做**反向验证**：把补丁改回去，测试必须挂；挂不出来就说明测试是空的。本轮 F1 的三条测试都通过了这个检验。
3. **要求"给出实验设计"而不是"直接猜"**。F7 的平台上限本机判不了，正确产出不是"我猜会失败"或"我猜没事"，而是：写清楚本机缺什么证据（无 API 19 平台包、无 sources、stub 无 javadoc、无网络）、在此前提下选择零成本保险（派生常量分块），并把**一次性的点火判据**（打印一次 16420 B 的 `bulkTransfer` 返回值，`-1` ⇒ 必须分块）交给唯一能给出证据的环境。同理 F5 的窗口是纳秒级、无法确定性复现，就明确改写成"断言修复后必然成立的不变量 + 压力采样"，并如实标注它不是确定性复现。
4. **反例优先于正例**：每条边界修复都要有"边界之内仍然正确"的用例（8184 的 ADTS 头仍然自洽、合法密封帧仍然整帧投递且无诊断、合法 36 B `sync` 仍然收到回显 seq 的 `rply`）。只测"坏输入被拒绝"很容易写出把好输入也拒掉的补丁。
5. **修改最小、口径一致**：能用现有计数器（`inputDropped`）就不新增统计；能用现有失败路径（`onClosed`）就不新造错误通道；能不抛异常就不抛（音频线程）；能不阻塞生产者就不加锁（`poll`）。这五条决定了本轮 7 条修复里没有一条改变对外行为，只改变"坏输入发生时"的行为。
