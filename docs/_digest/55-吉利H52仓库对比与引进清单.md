## 2. 本次引进的四项（代码级）

### 2.1 USB 写：短写续写 + 一个共享截止时间 —— `transport/UsbBulkWrite.kt`

- **对方证据**：`P21快照/shared/.../transport/LegacyUsbTransfer.java`（原文：API<28 分块 ≤16KiB、
  短写推进实际偏移、**各块共享 elapsedRealtime 截止时间**，避免每块重新计时导致永不超时）。
- **我们原来的行为**（【事实】）：
  - `IphoneUsbHost.kt` 的 `Iap2UsbSession.write`：一次 `bulkTransfer`，`transferred != size` **即抛
    `DeviceUnavailable`** ⇒ MUSB 截断一次就整条有线链路失败；
  - `NcmUsbBridge.send`：短写同样直接抛（`transferred <= 0` 才是"手机未就绪，保留重试"）。
- **现在**：`UsbBulkWrite.all(length, timeoutMillis, nowMillis, transfer)` 纯逻辑：
  从"实际到达的偏移"续写，**所有尝试共用一个 deadline**；返回 `(written, timedOut)`。
  调用方只在**真的发生短写**时才切片（`copyOfRange`），正常路径仍是一次 4 参 `bulkTransfer`、
  **零分配、零行为变化**（这一点也是为兼容 Robolectric 的 USB shadow 而必须的，见 §6）。
- **测试**：`UsbBulkWriteTest`（5 例：单次完成 / 续写偏移与递减预算 / 停滞立即返回 / 截止时间共享 /
  预算耗尽不再调用）。
- **上车验证**：有线连续使用看 `USBMUX write transferred …` 是否还出现；MUSB 阶梯（`UsbReadQueuePolicy`）
  侧不变。

### 2.2 USBMUX 读：改为**持久请求**（对齐我们自己的 NCM 形态）

- **对方证据**：`P21快照/.../transport/H52UsbReadPump.java:24-63`（专用线程 + `ArrayBlockingQueue(64)`
  + 无参 `requestWait()`）；其注释与我们 NCM 的注释同源：`bulkTransfer(byte[])` 会把数组**钉在
  JNI critical section** 里。
- **我们原来的行为**：`Iap2UsbSession.read` **每次读**都新建 `UsbRequest` + `allocateDirect(64KiB)`，
  超时就 `cancel()` + `drainCancelledRead()`（再等一次 `requestWait`）。
- **偏离原计划（有理由）**：我们**没有**再加第三条线程，而是把 USBMUX 改成与
  `NcmUsbBridge.readChunk`（`NcmUsbBridge.kt:47-52, 235-303`，**我们自己的既有形态**）一致的
  **持久请求 + 复用直缓冲**：一次会话只建一个请求/一个 64KiB 直缓冲，超时**保持排队**、不再
  cancel+drain。理由：① 调用方本来就是专用 USB 工作线程，"把阻塞搬到另一个线程"本身不产生收益；
  ② 真正的收益是**消掉每次读的 UsbRequest/64KiB 分配与 URB 重建**（我们 W2 一直在打的分配/GC 目标）；
  ③ 复用本项目已在本车验证过的形态，比引入新线程模型风险更低。
- **测试**：`UsbMuxIssue100RegressionTest`（既有，覆盖 USBMUX 读写与分帧）**全部通过**。
- **上车验证**：有线 iAP2 控制通道；日志里 `USBMUX read queue compatibility fallback` 行数不应增加。

### 2.3 视频线程优先级 `-4 → -8` —— `airplay/VideoThreadPriority.kt`

- **对方证据**：`P21快照/.../compat/H52NoRootBridge.java:108-115`（`THREAD_PRIORITY_URGENT_DISPLAY`），
  调用点在 `ScreenStream` 与 `AndroidMediaSink` 的线程入口。
- **我们**：两处都是 `THREAD_PRIORITY_DISPLAY(-4)`（`ScreenStream.kt:62`、`AndroidMediaSink.kt:522`）。
  音频一直是 `URGENT_AUDIO(-19)`，仍高于 -8，不会被抢。
- **现在**：新增 `VideoThreadPriority`（纯 `sanitize()` + 属性读取），默认 `URGENT_DISPLAY(-8)`；
  **热回退**（ADR-8）：
  ```powershell
  & $adb shell setprop debug.diplay.video_priority display   # 回到 -4（A/B 的另一侧）
  & $adb shell setprop debug.diplay.video_priority ''        # 回到默认 -8
  ```
  下一次视频流 SETUP 生效（无需重装）。**按 ADR-19 交错 A/B**，判据：
  `DiPlay-VideoStats` 的 `shown`/`dropped`/`queueMax`/`touch2frame` + `DiPlay-AudioStats` 的
  `underruns`/`skipped`。
- **风险**：i.MX6Q 上 -8 可能与 SurfaceFlinger/触控抢核，**反而抬高 `touch2frame`**；所以必须有 A/B。

### 2.4 热点：MANUAL 补 `0x5703` 的 BSSID（并接入免 root 信道读数）

- **对方证据**：P12"修复无线凭证 BSSID"（工作树 `compat/H52WirelessBssid.java`，`Iap2WirelessControlClient`
  把 6 字节 `bssid=` 放进移交消息）；其自述"不能把成功归因于 BSSID 单项"。
- **我们的缺口（【事实】）**：`0x5703` 的可选字段 0 只有 **EXISTING_WIFI** 填
  （`ExistingWifiManager.kt:107,152`）；**MANUAL（CS11 的默认路径）留空**，而
  `CarPlayController.kt:1122` 转发的就是 `hotspotInfo.accessPointBssid`。
- **现在**：把原先 `ExistingWifiManager` 私有的 `accessPointAddress()` 提成
  `network/AccessPointAddress.kt`（同一套校验：**全零 / 组播位 / `02:00:00:00:00:00`
  一律拒绝**，宁缺勿造），MANUAL 用 `localInterface.hardwareAddress`
  （其来源含 `HotspotInterfaceBssid` 的 EUI-64 反推兜底）填 `accessPointBssid`；
  诊断行新增 `apBssidKnown=`。
- **上车验证**：`DiPlay-Cluster`/iAP2 日志出现 `bssid=`；对照 iPhone 是否入网更快/更稳。
  ⚠️ 若该 MAC 与 iPhone 扫到的 BSSID 不一致，需保留"留空"这一侧的 A/B。
- **信道路径**：`observedManualHotspotChannel(..., driverFrequencyMHz)` 新增**最后一位**证据源，
  接的是我们**已有但从未接线**的 `LegacyHotspotRadio`（`SIOCGIWFREQ`，无 shell、无提权）；
  它只会在原本要报 `0`（未知）时才补值，**不会改变今天任何已知值**。
  ⚠️ **但原生模块当前被禁用**：`shared/build.gradle:20` 明确写着"暂时关闭原生构建（hotspot JNI 模块；
  后续如需再用 NDK<=r26 接入）"，已构建 APK 里只有 `libconscrypt_jni.so` 与 `libdiplay_opus.so`
  ⇒ 在车上它只会返回 `driverError=driver reader unavailable`。**本项只是把代码路径准备好**，
  真正生效还需要单独一轮"重新启用原生模块"的任务。

### 2.5 legacy P2P：createGroup 前记录"我们请求过"

- **对方证据**：`docs/geely-android43/H52-P2P-FIRMWARE-REVIEW.md`（反汇编）：API18 两参
  `createGroup` 实为 `P2P_GROUP_ADD persistent`，**`removeGroup` 不删 persistent profile**，
  且该固件 `WifiP2pGroup` **无频率 getter**。
- **⚠️ 我方复核修正了对方（及我方首轮分析）的前提**：`WifiP2pGroupManager.kt:253` **确实**在建组成功后
  写入 `owned_ssid = group.ssid`，所以"legacy 分支不写 owned_ssid"是**错的**。
- **真正的缺口**：legacy 分支在 `createGroup` **之前**不记录任何东西，而该固件会让组**存活下来**；
  若 App 在 createGroup 与 `:253` 之间死掉（崩溃/拔线），下次启动 `canReclaim(isOwner=true,
  ssid="系统生成名", recorded=旧值/null, prefix="DIRECT-dp……-")` = false ⇒ 抛
  `P2pResetRequiredException`，把"我们自己建的组"当成陌生组。
- **现在**：legacy 分支在建组前写 `owned_legacy_request=true`；`P2pOwnership.canReclaim` 增加
  `legacyGroupRequested` 参数（默认 false，语义不变）；组名落库（`:253`）与成功回收（`:168`）时
  **清除该标记**。测试：`P2pOwnershipTest` +1 例。

## 3. 明确不引进（含理由，避免重复评估）

| 项 | 对方做法 | 不引进的理由 |
|---|---|---|
| 视频接收窗 | `setReceiveBufferSize(524288)`（`H52NoRootBridge.java:124`） | 与我们 2026-10-10 实测方向相反：请求 8KiB→实际 16KiB 时迟到丢帧 161→17–28、`maxGap` 1736→239–331ms、`touch2frame` 86→51–60ms；大窗让手机突发挤掉音频 UDP（doc 51 / ADR-11） |
| `MediaCodec.flush()` 代替重建 | `H52MediaCodecOptimizer.flushDecoder()` 仅 `codec.flush()` | 其 `VERSION-HISTORY.md` 自认"flush 触发后的恢复未专门回归"；我们注释记录 flush 可能在首帧前丢 CSD。**只值得做成带开关实验，且 flush 后必须重放 CSD** |
| Concentus 纯 Java Opus 解码 | `P21快照/media/LegacyOpus.java` + 内联 Concentus | 我们 `LegacyNativeOpus`（libopus）已在解导航/通话 Opus；纯 Java 在 4×A9@1GHz 无 NEON 上更慢。真正缺口只是"libopus 不可用时下行无兜底"，属独立课题 |
| `HotspotJoin*`／`SoftApConfiguration` 厂商元素事务 | 无对应（他们没这族） | 我们那族是 `require(SDK_INT>=33)`，与 API19 无交集；按已删 LocalOnlyHotspot/MapEmbed 的同一口径处理 |
| usbfs JNI（`LegacyUsbNative`）、`SET_CONFIGURATION`、`GET_CONFIGURATION` 校验 | `P21快照/compat/LegacyUsbNative.*`、`UsbDeviceLayout`、`NcmConfigurationGuard` | CS11 的 NCM 由**内核** `cdc_ncm` 按接口描述符认领（`CarPlayController` API<21 不选配置），app 不该改配置；引入 JNI 的收益不抵 NDK/权限风险 |
| `Base64Compat`/`CharsetsCompat`/`PendingIntentCompat`/`ConcurrentHashMapCompat` | 手写兼容类 | 我们 `minSdk=19` + **core library desugaring** + `ForbiddenLibraryApiTest`；已核对 AGP 的 desugared-API 清单：`java/util/Base64`、`java/util/Optional`、`java/util/concurrent/ConcurrentHashMap`(类级)、`Collection#removeIf`、`Map#getOrDefault`、`Stream#anyMatch`、`Map#computeIfAbsent` 均在列 |
| legacy Wi-Fi Direct 建组 | 去 API29 下限走两参 `createGroup` | 我们**已更完整**：同样走两参，另有 `WifiP2pLegacyChannels` 反射 `setWifiP2pChannels` 做显式信道协商，并拒绝把超时当拒绝 |

## 5. 两条必须记住的负面结论

### 5.1 "免 root 桥接"名不符实，且真身是固件后门

- **开源工作树里根本没有** `H52NoRootBridge`/`usbprotect`（我已全树检索确认）；工作树的写法是
  `su` 回退：`H52WirelessDiagnostics.java:13-15`（`su -c cat /data/misc/wifi/hostapd.conf`）、
  `H52UsbConfigurationFix.java:53-70`（`su -c echo … > /sys/…`）。`e3016ce` 提交也只是"记录 root 需求"。
- **P21 快照里的真身**（`P21快照/.../compat/H52NoRootBridge.java:17-55`）：
  `ServiceManager.getService("usbprotect")` → 写接口 token
  `com.neusoft.c3alfus.projectservice.IUsbProtectService` → `transact(0x16)`，把一个 **UTF-8 shell
  命令字符串**交给该服务（uid=1000）执行并读回输出。作者自述这是"绕过客户端白名单"。
- **对我们的意义**：它证明**同族 GKUI/ECARX 固件可能存在"厂商服务替应用执行 shell"的通道**。若 CS11
  也有，我们"每次点火都要靠 modprobe 劫持重建 root 链"的做法（`Cs11NetdevBootstrap`）就有可能被替代。
- ⚠️ **合规取舍由车主拍板**：这等于调用一个"设计上就是任意命令执行"的厂商接口。它不刷机、不装改包、
  不改 `/system`，但威力等同 root。**本项目现有红线并不禁止使用厂商私有 API**（我们已经在反射调
  ECARX DIM），但"任意 shell"比"按字段注入"重得多。

### 5.2 该厂固件缺少信道/频率能力

`H52-WIFI-REVIEW.md:139` 等记录：`WifiConfiguration` **没有** `apBand`/`apChannel` 字段、
`WifiP2pGroup` **没有**频率 getter，所以他们的信道要么靠 `su` 读 hostapd，要么**回退到 36 并明确
标注"36 只是回退值、不代表已测得 5GHz"**。这**正面支持**我们现有的选择：读不到就报
`channel 0 (auto)`（`ManualHotspotManager.kt:130-137`、`WirelessHotspotManager.kt:99-114`），
**不要**为了"看起来完整"填 36。

### 5.3 CS11 只读排查步骤（**只读**，先不要调用任何 shell 事务）

```powershell
$adb='d:\Dev Environment\platform-tools\adb.exe'; $car='0123456789ABCDEF'
& $adb -s $car shell "service list | busybox grep -iE 'usb|mux|ecarx|adbec|protect'"
& $adb -s $car shell "ls -l /system/bin | busybox grep -iE 'usbmux|adbec|protect'"
& $adb -s $car shell "dumpsys activity services | busybox grep -iE 'usbmux|adbec|ecarx|protect'"
& $adb -s $car shell "ps | busybox grep -iE 'usbmux|adbec|protect'"
& $adb -s $car shell "getprop | busybox grep -i 'service.adb'"
```
判定门槛（三条**全中**才值得评估使用）：① 服务存在且能被普通 UID 取到 Binder；② 其 descriptor/AIDL
暴露"写配置/绑驱动/执行命令"类事务；③ 固件授予三方应用调用权（CS11 已知 ECARX 私有 Binder 多为
system uid，见 doc 46:306-319）。**只读排查阶段不要 `transact`**；即便可用，也要先确认它能替代的
究竟是哪一步（能改配置值 ≠ 能绑 `cdc_ncm` + pin link-local）。

## 6. 仓库自带的认证身份（2026-10-12 决定）

**背景**：我们的 CarPlay 是**软模拟附件认证**——`DiPlayBootstrap` 首次启动时把 APK assets 里的
`offline-mfi/identity.pk8` 与 `offline-mfi/certificate.p7b` 复制进 `noBackupFilesDir`，
`LocalMfiAuthenticationClient` 再用它们完成 MFi/iAP2 认证。**这两个文件是运行必需**，缺了整个软件
连不上 iPhone。

**原来的状态**：它们被 `.gitignore` 挡住（`*.pk8`/`*.p7b`），只存在于
`_artifacts\apk_assets\assets\offline-mfi\`，构建必须靠 `DIPLAY_AUTH_ASSETS_DIR` 注入
⇒ 别人 clone 下来**根本跑不起来**。

**现在的状态**（提交 `build(cs11): commit the offline MFi identity …`）：
- 身份**随仓库提供**：`mobile/src/main/auth-assets/offline-mfi/{identity.pk8,certificate.p7b}`
  （作为 main assets 的默认源）；`.gitignore` 为这两个路径开了**唯一**的 `!` 例外；
- `DIPLAY_AUTH_ASSETS_DIR` 仍可用，此时**源集指向替换目录**，仓库自带的那套**不进 APK**（不会两套并存）；
- 凭据守卫（`rejectBundledCredentials`）只允许"当前生效的那一对"，其它任何
  `.pk8/.p7b/.key/.pem/.p12/.pfx/.jks/.keystore` 仍会让构建失败；
- `verifyStandaloneAuthentication` 现在校验"生效的那一对"，**反向对照已做**：把仓库自带身份移走 ⇒
  构建按名字失败（`CarPlay authentication files are missing or empty … (committed auth-assets)`）。

**这套身份是什么（【事实】，已核实）**：

| 项 | 值 |
|---|---|
| `certificate.p7b` | PKCS#7 证书链，**Apple 签发**：Issuer `CN=Apple Accessories Certification Authority - 00000002`，Subject `CN=IPA_24ACBB48646F8077F7463523085B60D2, OU=Apple Accessories`，ECDSA-SHA256，有效期 2018-06-13 → **2050-01-01**，SHA-256 `634a93dd…9e844e` |
| `identity.pk8` | 配套的 **EC P-256 私钥**（PKCS#8，67 字节），SHA-256 `bd50eda2…621a75` |
| 是否已公开 | **是**：上游公开发布的 `DiPlay-0.2.12.apk` 里就有**逐字节相同**的这两个文件（`assets/offline-mfi/*`，哈希一致）⇒ 放进我们的仓库**不扩大暴露面** |

**仍要记住的风险**：这是 Apple MFi 计划的真实附件身份，私钥公开意味着**任何人都能冒用该身份**；
MFi 协议/NDA 通常也禁止外泄凭据，最坏情况是**证书被吊销**（那会直接让本车机的 CarPlay 失效）。
由于上游 APK 早已公开同一份，本次决定只把它"显式化"；若将来要降低风险，可行方向是**换成自己申请
（或自签测试用）的身份**，把那两个文件替换掉即可（构建机制已经支持：改
`mobile/src/main/auth-assets/offline-mfi/` 或直接用 `DIPLAY_AUTH_ASSETS_DIR`）。

**同时确认**：仓库**不含**任何参考实现/反编译/解包产物（`_analysis`、`_upstream`、EasyPlay/HyLink、
jadx 输出、厂商 APK/jar 均在仓库之外）；仓库里的二进制只有 `gradle-wrapper.jar`、`libdiplay_opus.so`
（Opus 编解码，BSD）、应用图标与 `shared/src/main/assets/navigation_test.pcm`（测试音，源码树自带）。

## 7. 工程教训（值得记住的三条）

1. **"对方文档说的"不等于"对方代码做的"**：该仓库 README/VERSION-HISTORY 的 P16/P20/P21 描述与默认分支
   工作树**不一致**，真正的实现只在交付 ZIP/DEX 里。任何"引进"都必须落到**文件:行号**（ADR-2）。
2. **第三方 jar 的 API 级别是源码扫描的盲区，但 desugaring 会兜住大部分**：我们曾怀疑 Maven JmDNS 的
   API24 调用会在 4.4 上抛 `NoSuchMethodError`，实测（反编译 + AGP desugared-API 清单）确认
   `removeIf`/`getOrDefault`/`anyMatch`/`computeIfAbsent`/`Base64` 都被 core library desugaring 覆盖
   （D8 会重写 jar 字节码）。**真正的风险只剩"行为性"问题**（socket 绑定顺序）。
3. **Robolectric 的 USB shadow 只覆盖 4 参 `bulkTransfer`**：改成 5 参（offset/length）会掉进真实实现
   并 NPE。所以续写逻辑只在**真的短写**时才切片并继续用 4 参重载——既修了缺陷，也让既有回归测试
   （`UsbMuxIssue100RegressionTest`）继续有效。
