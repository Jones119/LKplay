## 1. 总览

DiPlay 的"安全与身份"实际是三套互相独立、用途不同的密钥/身份体系：

| # | 体系 | 身份载体 | 用途 | 存储/来源 |
| --- | --- | --- | --- | --- |
| A | **MFi 配件身份**（P-256 / RSA-BAA） | `offline-mfi/identity.pk8` + `certificate.p7b`，或硬件 I2C 协处理器，或远程签名服务 | iAP2 CSM 认证（0xAA00–0xAA05）与 AirPlay `/auth-setup`（MFiSAP）；向 iPhone 证明"Apple 授权的配件" | 三选一：APK assets（构建注入）/ I2C 芯片 / 远程 HTTP 服务 |
| B | **AirPlay 长期身份**（Ed25519） | App 首次运行自生成（`AirPlayIdentity.generate()`） | pair-setup 中交换的配件长期身份；pair-verify 签名与验证 | `SharedPreferences` hex（`AirPlayPersistence.loadIdentity`） |
| C | **Lockdown 主机身份**（RSA-2048 自签根/主机/设备证书） | 配对时本地生成（`LockdownPairRecordGenerator`） | USB 有线路径的 iOS Lockdown 配对、StartSession/StartService 的 TLS 客户端证书 | `SharedPreferences` hex（`AirPlayPersistence.loadLockdownRecord`） |

三条结论先行：
1. 源码与 CI **不含任何身份资产**；`DIPLAY_AUTH_ASSETS_DIR` 外部注入两个文件进 APK assets（`mobile/build.gradle.kts:7-8,26`；`docs/BUILD.md:15`），并有拒绝意外凭据文件的守卫任务。
2. MFi 身份的性质：发布 APK 打包的是**从公开 Carlinkit C2Air 固件回收的配件证书/密钥**（`docs/THIRD_PARTY_NOTICES.md` "Experimental authentication data" 一节），不是 Apple 为 DiPlay 签发的身份；文档明确"持续可接受性与适合一般分发尚未解决"。
3. 加密实现全部可盘点：BouncyCastle 只用于 X25519 / Ed25519 / ChaCha20-Poly1305 / HKDF / SHA-512 与两处 ASN.1；SRP-6a 为自实现 BigInteger 版本；AES 只有 AES-128-CTR（`/auth-setup` 的签名加密）；**无 FairPlay 实现**（仅判定"不支持"并跳过）。
4. 无线路径（RFCOMM iAP2 bootstrap + Wi-Fi AirPlay）**不使用 Lockdown**；Lockdown 仅在有线 USB 路径（`CarPlayController.kt` 的 wired runStack）出现。

## 3. 三条 MFi 路径逐一分析

选择逻辑：`MfiTarget` 四值枚举（`CarPlayRuntimeConfig.kt:14-19`），运行时在 `CarPlayController.startMfi()` 分派（`CarPlayController.kt:755-784`）。其中 USB_CH341 与 I2C 都属"硬件 I2C 协处理器"机制，只是传输不同：

| MfiTarget | 机制 | 入口 |
| --- | --- | --- |
| `LOCAL` | 离线软件身份（offline-mfi 文件） | `openLocalMfi` `CarPlayController.kt:786-804` |
| `USB_CH341` | 硬件协处理器，CH341 USB-I2C 桥 | `checkCh341Mfi`/`openCh341` `:829-972` |
| `I2C` | 硬件协处理器，板载 `/dev/i2c-N` | `openLinuxMfi` `:840-860` |
| `REMOTE` | 远程 HTTP 签名服务 | `openRemoteMfi` `:806-827` |

持久化默认值：**缺省 LOCAL**（`AirPlayPersistence.kt:239-243`）；设置界面单选 + I2C 路径/远程 URL+Token 输入（`CarPlayHostActivity.kt:2100-2231`，键名 `AirPlayPersistence.kt:93-96`）。配置校验：USB_CH341 必须配 CH341 设备 ID、I2C 必须配路径、REMOTE 必须配服务器地址（`CarPlayRuntimeConfig.kt:83-91`）。

### 3.1 硬件 I2C 协处理器（USB_CH341 与 I2C）

- **探测**：候选地址 `[0x10, 0x11]`，先写寄存器 0x00（选寄存器、STOP）再单独读 1 字节，丢弃 0x00/0xFF（`MfiDeviceScanner.kt:9-11,24-59,107-116`）；启动探测超时 15s（`MfiRuntime.kt:40`），单个扫描默认 2s。CH341 路径在 `MfiRuntime.scan` 之后**额外探测两份地址**的寄存器 0x00/0x01/0x02/0x30/0x50，并优先选择"带 accessory 证书"的地址（`CarPlayController.kt:941-949,1001-1049`）。
- **寄存器协议**：`MfiAuthenticationClient.kt` —— 协议版本 0x02、错误 0x05、控制/状态 0x10、响应长度 0x11/数据 0x12、挑战长度 0x20/数据 0x21、证书长度 0x30/数据 0x31（:227-235）；读证书按 128 B 窗口（:236,75-80）；签名流程：写挑战（1..128B）→ 0x10 写 0x01 启动 → 轮询 0x10==0x10 → 读 0x11/0x12（:90-120）；I/O 重试 2s、初始延迟 10ms、认证超时 3s（:241-245）。全程 `synchronized(COPROCESSOR_LOCK)`（:223）——即全局单实例串行。
- **CH341 运行细节**：权限（USB 广播 + 轮询兜底，`CarPlayController.kt:862-921`）、可选 MFi 复位 GPIO 脉冲 D0..D5（`:934-939`；`CarPlayRuntimeConfig.kt:49,92-94`）。
- **失败语义**：找不到芯片 → `MfiCoprocessorNotFoundException`（可重试），进入 `WaitingForMfi` 轮询（`CarPlayController.kt:1051-1061`）；I2C 打开失败 → 直接 fail。
- **运行前提（CS11 待验证）**：Android 4.4 的 USB Host 权限流程不同（API 19 无 `UsbManager.hasPermission` 的现代语义？其实存在），以及 `/dev/i2c-N` 对普通 App 的可访问性——CS11 上均需实测。

### 3.2 离线软件身份 offline-mfi（LOCAL）

- **目录与文件**：私有 `noBackupFilesDir/offline-mfi/`，固定两个文件：`identity.pk8`（PKCS#8 EC P-256 私钥）、`certificate.p7b`（单张 X.509 配件证书）（`LocalMfiAuthenticationClient.kt:43-46`）。
- **加载校验**（`:48-76`）：文件 ≤16KB；证书恰好 1 张；公钥必须是 P-256（比对曲线阶常量 :62-65）；用 `NONEwithECDSA` 做一次"私钥↔证书"自洽签名验证（:66-74）。
- **签名行为**（`:32-41`）：只接受 **32 字节摘要**（调用方已哈希，禁止二次哈希）；`NONEwithECDSA` 出 DER 后转 64B raw r‖s（:90-103）；`protocolMajor()` 硬编码 **3**（:23）。
- **失败封闭**：local 身份损坏时直接 fail，**不会回退**到硬件/远程（`CarPlayController.kt:799-801` 注释与逻辑）。
- **assets→私有目录安装**：`DiPlayBootstrap.ensure`（`DiPlayBootstrap.kt:14-42`）仅当 `MfiTarget.LOCAL` 时；staging 目录先收紧权限，复制两个文件→`load` 校验→`renameTo` 原子落地；失败即抛异常（测试 `DiPlayAuthenticationTest.kt` 覆盖"USB 选择不被本地坏身份影响"等）。
- **构建注入**：`DIPLAY_AUTH_ASSETS_DIR` → `sourceSets.main.assets.srcDir`（`mobile/build.gradle.kts:7-8,26`）；`rejectBundledCredentials` 只允许这两个文件路径（:85-98），任何其它 `*.pk8/*.p7b/*.key/*.pem/*.p12/*.pfx/*.jks/*.keystore` 会构建失败；`assembleStandaloneDebug` 要求两文件非空（:102-120）。`docs/BUILD.md:11,23` 说明：源码/CI APK 无身份；release APK 故意含实验身份且"可被接收者提取"。
- **身份注记（不涉字节）**：身份来源为公开 Carlinkit C2Air（全志 V821）固件回收件；Git 忽略 `*.pk8/*.p7b`（`.gitignore:34-35`），仓库内无任何身份文件（已核）。
- 另有本地自检工具 `LocalMfiProbe.kt`（两次启动 × 三次签名验证 + 篡改摘要拒绝），测试材料为**运行时合成**（`LocalMfiAuthenticationClientTest.kt:33-56` 现场生成 EC 密钥与自签证书，不落盘仓库）。

### 3.3 远程签名服务（REMOTE）

`RemoteMfiAuthenticationClient`（`RemoteMfiAuthenticationClient.kt`）：

- **配置项**：`serverAddress`（必须以 `http://` 或 `https://` 开头，:41-43）、`token`（Bearer，:224）、`connectTimeoutMillis=5s`、`readTimeoutMillis=10s`、`maximumAttempts=2`（:282-284）。
- **接口**（:278-280）：`GET /mfi/certificate`（返回 `protocolMajor`、`type`(mfi|baa)、`certificate`(base64)、`certificateSha256`(hex)）；`POST /mfi/sign`（`{challenge, requestId}` → `{signature}`）；`POST /mfi/reset`。
- **行为**：证书响应**缓存**（:37,109-161）；校验 SHA-256 摘要绑定（:134-138，`MessageDigest.isEqual`）；挑战 1..128B、Base64 编码、requestId 为 UUID（:94-99）；响应上限 65535B（:287）、HTTP 体上限 2MiB（:288）。重试只对超时/429/5xx（:272-275），`reset` 不重试（:56,194）。
- **BAA 分支**：`type=baa` 时证书是"8 字节头(u32 leaf 长度+u32 intermediate 长度)+leaf+intermediate"包（:164-179），再经 `Iap2AuthenticationMessages.baaCertificatePackage` 包装为 0xAA01 参数序列（`iap2/message/Iap2Messages.kt:228-240`）。
- **运行时**：`openRemoteMfi` 先 `reset()` 再读 `protocolMajor()` 才算就绪（`CarPlayController.kt:806-827`）。
- **安全观察**：明文 `http` 被允许（挑战/证书/token 走网络）；无证书固定、无 HMAC 请求签名——协议本身只有 Bearer 可鉴权。**建议 CS11 端口强制 https 或仅本机回环**。服务端实现不在本仓库（仅接口文档 `docs/UPSTREAM-README.md:60-84`）。

## 5. 配对 / 鉴权流程细节

### 5.1 AirPlay pair-setup（SRP-6a，不依赖 MFi）

- 起手：M1 由手机发；配件回 M2（salt + 公钥 B）（`PairSetup.kt:34-44`）。M4 验证客户端证明并回服务器证明（:46-60；证明公式 `Srp6a.kt:82-109`）。
- M6：用 HKDF(key, `Pair-Setup-Encrypt-Salt/Info`) 派生 ChaCha 密钥，nonce `PS-Msg05` 解密手机子 TLV；校验手机 Ed25519 签名（签名数据含 `Pair-Setup-Controller-Sign-Salt/Info` 派生键）→ **把控制器 LTPK 存入 PairingStore**；再用 `PS-Msg06` 封装配件身份回包（:62-106）。
- 密码学性质：口令固定 `3939`，且注释自述 **unauthenticated SRP**（:6-8）——配对阶段依赖手机端用户确认/首次信任，而非保密口令。

### 5.2 AirPlay pair-verify（不依赖 MFi）

- M2：配件生成临时 X25519，收到手机临时公钥后：共享密钥 → HKDF(`Pair-Verify-Encrypt-Salt/Info`)；签名数据 = 临时公钥 ‖ 配件 ID ‖ 手机临时公钥（`PairVerify.kt:42-72`）。
- M4：解密手机子 TLV，按 controllerId 查 PairingStore 的 LTPK，验证 Ed25519；通过后派生 **控制读写键**（HKDF `Control-Salt` + `Control-Read/Write-Encryption-Key`）（:74-102）。
- 加密启用点：`AirPlaySession` 在**下一次写响应时**检测到 `pairVerify.controlKeys` 才启用 `ControlCipher`（`AirPlaySession.kt:504-509`）——即 pair-setup/pair-verify 本身走明文 RTSP，之后同一连接自动加密。
- 事件信道（HID/命令回传）：独立 TCP 端口，要求 `pairVerify.shared` 存在，键 = HKDF(`Events-Salt`, `Events-Read/Write-Encryption-Key`)（`AirPlaySession.kt:812-878`）。
- **观察（待验证）**：`handle()` 内没有"必须已验证"的门禁——未配对连接也可直接打 `/info`、`/command`、`/feedback` 等（`:523-601`）；只有事件信道强制校验 shared 秘密。实际风险取决于手机行为，移植时应评估是否加门禁。

### 5.3 /auth-setup（MFiSAP，**依赖 MFi**）

- 请求 = `[1B 版本=1][32B 手机 X25519 公钥]`；响应 = 配件临时公钥 + MFi 证书 + `AES-128-CTR` 加密的协处理器签名（`MfiSapAuthSetup.kt:12-16,25-67`）。
- 摘要规则：MFI 类型时 protocolMajor==2 → SHA-1(pub‖peer)，否则 SHA-256(pub‖peer)（:39-43）；**BAA 类型签原始拼接**并在响应尾部附 OPACK `{"baIC": intermediate}`（:52-65,108-159）。
- 无 MfiAuthenticator 时返回 400（`AirPlaySession.kt:556-559`）→ **CarPlay 会话强依赖 MFi**（至少在有线/官方手机行为下）。

### 5.4 iAP2 CSM MFi 认证（**依赖 MFi**）

- 交换：手机 `0xaa00` 请求证书 → 配件 `0xaa01`（MFI 证书或 BAA 包体）→ 手机 `0xaa02` 挑战 → 配件签名 `0xaa03` → 手机 `0xaa05` 成功（失败 `0xaa04`）（`Iap2MfiAuthenticationClient.kt:28-69`，常量 :103-109）。
- 证书/挑战上限 65525 / 128 字节；等待默认 30s（:110-113）。
- 注入点：有线 `CarPlayController.kt:2008`、无线 bootstrap `:1371`、无线隧道 `:1465`；消息清单见 `Iap2IdentificationClient.kt:301-341`（我方发送 0xaa01/0xaa03，接收 0xaa00/0xaa02/0xaa04/0xaa05）。

### 5.5 iOS Lockdown 配对（有线 USB 专用，**不依赖 MFi**）

- 流程（`LockdownPairingClient.kt:27-86`）：USBMUX 连 **62078** 端口 → `SetValue UntrustedHostBUID`（:125-147）→ `GetValue DevicePublicKey / WiFiAddress`（:149-171）→ 本地生成记录 → `Pair`（含 `PairRecord` 字典：DeviceCertificate/HostCertificate/HostID/RootCertificate/SystemBUID；ProtocolVersion=2；ExtendedPairingErrors）（:110-123）→ 处理 `PairingDialogResponsePending`（等用户在手机上点信任，1s 重试）/`UserDeniedPairing`/`PasswordProtected`（:73-85,220-227）。
- **记录结构**（`LockdownPairRecord.kt:26-62`）：`hostId`、`systemBuid`、`wifiMacAddress` + 6 个 PEM（devicePublicKey、deviceCertificate、hostPrivateKey、hostCertificate、rootPrivateKey、rootCertificate）；`toString()` 已脱敏；`EscrowBag` 只存在于内存 `PairedRecord`（`LockdownPairingClient.kt:74,230-241`），不持久化、不随 Pair 请求发送（`LockdownPairRecord.kt:51`）。
- **存储**：`AirPlayPersistence.saveLockdownRecord/loadLockdownRecord`（`AirPlayPersistence.kt:889-940`）——所有 PEM 以 hex 存 SharedPreferences；损坏时静默返回 null 重新配对。
- **会话**：`StartSession`（必回 `EnableSessionSSL=true`）→ TLS 客户端引擎 → `StartService com.apple.carkit.service`（`LockdownCarKitClient.kt:25-105`）。TLS 引擎用记录里的 **root 私钥/证书**作客户端身份，且**不校验对端证书**（`LockdownTlsEngineFactory.kt:27-31,90-97`）。
- **ValidatePair：仓库中不存在该请求**。等效校验发生在使用侧：把 `StartSession`/`StartService` 的错误串当作判据，命中 `InvalidPairRecord`/`InvalidHostID` 就清记录重新配对（`CarPlayController.kt:1919-1922,2043-2049`）。
- 诊断后门：有线建链时会额外打开 `com.apple.syslog_relay` 抓 2 分钟电话侧认证日志（`CarPlayController.kt:1886-1910`，仅调试用途，移植时可裁）。
- 与 MFi 的关系：Lockdown 是 USB"主机信任"通道；CarPlay 的 CarPlayStartSession 经 iAP2（CSM），MFi 认证也走 iAP2——两条线并行、互不替代。

### 5.6 版本协商与依赖汇总

- **不依赖 MFi**：Bonjour 广播（`deviceid/features/srcvers/pi/pk`，`CarPlayBonjour.kt:84-95`）、pair-setup、pair-verify、`/info`（`sourceVersion`+64 位 `features`，`AirPlayInfoPlist.kt:28-40`）、stream SETUP/TEARDOWN、事件信道、NTP。
- **依赖 MFi**：`/auth-setup`（会话内）、iAP2 0xAA00 序列（CarPlayStartSession 前置）、BAA 变体。
- 版本面：AirPlay 用 `sourceVersion`+`features` 位（无线 TXT 用 `featuresTxt`）与 `protovers 1.1`（`CarPlayBonjour.kt:91`）；iAP2 侧 `IdentificationInformation` 上报 6 元组（含固件/硬件版本，`Iap2IdentificationClient.kt:43-44,219-220`）；MFi 协议主版本三路径来源不同：硬件**读寄存器 0x02**、LOCAL 硬编码 3、REMOTE 由服务端下发——`/auth-setup` 据此在 SHA-1/SHA-256 间选择。

## 6. CS11 适配观察（API 19）

### 6.1 风险清单（按严重度）

1. **BouncyCastle 1.79 与平台 BC 的类遮蔽（最高风险，待验证）**：Android 4.4(API 19) 引导类路径带有平台自带的裁减版 BC，历史以 `org.bouncycastle.*` 命名，与 App 内捆绑的新版 BC 存在著名的类加载冲突（SpongyCastle 重打包即为此而生；后续 Android 把平台副本改名 `com.android.org.bouncycastle` 后才缓解，改名发生的具体版本边界本次未确证）。因此 App 内同包名的 BC 1.79 类**可能**被平台旧版遮蔽 → `X25519*/Ed25519*/ChaCha20Poly1305/HKDFBytesGenerator` 等可能 `NoClassDefFoundError/NoSuchMethodError`。涉及 `airplay/AirPlayCrypto.kt:3-14`、`mfi/LocalMfiAuthenticationClient.kt:3-9`、`mfi/LocalMfiProbe.kt:8-9`。规避方向：SpongyCastle 式重打包、或集中替换（`AirPlayCrypto.kt` 是唯一 BC 加密入口，见 §6.2）。**必须先在 4.4.3 实机/模拟器验证**。
2. **TLS 1.2：API 19 的 SSLEngine 不支持 TLS 1.2（官方文档：SSLEngine 的 TLS1.1/1.2 支持自 API 20 起；SSLSocket 自 API 16 起可用）** → `TlsDuplexChannel.kt:392` 的 `ALLOWED_PROTOCOLS=[TLSv1.3, TLSv1.2]` 在 API 19 会得到空集并在 :411-415 抛 "TLS engine supports neither TLSv1.2 nor TLSv1.3" → **有线 Lockdown/carkit 链路在 4.4.3 直接失败**。候选修法：改为 SSLSocket（API16+ 可显式启 TLSv1.2）或在 native 层自持 TLS（代价高）。还需确认 iPhone 端 lockdown 是否强制 TLS1.2+（**待验证**）。
3. **`java.util.Base64`（Android API 26+）**：安全域内 4 处——`mfi/RemoteMfiAuthenticationClient.kt:9,95,258`、`transport/LockdownPairRecord.kt:16,302,320`、`transport/LockdownPlistChannel.kt:7,217,252`、`transport/LockdownTlsEngineFactory.kt:12,67`（另 `adb/AdbKeys.kt:17`、`airplay/VideoInCar.kt:4`、`hud/BydCarPlayCall.kt:364`、`hud/BydClusterSong.kt:328`）。当前工程**未启用 core library desugaring**（`shared/build.gradle:30-33`、`common/build.gradle.kts:16-19` 都只有 Java 11 源/目标）→ 移植需开 desugaring 或换 `android.util.Base64`。**必改项**。
4. **`AES/CTR/NoPadding`**（`MfiSapAuthSetup.kt:172`）：预期 API 19 可用（AndroidOpenSSL/平台 BC 均提供），实机确认。
5. **JCA 基础件**（预期可用，实机确认）：`KeyFactory("EC")`、`Signature("NONEwithECDSA")`、`CertificateFactory("X.509")` 读 p7b、`SHA256withRSA`、`KeyManagerFactory("PKIX")`、`KeyStore.getDefaultType()`（4.4 上是 BKS）——分别见 `LocalMfiAuthenticationClient.kt:35,52,57`、`LockdownPairRecord.kt:247,308`、`LockdownTlsEngineFactory.kt:39-45`。
6. **TLS 密码套件默认集差异（待验证）**：API 19 默认启用套件偏旧（GCM/部分 ECDHE 可能不在）；`TlsDuplexChannel`/`LockdownTlsEngineFactory` 未显式 `enabledCipherSuites`，移植时应固定一套 iPhone 接受的套件。
7. **远程 MFi 允许明文 http**（`RemoteMfiAuthenticationClient.kt:41-43`）：CS11 移植建议收敛为 https 或回环。
8. 本笔记只列"安全/身份"相关问题；Compose/appcompat/Media3 等 UI 依赖阻塞见 07d。

### 6.2 可简化点（利于 CS11 端口）

- **三选一收敛**：若采硬件协处理器（CS11 需有 I2C 芯片）就删 LOCAL/REMOTE；若采离线身份就删硬件探测与远程客户端。两条硬件传输（CH341 vs 板载 I2C）也只保留 CS11 实际所需的一条。
- **BC 依赖集中**：加密原语只从 `AirPlayCrypto.kt` 进入（唯一 import 面），替换成本低；先做 §6.1-1 的验证，再决定"重打包 BC / 换实现"。
- **Lockdown 可替换复用系统 usbmuxd**：CS11 自带 usbmuxd 时，`Iap2UsbMuxHost`（自研 USB 栈）可换成 socket 客户端，安全侧只需保留 `LockdownPlistChannel` + `LockdownPairingClient` + `LockdownCarKitClient`（07a 决策）。
- **无线优先则整套 Lockdown 可裁**：无线路径无 Lockdown 调用（已核：`LockdownPairingClient/LockdownCarKitClient` 仅在 `CarPlayController.kt` 有线链路使用）。
- **密钥落盘**：当前三种身份/密钥均以 hex 明文存 SharedPreferences（`AirPlayPersistence.kt:853-940`）；API 19 无硬件 Keystore，可维持现状但应在移植文档中注明风险与边界。
- 调试期功能（syslog_relay 抓日志、逐 256B 分片 TX、trace 全量 hex 日志）在移植时建议裁剪。

## 7. 未决问题

1. **平台 BC 遮蔽在 4.4.3 的真实行为**：需实机（或 4.4 模拟器）跑改造版 `LocalMfiProbe`，确认 `org.bouncycastle.crypto.*` 解析到 App 内 1.79 还是平台旧版（待验证，优先级最高）。
2. **API 19 SSLEngine 实测**：文档说 TLS1.2 自 API 20；需真机确认 `supportedProtocols` 到底含哪些（待验证）。若确无，评估 SSLSocket 化改造量。
3. **iPhone 端最低 TLS 版本**：Lockdown/carkit 是否接受 TLS1.0/1.1（决定 API 19 有线路径是否存在"文档外"的可用组合）（待验证）。
4. **`/auth-setup` 是否在所有场景强制**：无线/有线、不同 iOS 版本是否都要求 MFiSAP？若恒强制，CS11 必须落地方案 A 的某一路径（待验证）。
5. **`/fp-setup` 空 200 的后果**：对非 DRM 媒体是否完全无影响（`AirPlaySession.kt:599`）（待验证）。

7. **未配对连接的门禁缺失**：`/info`、`/command` 等在 pair-verify 之前可被服务（`AirPlaySession.kt:523-601`）；是否需要补"已配对"检查，需结合 iPhone 行为评估。
8. **远程 MFi 服务端**：不在仓库，部署与凭据强度未知；`docs/UPSTREAM-README.md:60-84` 仅有接口描述（待补）。
9. **BAA 通道的适用性**：BAA 证书类型何时被 iPhone 接受（Showcase/模拟器口径？）未确认（`Iap2MfiAuthenticationClient.kt:29-32`、`MfiSapAuthSetup.kt:52-65`）（待验证）。
10. **EscrowBag 缺失的影响**：未持久化（仅内存）是否影响后续重新配对的某些 iOS 版本流程（待验证）。
