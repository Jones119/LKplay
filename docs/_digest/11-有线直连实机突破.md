# 11 · 有线直连实机突破实录（CS11 × iPhone × DiPlay-CS11）

> 日期：2026-10-06 ｜ 设备：领克03 CS11（无 root，Android 4.4.3 / API19）＋ iPhone（USB2 口，config 6）
> 应用：`com.shihab.diplay.hudtest`（DiPlay-CS11 自编译 standalone 版）+ `com.android.vpndialogs`（自造替身）
> 结论：**有线"控制通道"在真机上全链路打通且实时运行**（USB→usbmux→lockdown 配对→Conscrypt TLS→iAP2 CSM→MFi 认证通过→iPhone 确认 CarPlay 会话）；**媒体通道（AirPlay 视频流）因车机硬件/系统限制（无 TUN、无 root、无能力位）走不了 USB-NCM，锁定新路线：有线引导→Wi-Fi 媒体**（App 内已有全套无线握手实现）。

## 1. 已打通的链路（含精确实证）

## 2. 为 4.4 做的关键改造（真机验证过）

| # | 问题 | 解法 |
|---|------|------|
| 1 | 4.4 无 UsbConfiguration 枚举(21+) | 活动配置检查：`UsbDevice#getInterface`（API12）遍历，要求 **USBMUX+NCM 同时存在** 才就绪 |
| 2 | 无法 setConfiguration | 用厂商请求(0x52/idx4)让 iPhone 自行切 config 6 |
| 3 | usbmux 接口直取 | `activeUsbMuxInterface()`；真机认领成功（系统 usbmuxd 崩溃循环不挡路） |
| 4 | NCM alt0 无端点/alt1 才有 | 数据接口搜索"带 bulk 端点对者"；`bulkEndpoints` firstOrNull 放松（真机：6.3/6.4 认领 ok=true） |
| 5 | 4.4 无 setInterface(21+) | **controlTransfer 发标准 SET_INTERFACE(0x0B) 到全部 0x0a 数据接口**（真机：iface=4/6 → 0 成功） |
| 6 | **本 ROM SSLEngine 仅 TLSv1/SSLv3** | **打包 Conscrypt 2.5.2**（armeabi-v7a 原生库）；真机实证 `supported=TLSv1…TLSv1.3` |
| 7 | 无 VPN 确认对话框（ROM 裁剪） | 自造 **`com.android.vpndialogs` 替身**（见 §4） |
| 8 | VPN consent ActivityNotFound | 捕获降级 + 替身后不再触发 |

## 3. 媒体通道为什么走不了 USB-NCM（代码级死路，三连实锤）

1. **VPN/tun**：`E/VpnJni: Cannot allocate TUN: Bad file number`；`/dev/tun` 不存在、`/proc/misc` 无 tun → **车机内核根本没编 TUN**。VpnService 方案在内核层死。
2. **内核 usb1（cdc_ncm 自动建卡）**：`usb1` 恒为 DOWN/无 carrier，拉起需 CAP_NET_ADMIN —— 无 root、shell 零能力位（CapBnd=0xc0 只含 SETUID/SETGID）、netd 封锁。
3. **车机自研以太网管理器**（`android.net.EthernetDataTracker`，ASC 反编译实证 `_analysis/cs11_fw/edt.java`）：
   `isTboxIface/isDVRIface` 按 **USB 物理端口路径硬编码**（TBox=`2-1.1`、DVR=`2-1.2`）；iPhone 在 `2-1.4`，**永远不被系统管理**。
   → 系统侧无任何组件会配置 iPhone 的 NCM 网卡。

## 4. `com.android.vpndialogs` 替身（已装机，机制已验证）

- 原理（AOSP 4.4 `Vpn.enforceControlPermission` 为**按包名解析 UID**比对，非签名）：
  ```java
  ApplicationInfo app = pm.getApplicationInfo("com.android.vpndialogs", 0);
  if (appId == app.uid) return;   // ← 我们装上同名包即通过
  ```
- 替身收到 consent intent → 反射 `IConnectivityManager.prepareVpn(null, "com.shihab.diplay.hudtest")` → 记录授权。
- 实证：次轮会话 **不再弹批准框**且 `VpnService.prepare()` 直接放行（授权已记录）。
- 遗留：因无 TUN，establish 仍失败（`Cannot create interface`）；替身保留为资产。
- 源码：`CarPlay-CS11/vpndialogs-stub/`；已提交；⚠️ 仅对 `com.shihab.diplay*` 前缀自动放行。

## 5. 媒体通道新路线：**有线引导 → Wi-Fi 媒体**（下阶段主攻）

App 内已具备全套无线握手实现（`Iap2WirelessControlClient`）：

| 消息 | 作用 |
|---|---|
| `0x5702` | 手机索要 Wi-Fi 配置 |
| `0x5703` | 车机回 SSID/密码/加密 → **手机加入车机热点** |
| `0x4300/0x4301` | CarPlay 可用/开始（4301 携带媒体端点+配对身份） |
| `0x4E0D/0x4E0E` | 无线传输状态/设备传输标识 |
| 识别组 17/24 | 声明 蓝牙+Wi-Fi 传输、SSID（无线形态识别） |
| **type-130 隧道** | 手机经 AirPlay 连接开 iAP2 运行时隧道（`startWirelessTunnelControl` 现成） |
| `attachWireless` | **免 VPN** 在 Wi-Fi AP 地址上起 AirPlay 监听（现成） |

**混合方案（待施工）**：保持现有 USB 控制会话；在识别中追加无线能力（Wi-Fi 组 + ACCESSORY_WIFI_CONFIGURATION_INFORMATION + 无线消息列表）→ 处理 0x5702 回 0x5703（车机热点 192.168.43.1 的 SSID/密码）→ 手机加入热点 → 用 Wi-Fi 端点（192.168.43.1:port）发 0x4301 → setup AirPlay 监听（attachWireless）→ 手机连入并开 type-130 隧道 → 运行时控制/媒体全走 Wi-Fi。
备选：直接跑 App 原有无线模式（BT RFCOMM 引导），前提是车机 nFore 蓝牙栈对标准 `BluetoothSocket` API 可用（待测）。

## 9. 娱乐视频播放能力调研（2026-10 问答存档）

> 问题：「适配好 CarPlay 之后，能播放视频吗？」

**结论分三层：**

1. **"CarPlay 画面本身"**（导航、UI、动效）= 这条链路本来传递的就是 H.264 视频流——媒体通道交付后自然上屏播放（VPU 硬解已就绪）。
2. **娱乐视频 App（YouTube / Netflix / 国内视频站等）**：
   - **旧规则**：标准 CarPlay 不支持任何视频内容（Apple 驾驶安全设计；CarPlay 无"视频 App"类别）。
   - **iOS 26+ 新功能 "Video in the Car"（驻车视频）**：驻车时可通过 **AirPlay** 把视频从 iPhone 投到 CarPlay 屏幕——Apple 支持文档明载：可从"受支持的 CarPlay 视频 App **或任何支持 AirPlay 的 App**"投屏；行车时自动停止（可降级纯音频）；**须"车机侧"启用**（车企集成，关联 MFi 计划）。**我们的自研栈就是"车机侧"**——理论上有机会自实现：需研究 iOS 26+ 的能力协商与 AirPlay 视频流挂接（新协议、资料少；行动=后续阶段用 iOS 26+ iPhone 实测探测）。
   - **越狱路线（当前可用）**：CarBridge（iOS 13–18）/ NGXPlay 等插件让任意 App 上 CarPlay；YouTube 等可用，**Netflix 类 DRM 内容不可用**；车机侧零改动；条件=iPhone 可越狱（取决于机型+系统版本）。
3. **本地视频**（U 盘/车机存储）：装个播放器即可，与 CarPlay 无关，现在就能（车机 64G 存储 + 开放侧载）。

**对项目的定位**：不阻塞主线——先完成控制+媒体通道（CarPlay 基本功能：导航/音乐/电话）；"驻车视频"列为通后研究项（机会点：我们本就是 accessory 侧且带 MFi 身份）。安全建议：若自研实现，仿 Apple 做"驻车才可播"限制（P 挡信号来源待查）。
