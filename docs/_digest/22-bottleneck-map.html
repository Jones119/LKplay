iPhone 发送侧（AirPlay 加密流）⚠️ 突发源（不可控侧）
视频 = TCP + ChaCha20 加密 H.264；音频 = UDP；触控 = iAP 回程。有线持续 3–4.4Mbps，滑动/地图重绘瞬间更高——大接收窗时手机会把多兆突发灌进链路，把音频 UDP 挤掉（"窗口限速点"发现）
可选缓解：协商帧率 30（~-40% 视频负载）· 分辨率降档（像素 -55%）

🧵
USB 线缆 → 控制器中断 🔥 瓶颈 #1 · 已修复 · 最大根因
IRQ 72 = 2,846,638 次中断全挤 CPU0（cpu1/2/3 = 0，IRQ 75 同病）→ 中断补位抖动 → URB 补位迟滞 → NCM 收包迟滞 → 手机 TX 队列溢出丢包
修复：smp_affinity = e（迁 CPU1+2+3，已固化进 bootstrap）→ 丢包 44–61/5s → 2–5/5s（10×），Udp6InErrors 4.4 → 1.3/s
▼
📦
内核：cdc_ncm 驱动（usb1）+ IPv6/UDP6/TCP6 栈 📍 丢包点 A（链路级）
驱动层 0 丢（+23,636 包/60s）；IPv6 层 0 错 0 丢；UDP6 socket = 唯一窟窿：Udp6InErrors +217/60s（3.6/s）；双协议同损（TCP 重传 ~3%）= 链路级 1–3% 均匀损耗
死路已排除：cdc_ncm 无可调 rx_max · 内核未编 usbmon · 双方未实现 RTCP NACK
▼
🚪
应用接收层（ScreenStream 视频 / BufferedAudioStream 音频）📍 丢包点 B · 已节流封边
修复前：大接收窗 → 视频突发挤音频；修复：64KB rcvbuf + TCP_NODELAY（发送端被节拍化）。修复后仍 +246/90s → 反证根不在应用层，在更下层

解密 ChaCha20-Poly1305 🔥 瓶颈 #2 · 已修复
原 = 纯 Java（BouncyCastle），i.MX6 最大单一 CPU 耗电源（视频帧逐帧解密）→ 修复 = Conscrypt/BoringSSL 原生 AEAD（带回退）
实测：交互丢包 4.5/s → 2.0/s（-55%）（NATIVE_TEST +177/90s）；日志实锤 "native ChaCha20 active"
