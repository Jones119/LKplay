## 1. 两链路结构性对照（方案为什么不同）

| 维度 | 有线（USB NCM / 用户态 lwIP 桥） | 无线（车机 Wi-Fi AP） |
| --- | --- | --- |
| 视频 | type110 TCP+ChaCha20，**两侧代码与无线完全相同**（doc51 §9） | 同左；空口是 2.4GHz 共享信道（频段待上机核对） |
| 音频 | type100 **LPCM 134.9pps / 1565kbps**（iOS 强制，不可协商 ADR-13） | type102 **AAC-LC 47.8pps / 252kbps** |
| 音频过路面积 | **2.8× 包率 / 6.2× 码率**（相对无线），与视频突发共用同一条 NCM 队列 ⇒ "有线反而更卡"的结构性原因 | 低负载；卡顿风险来自**空口竞争**而非队列 |
| 额外通道 | USBMUX/lockdown + iAP2 CSM 两条控制通道争带宽 | Bonjour/mDNS + BT RFCOMM（iAP2 无线段） |
| CPU/IRQ 面 | USB IRQ72/75 已迁 CPU1、RPS=2、taskset 0xd（cs11_tune.sh，内存态易失） | WiFi/USB IRQ→CPU1、RPS、app 绑 CPU2-3（cs11_wireless_tune.sh，易失）；CPU0 留给 DIRANA 48kHz 风暴 |
| 已做核心修复 | IRQ 亲和（10×）、原生 AEAD（−55%）、接收窗 16KiB、降 GC 第一批 | type102 AEAD tag 卡顿根治（13511e91）、30fps 定档（recoveries=0）、热点自动化 |
| 最大未决 | **丢包最后一锤**（到内核被拒 vs 没到）；三假设 A/B/C 裁定 | 60fps 不可达的确切瓶颈；音频丢包无系统性数据 |

**推论**：三目标中——
- **音质**：有线要"治队列挤占+钉死归因"，无线要"治空口突发+验证基线"；
- **帧率**：两边都是 30fps 打满、60fps 是同一台 SoC 的同一道墙，突破顺序 = 先消抖动再摸上限；
- **触控**：app 层病灶相同（拼包分配/共享队列/锁），无线额外叠加空口 RTT。

## 2. 有线方案

### 2.1 音质稳定不丢包

**现状**：永久缺包 0.42%、缺口成串（均 6.5 包、最大 34 包 ≈ 1–3 个 NTB 聚合帧）、`lateOrDuplicate=0/underruns=0`（ADR-12：**是丢包不是抖动**）；交互期 `Udp6InErrors=+79/160s(0.65%)`，已排除 rxErr/RcvbufErrors/NoPorts/Retrans（doc51 §2）。归因差最后一锤：(a) 到内核被校验拒收 vs (b) 根本没到。

按"先钉死再动手"排序：

| # | 动作 | 机理 | 验收 |
| --- | --- | --- | --- |
| A1 | **【前置】lossprobe4 上车裁定**（工具已就绪未实车出结论，doc54 §2.3/B） | 判读表四分支区分 (a)/(b)，并绕开 NTP 每秒 1 包对 `Udp6InErrors` 的污染 | 一个点火窗口出唯一分支结论，写入 doc；**决定 A2/A3 谁是主攻** |
| A2 | 若 (a) 内核拒收：**收包侧全局旋钮 A/B** —— `rps_cpus 2→4/8`、`netdev_budget 300→600`（doc51 §6 P2，未做；ADR-16 教训=必须带数据，不拍脑袋改回） | 把 UDP 处理从被打满的收包核分流/增加每次软中断处理预算 | 交互期 `Udp6InErrors` 率对照（交错 A/B、同内容代理） |
| A3 | 若 (b) 没到：**发送侧突发继续压** —— 视频接收窗 `video_rcvbuf` 请求 8KiB(=实际16KiB 已定稿) → A/B 4KiB(=8KiB)：doc51 §5.3 单调好（dropped 28→17、maxGap 331→239ms），代价是吞吐上限需确认 | 更小的 TCP 接收窗反压 iPhone 的拥塞窗口 ⇒ 视频突发变平 ⇒ 给音频 UDP 让出 NCM 队列 | UDP 丢包率 ↓ + `kbps`/shown 不降 + `maxGap` 不劣化 |
| A4 | **CPU 面回收**（doc51 §6 P0，未做）：关车机「语音唤醒」「应用商店自动更新」（0.3–0.7 核）；app 绑核 0xd→**0xc**（CPU1 留给 IRQ/RPS，app 只用 2-3）；关 `debug.diplay.trace` | 交互期 CPU1 `irq+sirq` 尖 57% 是丢包窗口的重合因素；给收包核让出余量 | 交互期 CPU1 峰值 ↓、`Udp6InErrors` 率 ↓ |
| A5 | **消 GC STW 落在音频写**：doc69 P0-2（rtp 每包新数组池化，有线 135pps≈27KB/s）+ doc41 §2.1b（AAC 解码与 AudioTrack 写剥离——有线 LPCM 无解码，主要是写线程独立） | Dalvik STW 37–67ms 落在音频写路径=瞬间断流 | `alloc=` 降、`underruns` 保持 0、`maxWriteMs` 峰值 ↓ |
| A6 | **lwIP 桥 RX 拓扑核查**（若 A1 指向桥内）：`Ntb16Codec.parse copyOfRange → JNI → pbuf_take → socket读` 每帧 4–5 次拷贝 + `TCP_WND=16KiB`；检查 64×1600B pbuf 池是否交互期耗尽 | 成串缺包 ≈ 1–3 NTB ⇒ 怀疑 NTB 聚合/拆分环节的丢弃 | pbuf 池命中率/丢帧计数（lwIP_STATS 暂开）→ 定点修 |
| A7 | doc54 挂账 **A5：NCM RX 旋钮**（交互期 rx_queue/softnet 观测）与 `netdev_max_backlog`（现 4000）联动 A/B | 链路→软中断队列的溢出口 | 同 A2 口径 |

**明确不做**：应用层加大缓冲（ADR-12 实测无效——丢包不是抖动）；音频格式协商（ADR-13 两侧已判死）。

### 2.2 视频帧率高（有线）

**现状**：硬解（Freescale hw）、shown P50 33ms 已达 30fps 满帧；问题是 **P95/突发**（迟到丢帧 17–28、maxGap 239–331ms）；车机显示侧 1080p/60Hz 已解除但 1080p 解码被否（CPU 超载），保持 1280×720；应用请求 30fps，有线未试 60。

| # | 动作 | 机理 | 验收 |
| --- | --- | --- | --- |
| B1 | **先收 P95，不急提 fps**：随 §2.1 的 A2–A4 落地，`dropped→0`、`maxGap<200ms` | 当前"帧率高"的短板是突发期掉帧，不是平均帧率 | shownP95、dropped、maxGap 三值 |
| B2 | **解码侧三小项**（doc41 §2.2/2.3、doc69 P1-7）：① PTS 改用 `job.receivedNs`（旧帧不再当新帧上屏，省一次无效渲染）② buildFormat 补 `operating-rate/frame-rate` 键（硬解调度提示）③ BufferInfo 提为字段（每帧 new×2处） | 减少解码→渲染的浪费与分配 | shownP95 微降、`alloc=` 降 |
| B3 | **60fps 突破实验（可选，最后做）**：前置条件 = B1/B2/§2.1 落地且 recoveries=0 稳定；`display_fps 30→60` 请求，观察 `recoveries/queueMax/maxWriteMs/alloc`。同 SoC 无线 60fps 积压教训（doc27）在先 ⇒ **一档一档试（30→40/50→60）**，任何一档 recoveries>0 即回退 | 有线无空口争用、CPU 面比无线干净，理论上限可能更高；但 VPU@720p60 吞吐与 GC 余量未验证 | recoveries=0 持续 10 分钟 + shown≈请求值；失败则记录确切瓶颈（解码/喂帧/GC）回 30 |
| B4 | 渲染：**isOpaque=true**（零风险，doc41 §6）；**不做** TextureView→SurfaceView（doc36/42 黑屏风险，doc51 §6 明确不建议） | 每帧少一次 alpha 混合读 | shownP95 不回退即算通过 |

| --- | --- | --- | --- |
| C1 | **触摸固定布局直写**（doc69 P0-4）：hidSendReport 的 3 键 bplist 结构恒定 → 直写固定布局 + 整帧含 RTSP 头一次成帧；ControlCipher 写入同一缓冲；touchGate.shape 改位掩码。**单测要求：新旧输出逐字节等价**（doc 51 触摸编码等价测试的既有做法） | 交互期 60–120 事件/s 的 0.2–0.4MB/s + ~3000 对象/s 分配，是 GC STW 落在触摸路径的主源 | 分配率对照 + touch2frame p95 |

| C3 | **eventWriteLock 临界缩短**：锁内含 socket write+flush，反向链路慢时阻塞后续事件与夜模式/集群命令（doc69 P2 锁项） | 拆为"锁内组帧、单写线程串行发送"，保持顺序不变 | touchSendMax 峰值 ↓ |

## 3. 无线方案

### 3.1 音质稳定不丢包（无线）

| # | 动作 | 机理 | 验收 |

| A1w | **【前置】补无线音频丢包基线**：开音频 5s 窗统计跑一段交互（滑地图+播放），同时 `debug.diplay.video_rcvbuf` 保持默认 | 无线空口争用是否造成 miss/late 从未被量化 | 与有线同口径数据表；若全 0 ⇒ 无线音质问题只剩解码/写阻塞，主攻 A3w |

## 4. 通用批次（两链路共享，来自 doc69/41，按收益排序）

对三目标的贡献：P0-2/4/5 → **触控+音质**（消 STW 落点）；P1 → **帧率+音质**；零风险三连 → 全部。

1. **零风险三连**：BufferInfo 两处提字段、isOpaque=true、executor 命名+触摸队列分离（半天，先做）。
2. **音频 rtp 池化 + AAC ADTS 复用**（doc54 A1 挂账 + doc41 §2.5）：有线 27KB/s、无线 40KB/s 稳态分配；需先证明收益（ADR-23 口径）→ alloc 计量在前。
3. **触摸固定布局直写**（§2.3 C1，两链路共用同一条 sendHidReport）。
4. **AEAD key/iv 每 op 新建 → 每流复用**（doc69 P1-6，200–330 对/s，~20 行）。
5. **控制通道 O(n²) 累积 + 非 inline trace**（doc69 P1-9）。
6. **用户态 NCM 1ms 空转 → 自适应退避**（doc69 P0-1，仅影响有线的功耗/CPU 余量——间接给 A4 腾核）。
7. UDP 收包每包对象（DatagramNetwork/复用 InetAddress，doc69 P1-8）。

## 7. 不确定性与待上机核对

- 无线音频丢包"是否真的为 0"未量化（A1w 就是为此设）；若为 0，§3.1 只剩解码/写阻塞问题。
