# 69 · 项目审计：性能与安全（2026-10-13，只读审计）

范围：`CarPlay-CS11`（shared 35,860 行 / common 14,788 行 Kotlin，另有 automotive/samples/vpndialogs-stub）。
方法：静态只读审查（未运行、未改代码），对照已有结论去重（doc 22 瓶颈全图、doc 41 代码层优化、doc 54 ADR/GC、SECURITY.md、api19-lint-audit）。
威胁模型：攻击者**与车机热点同网段**（无线会话），或在车机上装了另一个**普通 App**（无 root、无系统签名）。有线链路绑 `fe80::2%usb1`，只有 USB 对端可达，不在攻击面。

## 一、总体结论

- **安全：1 个应尽快修的控制面鉴权缺口（H1）**，修复量很小（RTSP 入口一处门禁）；其余为纵深加固项，多数是 AirPlay/CarPlay 协议的固有取舍或已有缓解。
- **性能：数据面没有算法级新坑**（硬解/native AEAD/第一批消分配都已落地），剩余可优化项集中在**热路径零分配收尾**与**用户态 NCM 发送侧空转**。按 doc 54 的实测基线（GC STW 37–67ms、间隔 1.2–3s），本文 P0/P1 全部落地预计交互期分配率再降 ~0.4–0.7 MB/s，GC 间隔有望拉长 15–25%。
- 未发现：SQL 注入、命令注入（现有 exec 均固定串且有转义）、全局 TrustManager、凭据明文落日志、动态依赖版本。

## 二、安全发现

### H1（高）RTSP 控制面不校验 pair-verify——同热点设备可冒充控制器【已核实】

**位置**：[AirPlaySession.kt:544-625](../../CarPlay-CS11/shared/src/main/java/com/shilapi/xcertplay/airplay/AirPlaySession.kt)（`handle()`）；读循环 :459-531；会话注册 `CarPlayController.kt:313` 附近。

**事实**：控制通道加密是**惰性启用**的（:526-530，pair-verify 产出 `controlKeys` 后第一条请求才建 `ControlCipher`），但 `handle()` 对 `SETUP / RECORD / TEARDOWN / POST /command / POST /feedback / buffered-audio 方法` **没有任何"已验证"门禁**。攻击者自建 TCP 不做 pair-verify ⇒ `cipher` 恒为 null ⇒ 明文请求照常被处理。RTSP 端口无线时绑车机 AP 地址（doc 0bis：192.168.43.1，热点客户端可达）。

**可达操作**（逐条对照代码确认有处理逻辑）：

| 伪造请求 | 后果 |
| --- | --- |
| `RECORD` | `listener.onSessionActive(this)`（:547-550）把攻击者连接注册成 active session |
| `TEARDOWN` | 经共享 `media` 引擎拆掉真 iPhone 已建的流（拒绝服务） |
| `SETUP` | 创建屏幕/音频端口（资源耗尽；数据端口因缺 AEAD 密钥播不了声画，但对象会建） |
| `POST /command` | 直达 `handleCommand`，包含 **`disableBluetooth`**（会驱动 A2DP/HFP 释放看门狗，doc 66）等改变车机蓝牙状态的命令 |
| `/info` POST、`/feedback`、buffered-audio 控制方法 | 状态污染 |

媒体数据面有 AEAD（攻击者注入只会增加 authFail 计数，不可利用）；缺的是**控制面授权**。

**修复**（建议分两步，避免打断真实流程）：

1. 先做一轮**只记录不拦截**的上机观察（dry-run）：在 `handle()` 入口统计 `verified=false` 时各方法的真实出现（真实 iPhone 在 pair-verify 前应只发 `/info`、`/pair-setup`、`/pair-verify`、`/auth-setup`）。
2. 观察一轮无误后，在 `handle()` 最前面加门禁：除上述 4 个白名单路径/方法外，要求 `pairVerify.controlKeys != null`（注意判据用 controlKeys，不是 cipher——合法首条请求时 cipher 尚未惰性建立），否则返回 403/断连；并可锁定"首个完成 pair-verify 的对端"，后续连接只接受同源地址。
3. 单测：白名单 4 路径未验证可过；RECORD/SETUP/command 未验证 403；已验证全通；controlKeys 存在但 cipher 未建时不误杀。

### M1（中）pair-setup 固定 PIN "3939" 且无配对窗口

[PairSetup.kt:6,35](../../CarPlay-CS11/shared/src/main/java/com/shilapi/xcertplay/airplay/PairSetup.kt)。AirPlay 协议固有设计（与上游实现一致），SECURITY.md 语境下属"设计上接受"。但当前任何时刻同热点设备都能发起 SRP 配对并存入自己的 LTPK，此后可合法通过 pair-verify。**缓解**：仅在用户进入"等待连接"状态时接受 pair-setup；加会话超时与并发配对数限制（1 个）。修复成本高于 H1，建议在 H1 之后做。

### M2（中）MediaButtonReceiver 导出且无权限保护

[AndroidManifest.xml:127-134](../../CarPlay-CS11/common/src/main/AndroidManifest.xml)；receiver exported 无 `android:permission`。`MEDIA_BUTTON` 在 4.4 不是系统保护广播，任意 App 可伪造 KeyEvent，会话期间触发播放/切歌/暂停。
**修复**：receiver 内只在"会话活跃"时响应（非活跃直接丢弃）；真实系统媒体键走的是 `AudioManager.registerMediaButtonEventReceiver` 的运行时注册路径（doc 08 已实现 `CarPlayMediaKeys.startLegacyKeys()`），静态 receiver 只是兜底，收紧不影响方控。发送方包名校验 API 等级不够（`getSendingPackageName` 需新 API），不做。

## 三、性能发现

基线：doc 54 实测稳态分配 ≈4.3 MB/s、GC 间隔 1.2–3s、每次 STW 37–67ms（落在音频写/视频喂帧/触摸上行任意一条上即可感）。doc 41/54 第一批四项已核对**确无残留**。以下标【新】的为本次新发现，【挂账】为 doc 41/54 已列未做。

### P0（高收益/低风险）

1. **【新】用户态 NCM 发送线程 1ms 固定空转**：[UserSpaceNcmLink.kt:83-87,142](../../CarPlay-CS11/shared/src/main/java/com/shilapi/xcertplay/transport/UserSpaceNcmLink.kt) `TRANSMIT_POLL_MILLIS=1`，空闲时每秒 1000 次唤醒 + JNI `nativeTxPending`，整个有线会话持续耗电并阻止 CPU idle；:91 每帧再 `frame.copyOf(length)`。
   改：自适应退避（发完一帧保持 1ms 窗口，连续无帧渐退 5→10ms，来帧立即恢复）；TX 缓冲预留 28B NTB 头，连 [Ntb16Codec.kt:20-43](../../CarPlay-CS11/shared/src/main/java/com/shilapi/xcertplay/transport/Ntb16Codec.kt) 的每帧拷贝一起消掉（带数据：改前/改后 `top -m` 该线程 %、空闲功耗只能定性看 idle 计数）。

   改：hidSendReport 的 3 键结构恒定，写固定布局 bplist 直写（整帧含 RTSP 头一次成帧）；TouchDispatchGate.shape() 改位掩码（现每事件 2–3 个 List\<Boolean\>）。

## 四、与既有结论的关系（避免重复劳动）

- 链路/内核侧（USB IRQ 亲和、RPS、接收窗、rmem/backlog、taskset CPU2-3）：doc 22/51/66 已闭环，本报告不重复。
- 音频格式协商、加大应用缓冲：ADR-12/13 已判死，勿重试。
- doc 41 中"音频解码线程与 AudioTrack 写剥离（§2.1b）"仍未做，本文未列入 P0：当前实测 maxWriteMs 250ms 停摆属无线 AAC 场景，建议先做 P0-2/3 再用数据决定是否需要拆线程。
- HEVC：CS11 VPU 不支持，协商侧维持 H.264-only（doc 41 §1）。

## 五、建议的提交节奏（对齐用户固定流程）

- 安全 H1：dry-run 观察 → 门禁 + 单测 → 上车验证（点火窗口只多一项：确认真实 iPhone 流序中无白名单外的明文请求被 403）。
- 性能每项：先单测（尤其 bplist/加密输出做逐字节等价）→ 绿了再装机 → AllocationStats/top 前后对比数据写进提交信息与文档。
