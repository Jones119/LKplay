## 1. 项目概览

### 1.1 目标与背景

**目标**：在这台领克 CS11 车机上，用一个**自行开发、安装在车机上的 Android 应用**（GPL-3.0 开源项目 DiPlay 的 fork），实现：

1. **iPhone 通过 CarPlay 把画面/声音/触控/麦克风交给车机**——**无线**（车机自开 Wi-Fi 热点 + 蓝牙配对）与**有线**（USB 线 + NCM 网卡）两种形态；
2. **车机液晶仪表盘**（驾驶员正前方那块屏，不是中控大屏）上显示**导航指引**（转向箭头、路名、到下一路口距离、剩余距离/时间）与**媒体信息**（曲名/歌手/专辑/进度/封面）；
3. **可用的日常体验**：音频（媒体 + 导航语音）正常、麦克风（Siri）可用、方向盘媒体键可用、屏幕四角圆角遮罩、隐藏系统栏等。

**为什么做（业务/技术动机）**：

- **【事实】** 这台车机**出厂不支持 CarPlay**（原厂只支持"随心听"在线音乐、百度地图导航、亿咖通 ECARX 自家的互联方案）。车主想用 iPhone 的 CarPlay。
- **【事实】** 车机是 Android 4.4.3 / **API 19** / Dalvik，且**厂商对系统做了大量定制与阉割**（例如没有标准外部存储路径 `/storage/emulated/0`，见 §5.3）。直接跑现代代码会 `NoSuchMethodError` / `NoClassDefFoundError`。
- **【事实】** 仪表**不接受普通 Android 投屏**（全车只有一块 display，见 §4 的 ADR-3），只能通过厂商的 **DIM** 数据接口（见 §7.1）把文字/箭头/图片 URI 推给它。
- **【事实】** 有线上屏之前，该项目只跑通了无线；**2026-10-10 有线首次上屏成功**，随后进入"为什么有线比无线卡"的调优阶段（W2）。

### 1.2 项目来源与许可

- **【事实】** 本仓库是开源项目 **DiPlay**（GitHub `shihabal3amri/DiPlay`）的 **fork**，许可 **GPL-3.0**；实现的是 CarPlay **接收端（车机侧）**：AirPlay 协议 + iAP2 配件协议。
- **【事实】** 本 fork 分支名 `cs11-api19`；所有 `fix(cs11):` / `feat(cs11):` / `perf(cs11):` 开头的提交都是为本车机做的改动。
- **【事实】** 仓库**不合并上游**（约定：手工移植上游修复并把测试一起带过来，见 ADR-2）。
- **【事实】** git 提交者名字是同一个（`肉肉先森`，个别提交显示 `DSH agent`），**因此 git author 不能用来区分是哪个 AI 会话提交的**——请按提交内容 + docs 51/52/53 归属工作流。

### 1.3 成功标准与验收方式

**成功标准（按重要性）**：

1. **能连上并稳定使用**：无线/有线 CarPlay 都能连上；**不卡顿、不断连、异常后能自愈**（这是 W2 的目标，也是当前用户最关心的一条）；
2. **仪表导航可用**：箭头（白色，与原厂百度导航一致）、路名、距离、剩余时间；起步阶段显示"前往路线"；路线重算时卡片不闪；
3. **仪表媒体可用**：曲名/歌手/专辑/进度正确；**封面能显示并随曲目切换**（当前未达成）；
4. **不破坏车机**：不改系统分区、不装改过的第三方 APK、日常运行不需要 root。

**验收方式**：

- **单元测试**（无需车机）：

### 1.4 关键约束

- **技术栈**：目标 **API 19 / Dalvik**；**任何 ≥API 21 的调用必须隔离进专门的"版本持有者类"**（ADR-7），否则老系统上会崩（`catch(Exception)` 抓不到 `NoSuchMethodError` 这类 `Error`）。
- **兼容目标只有车机**：小米平板只做"没有车机时的次选冒烟测试"，**不为平板做取舍**（ADR-1）。
- **成本约束（很重要）**：**每次 `adb install` 都会中断当前 CarPlay 会话**，用户要重新连接。
  ⇒ 约定：**多改一次、少装一次**——把同一轮的多项修复合并成**一次构建 + 一次安装**。
- **合规/安全红线**：不装篡改过的第三方 APK；不改 `/system` 分区；日常运行不需要 root（仅调试时用 adb 读 `/system`、拉 jar、看 `/sdcard`）；**不刷机**（系统升级已评估并否决，见 ADR-15）。
- **性能约束**：i.MX6Q 弱（无硬件 AAC 解码、无硬件 Opus 解码）；**一切"软件编解码"都要先算 CPU 账**；系统在交互期本身就忙（见 §3.3/G）。
- **测量纪律（W2 血泪教训，见 ADR-19）**：车机侧任何旋钮的 A/B **必须交错（A/B/A/B）**、每侧 ≥2 个窗口，并用**内容强度代理指标**（`rx` 均值、`kbps` 中位数）校验两侧内容量级相当，否则整轮作废。
- **不烧油**：实车操作后提醒用户熄火；车机油耗与电瓶都在意。
- **文档约定**：全部技术文档写在 `D:\Development\DiAuto-DiPlay\docs\_digest\`（**不在 git 仓库内**，见 §2.5/D）。接手者请继续遵守，不要把文档塞进代码仓库。

### 2.3 【进行中】两个卡点

#### A. W1 唯一卡点：仪表专辑封面画不出来

**现象（【事实】）**：播放音乐时，仪表媒体卡片有曲名/歌手/专辑/进度，**封面区域空白**；换曲也不出图。

**已排除的交付形式（每一种都有日志证明"厂商收到了"，但仪表不画）**：

| 交付形式 | 厂商是否收到（日志证据） | 仪表是否画 |
|---|---|---|
| `content://<包名>.artwork/covers/<session>/<uuid>.jpg` + `grantUriPermission`（`grants=2 provider=true`） | ✅ 3 个不同 UUID | ❌ |
| `file:///storage/emulated/0/Android/data/<pkg>/files/cluster-artwork/…` | ✅ | ❌ |
| `file:///sdcard/DiPlay/cluster-artwork/<session>/<uuid>.jpg` | ✅ 36+6 次 | ❌ |
| `http://127.0.0.1:<port>/covers/<session>/<uuid>.jpg`（回环 HTTP 图床） | ⏳ 未验（代码已就绪，含每请求一行日志） | ⏳ |

**关键旁证（【事实】）**：
- 车机**自带的**"随心听"音乐应用，封面在仪表上**能显示且随曲切换**；它交付的是 `http://y.gtimg.cn/...jpg`（在线曲）与 `file:///sdcard/Music/mediacenter/images/<专辑>-<歌>-<歌手>.jpg`（本地曲）；
- 我们的 `/sdcard/DiPlay/…` 文件**确实可被其他进程读取**（`-rw-rw---- root sdcard_r`，`cat` 能读出完整 31326 字节）；
- **逆向参照实现 EasyPlay v71 发现**：它在**本机这一类机型**（`sdk==19 && Freescale && CS11`）上**主动把封面通道切成"回环 HTTP"**（`bind(127.0.0.1, 0, backlog 4)`，路径 `/covers/<session>/<uuid>.jpg`）。

**当前假设（【推测】，有上述证据支持）**：仪表取图方**只对 `http://` 发起抓取**，`content://` / `file://` 只被记录、不被加载。

**本轮已做的修复（【事实】，提交 `5051fef1`）**：修掉四个可能让 HTTP 档**静默失效**的缺陷——HTTP 服务生命周期（改为进程级单例，会话结束才释放）、封面保留策略（已交付的永不回收，未交付上限 32）、绑定失败不再静默降级、**每请求一行日志**（把"仪表没来取"与"我们没记录"区分开）。

**下一步**：§6.1 的判决实验（一次点火即可定性）。

#### B. W2 卡点：有线交互期仍丢包——"丢在哪一步"差最后一锤

**现象（【事实】）**：有线连接下，**手指在屏幕上滑动/拖动地图时**偶发音频卡顿与画面迟滞；**空闲时不丢包**（空闲 60 秒 `Udp6InErrors=0`、音频零缺包）。

**已定量的事实（【事实】，2026-10-10 全部会话共 670 个 5 秒音频统计窗口，≈56 分钟音频）**：

| 指标 | 实测值 | 含义 |
|---|---|---|
| **永久缺包** | **1888 个包 ≈ 14.2 秒音频 = 0.42% 的采样时间** | 音频内容真的少了 |
| `lateOrDuplicate`（迟到/重复到达的包） | **0** | **没有任何包是"迟到后到达"的** |
| `underruns`（播放缓冲被抽干） | **0** | 播放从不"饿死" |
| `skipped` / `skippedMs`（抖动缓冲被迫丢弃） | **0 / 0** | 抖动缓冲从未触发 |
| 播放缓冲占用（`estimatedQueuedFrames`） | 中位 **129 ms**（p90 346 ms，最大 509 ms） | **缓冲已经很深** |
| 缺口形状 | 平均 **6.5 包（≈9.4 KB）**，最大 **34 包（≈49 KB）**，**成串** | 与 NCM 聚合帧（NTB ≤16 KB ≈ 11 包）粒度吻合 |

**由此得到的两个结论（【事实】级）**：
1. **这不是"抖动"（jitter），是"丢包"（loss）**：再大的播放缓冲也造不出没到达的包 ⇒ **"应用内缓存 300 ms 再播放"解决不了这个症状**（缓冲已中位 129 ms 且从不被抽干）；
2. **不在应用侧的读取/处理/播放**：`underruns=0`、`skipped=0`、`Udp6RcvbufErrors=0`、`Udp6NoPorts=0`、`usb1` 驱动计数 `rxErr=0 rxDrop=0`。

**仍未定论的一步（⚠️ 待确认，见 §3.6/C 的判读表）**：包是
- **(a) 到了内核、但被 UDP 校验/长度校验拒收**（`Udp6InErrors` 增长，而 ICMPv6 计数不动、socket 队列不溢出）——意味着**报文在 USB/NCM 路径上已损坏**；还是
- **(b) 根本没到**（手机侧 NCM 发送队列在突发时整段丢弃，或 USB 传输整段失败）——**车机侧没有任何计数器能看见**。
- **干扰因素（【事实】）**：IPv6 UDP 的 `InErrors` **还会被 ICMPv6 错误报文推高**，而我们的 `NtpClock`（NTP 对时）有个线程**每秒往手机发 1 个 UDP 包**（实测 `Udp6OutDatagrams` = **+60/60s**）⇒ **这个计数可能被"与音频无关"的错误污染**。Linux 老内核还有一条"把某种丢弃错记进 `UDP_MIB_INERRORS`"的历史修正（3.10 早于该修正）⇒ 计数口径本身也要验。
- **判定工具已就绪并已离线自测**：`work/lossprobe4.sh` + `work/analyze_lossprobe4.py`（见 §3.6/C）。

**与此同时已确认的"结构性事实"（【事实】，同一天同一车机的有线/无线对照）**：

| 维度 | 有线 | 无线 |
|---|---|---|
| 物理链路 | USB2 High Speed（实测 `speed=480`）bulk；内核 `cdc_ncm` → 网卡 `usb1`，IPv6 link-local `fe80::2`，MTU 1500 | 车机自开 Wi-Fi 热点（802.11n）→ `wlan0` / `192.168.43.1` |
| 音频流类型 | **type 100 LPCM**：**134.9 包/秒、1565 kbps、1449 B/包** | **type 102 AAC-LC**：**47.8 包/秒、252 kbps、658 B/包** |
| 音频解码 | 不解码，只做 BE→LE 字节序交换 | MediaCodec **软件**解 AAC（≈25% 单核） |
| 视频流 | TCP type 110 H.264（`ScreenStream`，**两种形态完全同一套代码**） | 同 |
| 额外开销 | 同一条 USB 上还多养 USBMUX/lockdown + iAP2 CSM 两条控制通道 | 无 |

⇒ **"有线反而比无线卡"的结构性原因**：有线音频的"过路面积"是无线 AAC 的 **2.8 倍包率 / 6.2 倍码率**，却与视频突发共用同一条 NCM 队列；而**视频代码两边完全相同**，所以差异只能来自"链路 + 音频负载"。

### 3.3 核心模块与调用关系（数据流）

#### A. 无线链路（端到端）

1. 车机**自开 Wi-Fi 热点**（默认名 `Lynk&Co`，模式 `MANUAL`；另有 `EXISTING_WIFI` 组网方式可选）；
2. iPhone 通过**蓝牙**与车机配对 → iAP2 蓝牙握手 → 车机发 Wi-Fi 配置移交消息（`0x5702`/`0x5703`；字段定义可对照 `_upstream\livi\native\livi-helperd\crates\iap2-csm\src\messages\wifi.rs`）；
3. iPhone 加入热点 → **AirPlay over TCP**：RTSP 握手（车机发 `/info` 能力清单 → iPhone `SETUP` 各流 → `RECORD`）；
4. **视频**：TCP 流 `type=110`（H.264）→ `ScreenStream` → `AndroidMediaSink`/`VideoDecoder`（**MediaCodec 硬解**，走 VPU）→ `TextureView`/Surface 上屏；
5. **音频**：UDP 流 `type=102`（**AAC-LC**，加密）→ `AudioStream` → 解密 → `AndroidMediaSink.AudioRenderer`（**软件** AAC 解码）→ `AudioTrack`；
6. **触控**：AirPlay 事件通道反向发 HID 报告（`AirPlayHid`）；
7. **麦克风**：iAP2/AirPlay 语音流上行（native `libopus` 编码，96 kbps）；
8. **控制与元数据**：iAP2（NowPlaying 元数据、**封面文件传输**、方向盘按键、导航 TBT 快照）。

#### B. 有线链路（端到端）

1. USB 插入 → Android `UsbManager` 枚举 → USB 权限流程（`UsbPermissionSetup`）→ 识别 iPhone（VID/PID）；
2. 打开 iPhone 的多个 USB 接口：**USBMUX/lockdown**（iAP2 控制）、**NCM 数据**（网卡）；另有**板上 MFi 认证协处理器**（硬件芯片，用于 CarPlay 认证，**不能模拟**）；
3. `Iap2UsbSession` 建立；USBMUX 帧由 `UsbMuxFrameBuffer` 组帧（**本轮改为游标 + 原地压缩**，消除每次 USB 读的整段重分配）；
4. iAP2 认证（`Iap2MfiAuthenticationClient`，走 MFi 协处理器）；
5. **内核网卡引导（CS11 特有、最容易困惑的一段）**：
   - 本 ROM **没有 TUN 驱动** ⇒ 经典 `VpnService` + NCM 用户态桥**不可用**（报 "Cannot create interface"）；
   - 内核**自带 `cdc_ncm` 驱动**，但 iPhone 的 NCM 功能默认**不被认领**（`unowned`），并且不会自动出现 `usb1` 网卡 ⇒ 需要 **root 介入**让它绑定并配好 IPv6 link-local；
   - 做法（`network/Cs11NetdevBootstrap.kt`）：app 把一段脚本**排队写入 `/data/.android/rootcmd.sh`**（车机上有一个 `rootd` 守护进程消费该文件并执行；同目录还有 `rootcmd.sh.netdev` 作为暂存名），脚本负责网卡 up / 地址 / 路由；app 再**轮询**网卡是否就绪（`ready()`/`appeared()`），就绪后把 AirPlay 监听**直接绑在该网卡的 link-local 地址上**（实测 `fe80::2`）；
   - 网卡名 **`usb1`**，MTU 1500，链路速率实测 `speed=480`（USB2 High Speed，480 Mbps）。
6. 之后的**视频/音频/触控与无线是同一套代码**；差异只有：链路、音频格式（**LPCM vs AAC**）、以及多养两条 USB 控制通道。

#### C. 视频路径与"迟到丢帧"判定（W2 核心之一）

- TCP accept 后，`ScreenStream` 用 `VideoReceiveWindow.current()` 设置 `SO_RCVBUF`；
  **关键事实：Linux 内核会把 `SO_RCVBUF` 的实际值翻倍**（请求 8 KiB ⇒ 实际 16 KiB；请求 64 KiB ⇒ 实际 128 KiB）。本项目长期以为默认是 64 KiB，实际是 **128 KiB**——这是"有线卡顿"的一个大坑（§5.9）。
- 收到的帧进入解码队列；若**等到解码时已经比到达时刻晚超过"老化阈值"（默认 250 ms）**，该帧被**主动丢弃**（计入 `dropped`），以保持"画面与手指动作对齐"。`dropped` 高 = 迟到帧多 = 排队严重。
- 统计行（每 5 秒，tag **`DiPlay-VideoStats`**）关键字段：`rx`（收到的 fps）、`shown`（上屏 fps）、`dropped`（因迟到被丢的帧数）、`maxGap`（窗口内最大接收间隔 ms）、`touch2frame`（**触摸事件到画面响应**的中位延迟 ms，最贴近用户观感）、以及（`debug.diplay.trace=1` 时）`alloc=…KiB/s freed=…KiB/s gc=…`。

#### D. 音频路径与统计（W2 核心之二）

- `AudioStream` 用 `DatagramSocket` 收 UDP（`SO_RCVBUF` 默认 512 KiB，≈2.5 秒音频）→ 解密 → `AndroidMediaSink.submit(rtp, sample)`（内部 `LinkedBlockingQueue<AudioPacket>`，上限 **192 包**）→ `AudioRenderer`：
  - **LPCM（有线）**：不解码，只做 **大端→小端字节序交换**（本轮改为交换进复用缓冲，零分配）；
  - **AAC（无线）**：**MediaCodec 软件解码**（≈25% 单核）；
  - 再写入 `AudioTrack`（缓冲计划可选 300/500/1000 ms）。
- 每 5 秒一行（源码 `airplay/StreamReceiveStats.kt`，**字段即判据**）：

  ```
  Receive: audio type=100 packets=… bytes=… readMaxMs=… processMaxUs=… seqForwardGaps=…
           lateOrDuplicate=… interArrivalMaxMs=… seqGapEvents=… seqGapMax=… seqGapLast=[…]
           seqGapAtMs=… ended=… windowMs=… readsOver250Ms=… seqGapAfterReadOver250Ms=…
           seqMissingAfterReadOver250Ms=…
  ```

  另有一行（tag **`DiPlay-AudioStats`**）带播放侧状态：`underruns`、`skipped`、`skippedMs`、`estimatedQueuedFrames`。

  | 字段 | 含义 | 用来判定 |
  |---|---|---|
  | `seqForwardGaps` | RTP 序号"向前跳"的总包数 | **永久丢失**（这些包不会再来） |
  | `lateOrDuplicate` | 迟到/重复到达的包数 | **抖动**（缓存能救的那一类） |
  | `underruns` | `AudioTrack` 被抽干的次数 | 播放缓冲是否够深 |
  | `skipped` / `skippedMs` | 抖动缓冲主动丢弃的帧/毫秒数 | 是否触发了"丢弃保对齐" |
  | `estimatedQueuedFrames` | 播放缓冲内帧数（÷48000 ≈ 秒） | 缓冲深度（实测中位 129 ms） |
  | `readsOver250Ms` | 单次 socket 读阻塞 >250 ms 的次数 | 收包线程是否被暂停 |
  | `seqGapAfterReadOver250Ms` / `seqMissingAfterReadOver250Ms` | 上述暂停**紧跟着**的缺口事件数/缺包数 | **"我们被暂停"与"丢包"是否相关** |
  | `readMaxMs` / `processMaxUs` | 单次读/单包处理的最大耗时 | **尾延迟**（实测尖峰 128–245 ms） |

#### E. 触摸上行

`AirPlayHid.touchReport(contacts, widthPixels, heightPixels)` 把归一化坐标**直接编码**成 HID 报告（本轮改为零分配，且新重载与旧编码**逐字节等价**，有单测 `AirPlayHidTouchReportTest` 看守），由 `AirPlaySession.sendTouch` 发出。

3. **验证成功**：`/data/.android/mp_run.txt` 里出现 `MP TRIGGERED` 与 `CapEff: 0000001fffffffff`，`ps` 能看到 `rootd.sh`；
4. **队列用法**：把命令写入 `/data/.android/rootcmd.sh`，**约 1 秒内**被 `rootd` 执行，输出落 `/data/.android/rootout.txt`；
5. **调优/恢复脚本**：`tools/cs11_tune.sh`（IRQ 亲和/RPS/taskset/ksoftirqd/内核旋钮重放，**每次点火都要重放**）、`tools/cs11_recover.sh`（点火 + 拉 app + 调优重放 + 核验）、`tools/cs11_watchdog.sh`（常驻体检自愈）。

用法：`analyze_lossprobe4.py <探针日志> [<logcat 文件>]`。它的**判定顺序**（已用四种合成场景离线自测通过，见 §7.3 的 `probe4_*.log`）：

| 观察 | 结论 |
|---|---|
| `sockDrops > 0` | socket 层丢弃（softirq backlog 满）⇒ 收包核/软中断被挤 |
| `udp6rcv > 0` | socket 收队列溢出（应用读得慢/被暂停） |
| `rxqMax > 0` 多数窗口 | 应用侧积压 |
| `udp6err` 与 `icmp6in` 同步增长 | 该计数被 ICMPv6 污染 ⇒ **不能**据此说音频"到了内核" |
| `udp6err` 增长但 ICMPv6 不动、队列不溢出 | 包**到了内核但被校验/长度拒收**（传输损坏） |
| 内核计数完全不动 | **纯"没到"**（手机侧排队溢出或 USB 整段失败） |

## 4. 关键决策记录（ADR 风格）

> ADR-1…ADR-10 来自 W1（仪表/UI/API-19），细节见 doc 53 §4；ADR-11…ADR-23 来自 W2（有线/无线流畅与稳定），细节见 doc 51。

### ADR-1：只以 CS11（API 19）为兼容目标，平板仅做冒烟测试

- **决策**：所有兼容性取舍以车机为准；小米平板（Android 15/SDK 35）只用于"没有车机时验证功能是否还活着"。
- **背景与约束**：车机 API 19/Dalvik，平板 SDK 35/ART，差异巨大；同时照顾两者会让代码充满分支。
- **备选与否决**：① 两边都支持——成本高且车机才是交付对象，否；② 只支持平板——平板不是交付对象，否。
- **后果**：允许"老系统专用路径"（如软件 Opus 兜底）。**接手者不要为平板的异常行为改核心逻辑**。

### ADR-2：手工移植参照实现（EasyPlay / HyLink），不合并上游

- **决策**：从反编译的参照实现里"读懂机制 → 自己写 → 带单元测试 → 提交"，**不做** git merge/rebase 上游。
- **背景**：上游 DiPlay 与本 fork 已大幅分叉；参照实现（EasyPlay v71、HyLink）闭源，只能逆向学习。
- **备选与否决**：直接合并上游——历史教训是冲突巨大且上游没有本车机的定制。
- **后果**：每次移植都要写清"证据出处（文件:行号）"到 doc 42/52 这类文档；⚠️ 上游若有安全修复需人工评估。

### ADR-3：仪表走 DIM 数据注入（路径 A），放弃"投屏/镜像"（路径 B）

- **决策**：仪表内容全部通过厂商 DIM 接口**按字段注入**；不做第二 display 投屏。
- **背景与证据**：`dumpsys display` 显示**全车只有一块 display**（`内置屏幕 1920x1080 BUILT_IN, mDisplayId=0`），仪表不是 Android 独立 display。
- **备选与否决**：`Presentation` 投副屏——物理上不可能；截图镜像——成本高且仪表还要吃厂商私有渲染通道。
- **后果**：代码里"仪表内容模式（alt-screen）"相关路径在本车**永久空转**（如 `CarPlayClusterDisplay.Content`、安全区 px 化）。**接手者不要在这上面花时间**。

### ADR-4：箭头 id 使用"工厂导航族"（101–143），不用参照实现的旧族（1–45）

- **决策**：把苹果的机动类型映射到车机**原厂百度导航使用的整数 id 族**（左转 102、右转 103、左前 104、右前 105、掉头 106/107/108、直行 109、环岛 111、出口 112、目的地 115、环岛左右/掉头 141/142/143）。
- **背景**：仪表自己决定图标与颜色；最初照搬 EasyPlay 的 1–45 族 ⇒ 实车箭头**黄色且偏左**，原厂是**白色**。
- **证据**：反编译车机自带百度导航（`_analysis/cs11_vendor/naviauto_src/.../com/baidu/a/a.java:30-87`）得到静态 id 表；实车换族后**箭头变白** ✅。
- **后果**：`debug.diplay.arrow` 属性保留用于扫 id；"渡轮"类在工厂族里没有对应图标，暂用直行 109（⚠️ 待确认是否需要别的处理）。

### ADR-5：导航卡片"要么完整、要么清空"，并带 3 秒去抖

- **决策**：只有快照"可显示"时才提交卡片，否则**清空**；但清空**延迟 3 秒**（去抖）。
- **背景**：仪表收到不完整数据会自己显示 `0 m`/`<1min` 假值；而路线重算时 iPhone 快照会短暂不完整，立即清空会"闪一下"。
- **反直觉细节（【事实】）**：苹果上报的状态字节 **`3` 不是终点**，而是重算中继态（实车恒为 `5 → 3 → 1`）。**终态只认 `null`/`0`/`2`**。
- **后果**：`cluster card held (incomplete …)` / `cluster card cleared (…)` 成为验收关键字。

### ADR-6：封面交付"四档"，回环 HTTP 为首选

- **决策**：封面以 `http://127.0.0.1:<port>/covers/<session>/<uuid>.jpg` 交付（首选），失败依次降级 `file://`、`content://`。
- **背景与证据链**：`content://`（带 grant）、沙箱 `file://`、正确的 `/sdcard/DiPlay/…` `file://` **三种厂商都收到了、仪表一张都没画**；而车机自带应用用 `http://` **能画**；EasyPlay 在 `sdk==19 && Freescale && CS11` 门禁下**主动选 HTTP**（doc 52）。
- **备选与否决**：继续调 `file://`（已三次否证）；用 `Bitmap` 交付（逆向表明交付路径上只有 `Uri`）。
- **后果**：新增进程内 HTTP 服务（生命周期/端口/越权防护需维护）；**验证"取图方来没来取"必须看每请求日志**。

### ADR-7：API-19 隔离约定 + 反射读隐藏 API + 守卫测试

- **决策**：所有 ≥API 21 的类/方法放进"版本持有者类"；隐藏 API 一律反射；加测试看守。
- **背景与证据**：API 19 上 `Math.floorDiv/floorMod(long,long)`（API 24）抛 `NoSuchMethodError`，而 `catch(Exception)` **抓不到 `Error`** ⇒ 曾是必然崩溃点（已修）；Dalvik 还会在类校验期打印解析不到的引用（约 100 条）。
- **备选与否决**：不隔离直接调用（实车风险否证）；靠 lint（`android.jar` 检查覆盖不到 `java.*` 与 `Foo::class.java` 盲点）。
- **后果**：剩余技术债见 §2.5/B（不影响功能，但约定要继续遵守）。

### ADR-8：能热调的用"调试属性"，能持久的用"设置项"

- **决策**：上车实验用系统属性（`debug.diplay.*`，熄火即失效）；必须跨点火保留的用**持久化设置**。
- **背景**：历史教训——仪表推送开关最初是 adb 属性，一次点火后丢失（doc 38）。
- **后果**：**新增开关默认应做成设置项**；只有"一次性实验"才用属性。

### ADR-9：日志纪律（每次变化一行、每进程一次、不做逐帧刷屏）

- **决策**：状态变化才打日志；同一原因的告警每进程只打一次；判据关键字必须写进文档。
- **背景**：历史上同一行写两次（`83d064b4`）；逐帧日志淹没判据。
- **后果**：验收依赖**精确关键字** ⇒ **改日志措辞等于改验收判据**，必须同步更新 doc 28/50。

### ADR-10：OEM 图标通过 AirPlay `/info` 声明（不改 iOS 行为）

- **决策**：在 AirPlay 的 `/info` 里声明 `oemIconVisible/oemIconLabel/oemIcons`，由 iOS 决定显示位置。
- **背景**：想让 CarPlay 界面里有"回到车机"的入口。
- **后果**：实车证明它显示在 **CarPlay 主屏**（不是侧边栏）；点击行为待验收（§6.4）。

### ADR-11：视频接收窗默认改为"请求 8 KiB（实际 16 KiB）"，并做成可调属性

- **决策**：`VideoReceiveWindow.DEFAULT_BYTES = 8 KiB`（内核翻倍 ⇒ 实际 16 KiB），可调范围 4 KiB–256 KiB，非法值回落默认；属性 `debug.diplay.video_rcvbuf`。
- **背景与约束**：有线交互期画面迟滞；**关键发现：内核把 `SO_RCVBUF` 翻倍**，历史"64 KiB"实际一直是 **128 KiB** ⇒ 视频发送方被允许一次灌入过多数据，把 NCM 队列与音频包一起挤爆。
- **备选与否决**：保持 64 KiB（实测 `dropped` 161、`maxGap` 1736 ms）；选更小的请求 4 KiB（实测略优，但**不留 1080p/60 余量**，故取 8 KiB）。
- **后果（实测收益）**：迟到丢帧 **161 → 17–28**、`maxGap` **1736 → 239–331 ms**、`touch2frame` 中位 **86 → 51–60 ms**；音频 UDP 丢包率同口径从 **1.76% → 0.27%** 量级（样本不足以做统计结论，只算顺带收益）。**该属性是"零成本可再调"的第一旋钮**。

### ADR-12：有线音频**不做**"加大应用内缓冲"来治卡顿（实测否定）

- **决策**：不把"应用内缓存 300 ms 再播放"当作有线卡顿的解法；保留现有缓冲计划（300/500/1000 ms 可选）。
- **背景与实测（【事实】，670 个音频窗口 ≈56 分钟）**：永久缺包 **1888 个 ≈14.2 秒音频（0.42%）**；`lateOrDuplicate=0`（**没有任何包迟到到达**）；`underruns=0`；`skipped=0`；播放缓冲占用中位 **129 ms**（p90 346、最大 509）。
- **备选与否决**：加深缓冲——**逻辑上不可能**：缓存只能等"迟到的包"，对"不来的包"无能为力；而且缓冲已经 129 ms 且从未被抽干。
- **后果**：把精力转向"**减少丢包**"（视频 pacing、降环境负载、降尾延迟）与"**改变缺口的呈现方式**"（产品选择：跳过/补静音/伪造，其中伪造已被用户否决）。

### ADR-13：有线音频格式**不可协商**（负结果，两侧都试过，勿重试）

- **决策**：不再试图通过 `/info` 让有线走 AAC；`debug.diplay.audio_formats` 只保留为**负结果记录**。
- **背景**：有线音频是 **type 100 LPCM（134.9 包/秒、1565 kbps）**，是无线 AAC（47.8 包/秒、252 kbps）的 **2.8 倍包率 / 6.2 倍码率**，与视频突发共用同一条 NCM 队列——这是"有线更卡"的结构性原因。
- **实测（【事实】）**：把 type-100 的 media 格式换成 AAC（`no-pcm`）后，iOS **整条音频流都不建**（只有视频 `SETUP`）；用 `no-aac` 逼无线走 PCM 也导致无线**完全没有声音**。两种非 `auto` 模式都会让用户**没有声音**，必须清属性 + 重启 App 才能恢复。
- **后果**：有线那 1.5 Mbps / 135 pps 的负载**只能靠"投递侧"缓解**（降视频突发、降收包核压力、NCM RX 旋钮）。

### ADR-14：先"量化分配与 GC"，再决定改哪里（降 GC/分配第一批）

- **决策**：新增 `diag/AllocationStats.kt`，在 `DiagLog.traceEnabled` 时把 `alloc=…KiB/s freed=…KiB/s gc=…` 追加到主屏 `DiagLog-VideoStats` 行尾；并先把四处"稳态分配"消掉。
- **背景**：卡顿是**尾延迟**问题——Dalvik GC 每次**阻塞线程 37–67 ms**，落点正好是音频写、视频喂帧、触摸上行三条"必须准点"的路径；而分配率驱动 GC 频率。改造前**没有任何分配率指标**，只能靠 GC 行数间接推断。
- **备选与否决**：直接上"池化所有缓冲"——风险大且无法度量收益，否；先用 Dalvik 的 `Debug.startAllocCounting()` 系列计数（**只在 trace 时开**，因为逐次分配计数开销很大）。
- **后果（已落地，提交 `585ee614`）**：LPCM 载荷交换进复用缓冲（≈190 KiB/s）、`AudioStream` 密封包复用缓冲（≈194 KiB/s）、`UsbMuxFrameBuffer` 改游标+原地压缩（每次 USB 读不再重分配整段积压）、触摸报告零分配（≈60–120 次/秒）；新增单测 12 例。
  **注意**：Dalvik 的全局计数是 **32 位且会回绕**（约 8 分钟一次），代码里做了回绕校正（有单测）；ART(API 21+) 上这些计数是惰性的，首次读负值则不输出。

### ADR-15：**不**把车机系统升级到 Android 5.1+（评估后否决）

- **决策**：保持 Android 4.4.3；只在应用层做兼容与优化。
- **背景与约束（【事实】，doc 14）**：i.MX6Q **硬件上**支持到 NXP 官方 Android 9.0 Pie BSP；但真正的拦路虎是 ①**刷写入口**（U-Boot/fastboot/i.MX6 SDP 均未验证，HAB 熔断状态未知，DDR/DCD 配置板级私有）；②**整车集成重写**（MCU/CAN、车辆设置、TBox 远控、方控、倒车影像、功放、收音全是 ECARX 私有实现，且 **ECARX 从未为这块板出过 5.1 版本**，没有配套闭源 HAL 可捡）。
- **备选与否决**：① 逆向自建板级 BSP —— 以"人月/人年"计、变砖不可逆（空调/仪表/远控/影音一起失效）；② 换主机/加盒子 —— 违反项目"纯软件、不用盒子"的既定约束（但它是唯一成本/成功率合理的替代）。
- **后果**：**不要**在这条线上投入；若未来真要评估，先做"可逆侦察"（读 `/proc/device-tree`、`/proc/cmdline`、`/proc/mtd`、`/sys/fsl_otp/*`、`getprop | grep -i verifiedboot`），**不要**贸然 `adb reboot bootloader`。

### ADR-16：车机侧内核旋钮**保持厂商原值**（分区/绑核/GPU 实验未定论，不落地）

- **决策**：默认不写任何"性能调参"到持久化（不 `setprop` 持久项、不改开机脚本）；实验结果只在实验窗口内使用。
- **背景与证据**：曾据"降低环境负载"的分区实验宣称硬件有 ~10× 退化，**复核发现内容强度不对等**（见 §2.5/F），**结论撤回**；单独"回退 GPU 时钟"实验**无任何变化**（提交/脚本 `work/gpu_revert.sh`）。
- **备选与否决**：把"绑核 `taskset`"写进持久化——被否：① 实验未定论；② 车机侧旋钮熄火即失效，持久化会与厂商行为冲突。
- **后果**：想再试必须按 ADR-19 的协议，并且**在同一个点火窗口内**完成。

### ADR-17：有线稳定性以"自愈"为目标（B1–B5 的修复方向）

- **决策**：把"黑屏/不重连/进错页"这类**硬失败**当作最高优先级的稳定项；修法是把**无线已有的机制复用到有线**，而不是发明新机制。
- **背景（【事实】，只读代码审计的结论）**：有线没有首帧看门狗（B1）、没有 USB `DETACHED` 广播（B2）、网卡/附着失败只写 `debugLog`（B3）、模式默认偏无线导致插着线却进无线页（B4）、有线仍会 `establish()` 一个 `VpnService`（B5）。
- **备选与否决**：只在 UI 上做"重新连接"按钮——被否：根因是**状态机没有失败出口**，UI 按钮无法覆盖"内核网卡没起来"这类情形。
- **后果**：B1–B4 属于"同一次改动、同一次验证、同一次安装"的批次（§6.2）；B5 需要额外回归（去掉 `establish()` 后确认有线仍能承载 AirPlay）。

### ADR-18：并发会话纪律（只提交自己的文件）

- **决策**：开工前 `git log --oneline -3` + `git status`；**只 `git add` 自己的文件**（禁止 `git add -A`）；提交前重跑全量单测；安装/重启前先在 `work/` 里留一句"我正在测量"的标记（可选但推荐）。
- **背景（【事实】）**：同一工作区/同一车机曾同时有两个 AI 会话；已发生两次"另一个会话重装 APK 打断正在进行的测量"（17:10:53、17:47:58），以及一次"两个 gradle 同时跑导致 `classes.jar` 被锁"。
- **后果**：本仓库历史上出现过并行提交（`37a05abb`/`74d5ca89`/`585ee614` 与 W1 的提交交错），**彼此未覆盖**，但代价是**测量作废**。

### ADR-19：任何车机侧 A/B 必须"交错 + 内容代理校验"

- **决策**：协议固定为 `基线 60s → 改动 60s → 基线 60s → 改动 60s`（≥2 窗口/侧）；**每轮必须核对内容强度代理指标**（`rx` 均值、`kbps` 中位数）与对侧同区间，不同区间则**整轮作废**；同时记住"`input swipe` 注入本身消耗 CPU（每次一个 `app_process`）"。
- **背景**：一次分区实验因"内容强度只有基线一半"而得出错误结论（§2.5/F）。
- **后果**：所有 A/B 脚本（`work/ab_rcvbuf.ps1` 等）都应打印代理指标；判定脚本 `analyze_lossprobe4.py` 也会把每窗口的 `usb1` 速率、逐核 busy 一并列出。

### ADR-20：丢包归因**先于**继续优化（先判"没到 vs 被拒收"）

- **决策**：在拿到"包到底没在哪一步"的结论前，不继续投入"降低视频码率/换帧率"这类会牺牲画质的动作。
- **背景**：目前只确定"不在应用侧读取/处理/播放"（`underruns=0`、`skipped=0`、`RcvbufErrors=0`、驱动 `rxErr/rxDrop=0`），但"到了内核被校验拒收"与"根本没到"未分；而 `Udp6InErrors` 可能被 ICMPv6 污染（我们自己的 NTP 每秒 1 个上行包）。
- **后果**：判定工具已就绪（`work/lossprobe4.sh` + `analyze_lossprobe4.py`），下一次点火 3 分钟即可出结论（判读表见 §3.6/C）。

### ADR-21：探针与判定脚本一律"key=value + 离线自测"

- **决策**：车机侧探针输出 `key=value`（不依赖列序），判定脚本必须先用**合成数据**跑通所有判定分支再上车。
- **背景**：早期按固定列序解析的脚本出过至少两次口径错误（字段合并、半窗口切分），并在合成自测中发现判定顺序错误（把"校验拒收"误判成"核饱和"）。
- **后果**：`work/make_synthetic_probe.py` + `work/probe4_{icmp,corrupt,queue,nothere}.log` 保留在仓库外的工作区里，作为回归资产。

### ADR-22：热路径复用缓冲必须**证明数组不逃逸**

- **决策**：允许复用缓冲（`pcmSwap`、`AudioStream.wire`、`UsbMuxFrameBuffer.bytes`），但每一处都必须在注释里写明"谁可能持有它、为什么不逃逸"。
- **背景与证据**：`AudioPacketCapture.record` 是**立即写盘**（不持有数组）；解码队列只持有**解密后的 `rtp`**；`pcmSwap`/mux 窗口只在单一渲染线程/USBMUX 锁内使用。
- **后果**：`rtp` 保持"每包新建"（见 ADR-23）；测试补了"新旧触摸编码逐字节等价"与"游标缓冲 200 轮不增长"等不变量。

### ADR-23：`rtp` 每包新建**暂不改**（池化需"归还语义"，等计量结果）

- **决策**：`AudioStream` 里解密后的 RTP 数组仍每包新建（≈194 KiB/s）；**不**在没有计量证据的情况下改成池化。
- **背景**：该数组被 `AndroidMediaSink.submit(rtp, sample)` **放进队列**（`LinkedBlockingQueue<AudioPacket>`，上限 192 包 ≈270 KiB），因此复用需要一个"渲染完成后归还"的契约——这是**静默音频损坏风险**最高的改动类型。
- **备选与否决**：立刻池化——被否：收益（≈194 KiB/s，占实测总分配 ~4.3 MB/s 的 4–5%）不足以承担风险；先靠 ADR-14 的计量看是否值得。
- **后果**：若要动，必须带三态单测（归还/复用/队列满）并在车上验证 `underruns`/`skipped` 与音质。

## 5. 踩坑与注意事项

> 编号 1–26 为 W1 阶段（doc 53 §5 有更长的版本，这里保留最影响操作的条目）；27–32 是 W1 的历史事故；**33–52 是 W2 本轮新增**（这些是本会话真实踩过或差点踩到的）。**危险操作单列在 §5.9。**

### 5.1 工作流级（最重要）

1. **多改一次、少装一次**：每次 `adb install` 都会**中断用户正在用的 CarPlay 会话**。把同一轮的多项修复合并成**一次构建 + 一次安装**。
2. **一次点火窗口尽量多做**：车机必须点火才能 adb；窗口内把"要验证的、要抓的、要调的"列成清单逐个打勾（doc 28/50 就是干这个的）。
3. **开工前先查 `git log --oneline -3` + `git status`**：可能另一个会话正在同一工作区提交（§2.5/E）。
4. **只提交自己的文件**，不要 `git add -A`；提交前重跑全量单测，确认失败集没变大。
5. **操作完提醒用户熄火**（不烧油），并说明"车机侧旋钮已失效"。

### 5.2 车机 adb 环境

6. **adb 只在点火通电时在线**；熄火后 `adb devices` 为空，别误判为设备坏了。
7. **车机 adb 会掉线**：长时间抓 logcat 必须用**自愈循环**（检测到断线就重连并继续追加写），否则日志会静默中断。
8. **本机 adb 不支持 `-g`**（安装即授权）：`adb install -g` 会报错，用 `-r -d`。
9. **优先"流式抓取"而不是 `logcat -d`**：`-d` 只导出当前环形缓冲区，若缓冲区滚动过，**中间窗口会丢**（本会话因此损失过一轮数据）。
10. **孤儿 `adb logcat` 进程会锁住构建产物**（Windows 上表现为 `classes.jar 另一个程序正在使用此文件`）：先杀掉残留 adb 客户端再构建。
11. **`input swipe` 注入的代价**：每注入一次会起一个 `app_process`，**本身消耗 CPU**，会污染性能测量；而且它**绕过面板驱动**，所以"触摸时的 `ecspi` 中断"不会增长——**不能用中断计数去定位触摸**。

### 5.3 这台车机的存储是"非标准"的（W1 时代最容易踩）

12. **没有 `/storage/emulated/0`**；`/sdcard` 才是可用拼写（这也是"封面交付要写成 `/sdcard/…`"的原因，提交 `38db460f`/`4bd893a0`）。
13. Android 4.4 的 `/storage/emulated/*` 由 **FUSE** 提供，权限是"合成"的；用 `ls -l` 看到 `-rw-rw---- root sdcard_r` **不代表别的进程读不到**（实测 `cat` 能读出完整内容）。
14. 交付给厂商/其他进程的**文件 URI 拼写**必须与它们期望的一致；本项目因此把 `/sdcard/DiPlay/...` 与沙箱路径都试了一遍（§2.3/A）。

### 5.4 厂商 DIM 接口的隐藏规则（W1）

15. **反射必须按重载匹配**（同票优先级 `EXACT > PRIMITIVE_PAIR > ASSIGNABLE`），否则会**静默调不到**（历史 bug，提交 `f77c179c`）。
16. `turnState=0` **会抛异常**；合法值 1/2/3（含义见术语表）。
17. **苹果的状态字节 `3` 不是终点**（是重算中继态），终态只认 `null`/`0`/`2`（ADR-5）。
18. 仪表在数据不完整时会**自己编假值**（`0 m`/`<1min`）⇒ 必须"要么完整、要么清空"。

### 5.5 API 19 / Dalvik

19. **`catch (Exception)` 抓不到 `NoSuchMethodError`/`NoClassDefFoundError`**（它们是 `Error`）：老系统上调用新 API 必须用 `runCatching(Throwable)` 或版本守卫。
20. 隐藏 API 一律**反射**；`android.jar` 的 lint 检查覆盖不到 `java.*` 与 `Foo::class.java` 这类盲点。
21. **Dalvik 会在类校验期打印"解析不到的引用"**（不是崩溃）——看到这类日志先确认是否在守卫分支/`runCatching` 内。
22. **车机的 toybox/busybox 没有 `sed`**：想改一个共享 prefs 文件，**不要**用 `sed -i`（`run-as: exec failed for sed`）；用"push 一份改好的文件 + `cp` 覆盖"。
23. **`pm disable` 在本 ROM 无效**（想停用厂商 App/服务只能靠用户在设置里关，或 root 用 `pm hide`/改组件状态 —— ⚠️ 待确认最稳做法）。

### 5.6 构建与产物

24. **任何时候不要同时跑两个 gradle**（会互相锁 `classes.jar`；已发生两次）。
25. 文件锁导致的清理方式：杀掉残留 adb/logcat 进程 + 删除 `shared\build\intermediates\runtime_library_classes_jar\debug\bundleLibRuntimeToJarDebug` 后重试。
26. **认证身份已随仓库提供**（`mobile\src\main\auth-assets\offline-mfi\`），因此**不再需要** `DIPLAY_AUTH_ASSETS_DIR`；该环境变量现在只用于**替换**身份。构建失败可能留下**半成品 APK**（历史上 10.74 MB 的坏包会 `INSTALL_FAILED_INVALID_APK`，正常约 10.89 MB）。
    - ⚠️ **2026-10-11 新增：增量打包会把上一次构建的死空间留在 APK 里**。在别的会话构建过之后直接跑
      `:mobile:assembleStandaloneDebug`，实测产出 **15.87 MB** 的包：条目集合与逐条压缩长度和正常包
      **完全一致**，多出的 ~5 MB 是 zip 内的死空间（本地记录比中央目录多）。执行
      `.\gradlew.bat :mobile:clean :mobile:assembleStandaloneDebug` 重建后回到 **10,889,283 字节**
      （＝已知正常包 10,878,584 + 本次 dex 增量 28,972），`classes3.dex` 之外逐字节相同。
      ⇒ **APK 明显大于 ~10.8 MB 时不要装，先 `:mobile:clean` 重新打包**（这也解释了 §3.5① 里对不上大小时的疑虑）。

### 5.7 W1 历史事故（避免重演）

27. **音频每帧多 16 字节 0**：AEAD 的 tag 被算进明文长度 ⇒ 无线 type 102 卡顿根因（`13511e91` + 回归测试 `4953f50e`）。
28. **日志双写**：同一行写两遍，掩盖真正顺序（`83d064b4`）。
29. **"假重连"**：打开/关闭设置菜单触发不必要的重连（`0a7383af`）。
30. **`git worktree` 删除失败（Windows 长路径）**：`cmd /c rd /s /q "\\?\<绝对路径>"`。
31. **MSYS/Git-Bash 下跑 adb** 需 `MSYS2_ARG_CONV_EXCL='*'`，否则路径被转成 Windows 形式。
32. **反向对照（reverse check）**：改完行为后**故意改回旧行为**，确认相关测试**按预期失败**，再还原——这是本项目验证"测试真的在守行为"的方法。

### 5.8 W2 本轮新增的坑（**必读**）

33. **内核把 `SO_RCVBUF` 翻倍**：`setsockopt` 请求 8 KiB ⇒ 实际 16 KiB；请求 64 KiB ⇒ 实际 128 KiB。**任何时候读"接收窗口"都要用 `getsockopt` 的实际值**（app 已把这个值打进日志：`video socket accepted rcvbuf=… requested=…`）。
34. **车机侧的一切 `/proc`、`/sys`、`setprop` 都是易失的**：熄火即失效。任何"调参 → 验证"必须**在同一个点火窗口内**完成；要持久只能改 **app 设置项**。
35. **`Udp6InErrors` 不能单独用来判定"音频到了内核"**：它还会被 **ICMPv6 错误报文**推高；而我们的 `NtpClock` 有一个线程**每秒往手机发 1 个 UDP 包**（实测 `Udp6OutDatagrams` = +60/60s）⇒ 这个计数天然会被与音频无关的事件污染。老内核（3.10）还有一条"把某种丢弃错记进 `UDP_MIB_INERRORS`"的历史修正，**口径必须实测**（用 `work/lossprobe4.sh`）。
36. **`Udp6RcvbufErrors=0` 不等于"应用没问题"**（反向也成立）：它是**专门的 socket 缓冲溢出计数**；在 Eric Dumazet 的 drop-accounting 压力测试里，它和 `InErrors` 是**同时**增长的。要判定"我们读得慢"要看 `RcvbufErrors` + `/proc/net/udp6` 的 `rx_queue`/`drops` + app 的 `readsOver250Ms`。
37. **丢包是"成串"的**（平均 6.5 包、最大 34 包 ≈ 1–3 个 NCM 聚合帧 NTB）——单包随机丢失与整段丢失的**物理原因不同**，判定时要看形状，不要只看百分比。
38. **"应用内加深缓冲"治不了丢包**（ADR-12）：先看 `lateOrDuplicate` 与 `underruns` 再决定要不要动缓冲，否则只是白加延迟。
39. **切音频格式会让用户"没声音"**：`debug.diplay.audio_formats` 设为 `no-pcm` 或 `no-aac` 后，iOS 在对应链路上**完全不建音频流**；恢复必须"清属性（`setprop … ''`）+ 重启 App"。**这是危险操作，别在用户开车时做**（本会话发生过两次，均已恢复）。
40. **`debug.diplay.trace 1` 本身有负载**（交互期 15–25 行/秒字符串格式化 + 分配）：测量完记得关，否则你自己的测量被自己污染。
41. **并发会话会打断测量**（§2.5/E）：开始一轮 A/B 前，确认没有别的会话要装包/重启；一轮被打断就**作废重跑**，不要拿残段凑数（doc 51 §5.3 有一轮就是这样作废的）。
42. **内容强度不等的 A/B 会给出自信的错误结论**（ADR-19）：必须核对 `rx` 与 `kbps`；`input swipe` 的滑动次数也要记录（本会话固定为"88–95 次滑动 / 145 秒窗口"）。
43. **PowerShell 坑（本机反复踩）**：
    - `$pid` 是**只读**自动变量（用 `$appPid`）；
    - `busybox taskset -p c` 非法 ⇒ 必须写 `0xc`；
    - 双引号里写 `2>/dev/null` 会被 PowerShell 当成重定向，**创建出 `D:\dev\null` 文件**（用单引号或 `2>$null`）；
    - `Select-String` **大小写不敏感**，而 Python 的 `re` 默认**大小写敏感**（曾有 `transport=WIRELESS` vs `wired|wireless` 的统计口径错误）。
44. **按列序解析车机输出的脚本很脆弱**：本会话的探针脚本曾因"字段被 `;` 拼接"导致列错位（`$C$U` 把两个字段并成一个）。**新脚本一律用 `key=value`**（ADR-21），并且**先用合成数据自测判定分支**再上车。
45. **判定脚本的顺序会决定结论**：本会话在合成自测中发现"校验拒收"被误判成"核饱和"——判定必须按"**包在哪一步没的**"排序（socket drops → rcvbuf → 应用积压 → ICMP 污染 → 校验拒收 → 纯没到），CPU 饱和只作旁注。
46. **有线的"双路径"容易混淆**：API ≥21 走 `VpnService` + 用户态 NCM 桥；**API 19 走内核 `cdc_ncm` 网卡**（`Cs11NetdevBootstrap`），两条路径的代码不同、日志不同。看有线问题先确认走的是哪条（本机是内核网卡）。
47. **"网卡没起来"的失败是静默的**：`attachSystemNetdev()` 返回 `false` 时只写 `debugLog`，UI 上看不到 ⇒ 这就是 B3；排查时先 `adb shell ip -6 addr show usb1`。
48. **有线还会 `establish()` 一个 `VpnService`**（B5）：可能产生状态栏 VPN 提示；但**不要**在没回归的情况下直接删——它可能参与端口分配（`vpnService?.boundPort()`，见 `runStack`）。
49. **NCM 聚合帧（NTB）是最小可疑单元**：`cdc_ncm` 把多帧聚合成 ≤16 KiB 的 NTB；缺口成串（6.5 包 ≈9.4 KB、34 包 ≈49 KB）与 NTB 粒度吻合。调 `rx_urb_size`/`tx_timer_usec` 这类旋钮前，先 `ls /sys/module/cdc_ncm/parameters/` 看本内核有没有（3.10 未必有）。
50. **Dalvik 全局分配计数是 32 位且会回绕**（≈8 分钟一次）：直接用 `now - last` 会得到负数，必须做回绕校正（已实现 + 单测）。
51. **`Debug.startAllocCounting()` 的计数在交互期开销很大**：只在 `debug.diplay.trace=1` 时启用；ART 上这些计数是惰性的（首次读负值，代码据此不输出）。
52. **改测试要分清"改实现"还是"改语义"**：本轮把 `UsbMuxFrameBuffer` 改成游标缓冲后，`UsbMuxIssue100RegressionTest` 因**反射读私有 `bytes` 字段**而失败 7 例；正确修法是让测试辅助函数读"活跃窗口 `[start,end)`"，**断言语义保持不变**（不要为了让测试过而弱化断言）。

### 5.9 危险操作警告（红线）

53. **不要在车机上安装改过的第三方 APK**（用户红线）；不要把我们的包名伪装成系统应用。
54. **不要修改 `/system`**；日常运行不需要 root。
55. **不要 `git clean -fdx`**：`docs\` 不在 git 里，工作区还有大量逆向产物（`_analysis`）与实测日志（`_artifacts`、`work`）——删掉等于毁掉全部证据。
56. **不要在没有反向对照的情况下改行为型代码**（§5.7/32）。
57. **不要把 `debug.diplay.audio_formats` 设成非 `auto` 后离开**：用户会**没有声音**（ADR-13）。
58. **不要贸然 `adb reboot bootloader` / 进 i.MX6 串行下载模式**：这是唯一可能把车机变砖的一步（ADR-15）；要评估先做只读侦察。
59. **不要在用户开车/用车时做"会中断会话"的操作**（安装、重启 App、切音频格式）；先问。
60. **不要相信平均值**：本项目所有"卡顿"问题都出在**瞬时/尾部**（ADR-19、§2.3/B）。

#### W2（有线/无线链路）类

| 术语 | 含义 |
|---|---|
| **AirPlay（本项目语境）** | 苹果的流媒体协议。本项目实现**接收端（车机侧）**：RTSP 握手、H.264 视频流、AAC/LPCM 音频流、HID 反向事件、NTP 时钟、加密 |
| **iAP2** | iPod Accessory Protocol 2，苹果的配件协议：媒体元数据（NowPlaying）、封面文件传输、方向盘按键、蓝牙移交等 |
| **NCM** | USB CDC-NCM：把以太网帧**聚合成 NTB** 通过 USB bulk 传输的协议；iPhone 有线 CarPlay 的数据通道 |
| **NTB** | NCM Transfer Block：一次 USB 传输里承载的**聚合帧**（≤16 KiB ≈ **11 个 1452 字节包**）。本项目的音频/视频缺口是**成串**的（平均 6.5 包 ≈9.4 KB、最大 34 包 ≈49 KB）⇒ 与 NTB 粒度吻合 |
| **`cdc_ncm` / `usb1`** | 车机内核里的 NCM 驱动 / 它创建出来的网卡名（IPv6 link-local `fe80::2`，MTU 1500） |
| **USBMUX / lockdown** | 有线时 iPhone 的控制通道（与 iAP2 CSM 一起，构成"两条 USB 控制通道"） |
| **MFi** | 苹果的配件认证。**板上有一颗 MFi 协处理器（硬件芯片，不能模拟）**，CarPlay 认证必须经过它 |
| **LPCM** | 线性 PCM（无压缩音频）。**有线 CarPlay 的音频格式**：type 100，**134.9 包/秒、1565 kbps、1449 B/包** ⇒ 无法通过协商降低 |
| **AAC-LC** | 有损音频编码。**无线 CarPlay 的音频格式**：type 102，**47.8 包/秒、252 kbps、658 B/包** |
| **RTP / 序列号** | 实时传输协议与其递增序号。序号"向前跳"= 中间包**永久丢失**；序号乱序/迟到 = **抖动** |
| **抖动（jitter）vs 丢包（loss）** | 抖动 = 包**迟到但会到**（缓存能救）；丢包 = 包**永远不来**（缓存救不了）。本项目有线实测 `lateOrDuplicate=0` ⇒ **是丢包不是抖动** |
| **underrun（欠载）** | 播放缓冲被抽干（`AudioTrack` 无数据可播）。本项目有线实测 **0** ⇒ 缓冲从不缺 |
| **`SO_RCVBUF` / 接收窗口** | socket 接收缓冲大小。**内核会把请求值翻倍**（请求 8 KiB ⇒ 实际 16 KiB）——这是本项目最大的一个隐性坑 |
| **老化阈值 / `dropped`** | 视频帧若"等到解码时已比到达时刻晚超过阈值（默认 250 ms）"就被**主动丢弃**，计入 `dropped`，以保持画面与手指对齐 |
| **`maxGap`** | 视频窗口内**最大接收间隔**（ms）⇒ 反映"卡了多久没数据" |
| **`touch2frame`** | **触摸事件到画面响应**的中位延迟（ms）⇒ 最贴近用户"滑得跟不跟手"的观感指标 |
| **softirq / NAPI / RPS** | 内核收包下半部（softirq）、轮询收包（NAPI）、把软中断分派到指定核（RPS）。本机 USB IRQ 在 **CPU1**、以太网 IRQ 在 **CPU0** |
| **`Udp6InErrors` / `Udp6RcvbufErrors` / `sockDrops`** | 三个不同层级的"丢包/错误"计数：UDP 层错误（**可能被 ICMPv6 污染**）/ socket 缓冲溢出 / socket backlog 丢包。**判定丢在哪一步必须同时看这三个 + `/proc/net/udp6` 的 `rx_queue`** |
| **ICMPv6 错误** | 对端回的"不可达/端口不存在"等报文；它会**污染** `Udp6InErrors`（本项目自己的 `NtpClock` 每秒上行 1 个 UDP，天然会引入这类计数） |
| **GC / Dalvik / ART** | 垃圾回收 / Android 4.4 的运行时（本项目） / 5.0+ 的运行时（更快 GC，但本项目**不升级**，见 ADR-15）。本机 GC 停顿实测 **37–67 ms** |
| **分配率（allocation rate）** | 每秒新分配的字节数——驱动 GC 频率。本项目用 `Debug.startAllocCounting()` 系列计数实测（**只在 trace 时开**），估算约 **4.3 MB/s** |
| **内容强度代理（content proxy）** | 用来判断两次 A/B 跑的"内容量"是否相当的指标：`rx` 均值与 `kbps` 中位数（本会话的高内容区间约 `rx≈20`、`kbps p50≈3000`） |
| **交错 A/B（interleaved）** | 基线 60s → 改动 60s → 基线 60s → 改动 60s 的测量协议（ADR-19） |
| **trace** | 本项目的详细调试日志总开关（`debug.diplay.trace=1`）；开启会带来可观负载，测完要关 |
| **探针（probe）** | 车机上以 0.5 秒为周期采样内核计数/中断/逐核负载的 shell 脚本（`work/lossprobe2/3/4.sh`） |
| **`.xcap`** | `AudioPacketCapture` 产出的音频逐包抓包格式（wire/RTP/时间戳/错误），默认关闭 |
| **FUSE / sdcard** | Android 4.4 的外部存储实现：`/storage/emulated/*` 由 FUSE 守护进程提供，权限是"合成"的；本机没有 `/storage/emulated/0`（§5.3） |

## 8. 自检：以"完全不了解项目的人"的视角重读

> 本节按用户要求执行：读完后**列出仍然无法理解或无法直接执行的地方**，并就地补充说明。以下 15 条是自检发现的问题与补充。

**Q1：我照本文能跑起来，但我怎么知道"车上装的那一版"是不是我构建的这一版？**
⚠️ 这是本文写作时**唯一无法确定**的运行态事实（车机离线）。补充：第一次上车先核对
```powershell
& $adb -s $car shell "dumpsys package com.shihab.diplay.hudtest | Select-String -E 'versionName|lastUpdateTime'"
Get-FileHash 'D:\Development\DiAuto-DiPlay\CarPlay-CS11\mobile\build\outputs\apk\debug\mobile-debug.apk' -Algorithm SHA256
# 参考：2026-10-10 17:51 车上那版 = 9E4092B542B6A92E0FFE5BF65CD1C5A01164F99A205DA7EFD2532D5ACF121F83
```
若版本号相同但不确定，**直接重装一次**（代价是中断用户会话，先问）。

**Q2：`docs/` 不在 git 里，那我 `git clone` 之后是不是就"瞎了"？**
是。补充：**接手者必须先拿到完整工作区**（`CarPlay-CS11` + `docs` + `work` + `_analysis` + `_artifacts` + `_upstream` + `tools`）。只 clone 仓库会失去全部知识库、探针脚本与实测证据。这也是 §5.9 第 55 条禁止 `git clean -fdx` 的原因。

**Q3：探针脚本说"经 root 通道执行"，但 root 从哪来？**
已在 §3.5④ 补充完整链路：`modprobe` 劫持 → `mp.sh` → `rootd` 队列守护；**每次重启都要重跑 `tools/cs11_root_fire.sh`**；并给出了"队列卡死"的已知故障与处置。若 `rootd` 不在（例如别的会话动过），先修 root 链再谈测量。

**Q4：`Udp6InErrors` 到底算不算"我们的音频包"？**
本文明确标注为**未定论**（§2.3/B、ADR-20），并给出判定工具与判读表。补充：**在拿到该结论前，不要基于"丢包发生在内核"去做改动**。

**Q5："仪表专辑封面"的实验里，车机上没有 `curl` 怎么办？**
已在 §6.1 改为 `busybox wget`（本机有 busybox，没有 curl）。⚠️ 待确认：若该 busybox 未编译 wget，退化方案是**从 PC 侧发起请求**（用 `adb forward tcp:<P> tcp:<P>` 把车机回环端口转发到 PC，再用 PC 的 curl/浏览器取图）——这会改变"来源进程"，判定时要注意。

**Q6：我完全不知道"导航卡片"长什么样，怎么验收？**
补充：仪表媒体卡片显示 4 类导航要素——**转向箭头图标**、**下一路口路名**、**到下一路口的距离**、**到目的地的剩余距离/剩余时间**；起步阶段显示"前往路线"。**建议第一天上车用手机拍下仪表照片存档**（本文与 doc 53 都没有截图，这是文档的一个真实缺口）。

**Q7：什么是"高内容强度"？有没有绝对门槛？**
补充经验区间（【事实】，来自本会话 A/B）：高内容 ≈ `rx` 均值 **20**、`kbps` 中位 **3000–3400**；低内容 ≈ `rx` **13–17**、`kbps` **1900–2200**。**两侧 `kbps` 中位数相差超过约 30% 就应判该轮无效并重跑**。

**Q8："88–95 次滑动 / 145 秒窗口"这个协议在哪里？**
在 `work/inject_window.ps1`（配合 `work/lossprobe3.sh` 或 `lossprobe4.sh`）。补充：注入用 `adb shell input swipe`，**每次注入会起一个 `app_process`**，本身消耗 CPU（§5.2/11）。

**Q9：无线侧的对照基线数字（`dropped=0`、`maxGap` 122–151 ms、`touch2frame` 56–63 ms）能直接和有线比吗？**
⚠️ 待确认：那些数字来自 doc 40，采集条件（内容、负载、是否注入）与 W2 的有线 A/B 不完全相同。**只可作参考量级**；要严格对比必须在**同一天、同一车机、同一注入协议**下重采两侧（doc 51 §9 就是按这个方法做的）。

**Q10：`FirstTcpWatchdog` 接到有线时要怎么拿到"StartSession 已发出"的时点？**
⚠️ 待确认（实现 B1 前必须先读代码确认）：无线侧是通过控制客户端的 `onStartSessionSent` 回调（`CarPlayController.kt` 约 1147 行）喂给看门狗的；**有线控制客户端 `Iap2WiredControlClient.run(...)` 是否暴露同等回调需要先确认**，若不暴露，需要在有线客户端里加一个回调或在"发送 0x4301"处直接打点。

**Q11：B4（"线在即有线"）会不会让用户想用无线时反而被切走？**
补充：需要**明确产品语义**——建议：仅在"USB 上确实有 iPhone 且当前没有活跃无线会话"时收敛；若无线会话已建立，则**不打断**，只更新连接页提示。取舍要在实现时与用户确认一次。

**Q12：`compileSdk` 到底是多少？**
⚠️ 待确认：本文只确认了 `targetSdk=37`、`minSdk=19`。接手者读各模块 `build.gradle.kts` 的 `compileSdk` 一行即可补齐（不影响开工）。

**Q13：文档编号有重复（例如 40、47 各两篇），是错误吗？**
不是错误，是历史追加（同一天写了两个主题，沿用同一编号）。**按文件名检索，不要假设编号唯一**。

**Q14：`rootcmd.running` 残留导致 root 队列卡死，我能自己修吗？**
可以，但顺序很重要（doc 40 记录）：先确认 `ps` 里有 `rootd.sh`、看 `/data/.android/rootcmd.running` 属主与大小；`busybox killall -9 rootd.sh` **杀不掉**（实测），正确做法是**重跑 `tools/cs11_root_fire.sh` 重建整条链**。**不要**在没有把握时清空 `/data/.android/`（那里还有 `mp_run.txt` 等证据）。

**Q15：如果我只想"让用户马上更顺一点"，最快的三件事是什么？**
按收益/风险排序（都不需要改代码）：
1. **关车机「语音唤醒」与「应用商店自动更新」**（A4，腾出 0.3–0.7 核）；
2. **关 `debug.diplay.trace`**（trace 本身有负载）；
3. 有线时把**视频接收窗**再往小试一档（`setprop debug.diplay.video_rcvbuf 4096` → 实际 8 KiB；重连生效），观察 `dropped`/`touch2frame` 是否继续改善（ADR-11 已验证 4 KiB 请求略优，只是当时为 1080p/60 留余量才定 8 KiB）。
