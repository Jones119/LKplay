# 29 · CS11 车机系统级审计（点火实测）＋ CarPlay 品牌落地

> 目的：用户要求「看车机固件有什么可以优化」，并且**不是**优化我们的 app，而是**车机系统本身**。
> 方法：点火状态下全程 adb 只读实测（不猜测），再用 rootd 队列以 root 落地可逆调优。
> 时间：2026-10-07 22:4x（开机约 4 分钟的新鲜系统，所以调优项**都是易失的**）。

## 1. 结论摘要

1. **车机最主要的一处系统级损耗：`ssi@0202c000`（i.MX6 SSI2，娱乐音频 I2S 链路）以约 48,100 次/秒持续中断，且 100% 压在 CPU0。**
   实测 CPU0 的 `irq=16.8% + softirq=6.5%`（≈23% 一个核）全来自它；CPU1~3 的 `irq` 只有 0.7~0.9%。
   **根因是驱动/硬件级"每采样一次中断"（48kHz）**：与是否有音频流无关——AudioFlinger 输入线程处于 `standby: 1` 时速率仍是 48,129/s；把常驻采集进程强杀（立刻以新 PID 重生）后仍是 48,012/s。
   **用户态无法消除**（`/proc/irq` 只能改亲和，不能关；无内核模块可调），**只能规避**。
2. **常驻语音唤醒确实存在**：`com.baidu.che.codriver`（PID 2957 等）长期持有 **16 kHz 单声道采集**（AudioFlinger `Input thread` `standby: 0`、`active tracks` 有 client、挂 1 个 effect chain）。它自身也吃 **7.8% + 3%(`:remote`) CPU**。但**它不是中断风暴的成因**（见 1 的对照实验），且这台 ROM 的 `pm` **无法禁用它**（`pm disable`/`pm disable-user --user 0` 都返回 rc=0 却不生效，进程杀后立刻重生）。
3. **可规避的规避已经做了**：把 Wi-Fi SDIO 中断与网络软中断挪到 CPU1、把 app 绑定到 CPU2+CPU3，让 CPU0 独自承受那条无法消除的风暴。

## 3. 本轮已落地的优化

### 3.1 系统调优脚本（新增 `tools/cs11_wireless_tune.sh`，经 rootd 以 root 应用）

```
irq55=2  irq72=2  irq75=2        # Wi-Fi SDIO + USB 中断：CPU0 → CPU1
wlan0 rps_cpus=2                 # 接收软中断同核（CPU1），原来 RPS 是关闭的(=0)
netdev_max_backlog=4000          # 原 1000
rmem_max=2097152  rmem_default=524288   # 原均 163840
read_ahead_kb=512                # mmcblk2，原 128
ksoftirqd/0..3 renice -5         # 网络软中断线程优先于 app
app 亲和 f(0-3) → c(CPU2-3)      # 避开 CPU0 风暴与 CPU1 网络中断
```

设计说明（写进脚本注释）：**CPU0 = 音频风暴 + 杂项；CPU1 = Wi-Fi 中断 + 收包软中断；CPU2+CPU3 = app**。
这是把「不可修的 48k/s 风暴」隔离出去，让 CarPlay 三路（视频/音频/触控）拿到干净的两个核。

> 易失性：全部重启即失。重建 root 链后重跑脚本即可（见 §6）。app 未运行时脚本会跳过绑核并提示——**app 启动后需再跑一次**（或后续做持久化钩子）。

### 3.2 无需 root 的全局 UX 设置（已生效，持久）

```
settings put global window_animation_scale 0.5
settings put global transition_animation_scale 0.5
settings put global animator_duration_scale 0.5
```
整个车机 UI 的动画时长减半，操作"跟手感"提升（对 4.4 老车机观感改善明显）。想更激进可设 0（关闭动画）。

## 4. 想改但改不了的（如实记录，避免下次重复研究）

1. **SSI2 每采样中断无法从用户态消除**：`/proc/irq/79/smp_affinity` 只能迁移落点；`bcmdhd` 那类模块参数在 `imx-ssi`/`dirana` 上没有暴露；要修必须改内核驱动（DMA/period 配置）。**结论：接受它，把它隔离在 CPU0。**
2. **语音唤醒无法禁用**：`pm disable` / `pm disable-user --user 0` 均 rc=0 不生效，强杀即重生（有守护/自启）。若你不在意唤醒词，可尝试在**车机设置里关掉"语音唤醒"**（厂商入口，最干净）；那能省掉 `codriver` 的 ~11% CPU 与常驻采集，但**不会**消掉 §1.1 的风暴。
3. **Wi-Fi 省电/DTIM 无旋钮**：`bcmdhd` 只暴露 `clockoverride/dhd_doflow/dhd_dpcpoll/dhd_console_ms/op_mode/...`（无 PSM 开关）；要调只能改 NVRAM 固件参数（需 root+重启，且风险高，未做）。
4. **`com.ecarx.appstore` 6% 后台占用**：属厂商应用商店，禁用同样受 `pm` 限制；建议在车机设置里关掉"自动更新"类开关（未验证是否有该开关）。

## 6. 复现 / 操作命令

```bash
# 0) root 链在重启后必失，重建（MSYS 下必须禁掉路径转换，否则设备路径会被改写！）
MSYS2_ARG_CONV_EXCL='*' MSYS_NO_PATHCONV=1 bash tools/cs11_root_fire.sh 0123456789ABCDEF
#    成功标志：输出里出现 rootd 进程（/system/bin/sh /data/.android/rootd.sh）

# 1) 应用系统调优（rootd 队列，1 秒内执行，输出落 rootout.txt）
adb -s 0123456789ABCDEF push tools/cs11_wireless_tune.sh /data/.android/rootcmd.sh
adb -s 0123456789ABCDEF shell "cat /data/.android/rootout.txt"

# 2) 中断速率测量（基准与对照都靠它）
adb -s 0123456789ABCDEF shell "cat /proc/interrupts"   # 取两次、本地求差，不要依赖设备端 awk/paste
```

**本轮踩的坑（避免重犯）**：
- **`/proc/stat` 列名两次读错位**，把 idle 当 system，得出了"4 核 90% 忙"的假警报。正确列序：`user nice system idle iowait irq softirq`（聚合行还要先去掉行首 `cpu` 标记）。**先打印一行原始数据核对再下结论。**
- 设备端 **toolbox 没有 `printf`/`tr`/`tail`/`paste`**；busybox 有 `awk/grep/ps/taskset/renice` 但**以 root 身份跑特权操作时 busybox 会自降权**（`chmod` 失败即此因）——特权操作只用 `toolbox` + shell 内建重定向。
- **MSYS 会把 `/data/...` 改写成 `D:/Dev Environment/msys64/data/...`**，导致 push 全部失败；必须 `MSYS2_ARG_CONV_EXCL='*'`。
- **APK 体积异常之谜**：归档基线 APK 与本次 APK 的**条目未压缩合计只差 0.8 MB**（正是删掉的 50 个 BYD 资源 + 代码），但文件大小差 6.15 MB——差值全在 **ZIP 容器开销（31% vs 3%）**，即**增量打包残留的填充/陈旧字节**。教训：**判断产物完整性要比条目内容（未压缩大小/哈希），不要比文件大小**；归档前最好 clean 打包一次。
