## 1. 项目概览

### 1.1 目标与背景

**目标**：在这台领克 CS11 车机上，用一个**自行开发、装在车机上的 Android 应用**（不是外挂盒子、不是改车机固件），实现：

1. iPhone 通过 **CarPlay** 把画面/声音/触控/麦克风交给车机；
2. 车机的**液晶仪表盘**（驾驶员前方那块屏，不是中控大屏）上显示**导航指引**（箭头、路名、距离、剩余时间）与**媒体信息**（曲名/歌手/专辑/进度/封面）；
3. 一些体验细节：屏幕四角圆角遮罩、方向盘按键、隐藏系统栏、图像缩放等。

**为什么做**（业务/技术动机）：

- **事实**：这台车机出厂**不支持 CarPlay**（只支持原厂的"随心听"音乐、百度地图导航、"亿咖通 ECARX" 自家的互联方案）。车主想用 iPhone 的 CarPlay。
- **事实**：车机是 Android 4.4.3，**API 19**，Dalvik，且**厂商对系统 API 做了大量定制与阉割**（例如没有 `/storage/emulated/0` 这一路径，见 §5.3）。直接拿现代代码跑会各种 `NoSuchMethodError`、`NoClassDefFoundError`。
- **事实**：仪表盘**不接受普通的 Android 投屏**（全车只有一块 display，见 §4.3），只能通过厂商的"**DIM**"（见术语表）数据接口把文字/箭头/图片 URI 推给它。
- **动机**：把 CarPlay 体验做"像原车一样"——尤其是仪表上的导航与音乐，这是车主日常最需要的两块。

### 1.2 项目来源与许可

- **事实**：本仓库是开源项目 **DiPlay**（GitHub `shihabal3amri/DiPlay`）的 **fork**，许可 **GPL-3.0**。原项目实现的是 CarPlay 接收端（AirPlay 协议 + iAP2 配件协议）。
- **事实**：本 fork 的分支名 `cs11-api19`，提交历史里所有 `fix(cs11):` / `feat(cs11):` / `perf(cs11):` 开头的提交都是为本车机做的改动。
- **事实**：仓库**不合并上游**（约定：手工移植上游修复，并把上游的测试一起带过来，见 §4.2）。

### 1.3 成功标准与验收方式

**成功标准**（按重要性）：

1. **能连上并稳定用**：无线/有线 CarPlay 连接成功，画面流畅（目标：不卡顿、不断连），声音正常。
2. **仪表导航可用**：箭头（白色，与原厂一致）、路名、距离、剩余时间；起步阶段显示"前往路线"；路线重算时卡片不闪。
3. **仪表媒体可用**：曲名/歌手/专辑/进度正确；**封面能显示并随曲目切换**（当前未达成）。
4. **不破坏车机**：不修改系统分区、不装改过的第三方 APK、不需要 root 做日常运行。

**验收方式**（**事实**，项目既有流程）：

- **单元测试**：`.\gradlew.bat :shared:testDebugUnitTest :common:testDebugUnitTest --continue --offline`，从 `<module>\build\test-results\testDebugUnitTest\*.xml` 聚合用例/失败数。**基线必须不增长**（见 §2.5）。
- **实车验收**：每次点火按 `docs/_digest/28-CS11上机验证清单（点火窗口）.md`（下称 **doc 28**）与 `docs/_digest/50-本次点火验收单.md`（**doc 50**）逐条打勾；判据全部是**日志关键字**或**仪表上肉眼可见的现象**。
- **日志取证**：每次上车必须后台抓 `adb logcat -v time > _artifacts\car-session-<日期>.log`（车机 adb 会掉线，必须用自愈循环，见 §5.2）。

### 1.4 关键约束

- **技术**：目标 API 19 / Dalvik；**任何 ≥API 21 的调用必须隔离在专门的"持有者类"里**（见 §4.7），否则老系统上会崩。
- **兼容目标只有车机**：小米平板只做"没有车机时的次选冒烟测试"，**不为兼容平板做取舍**（用户明确要求）。
- **合规/安全**：不装篡改过的第三方 APK；不改系统分区；运行期不需要 root（只有**调试**时会用 adb 读 `/system`、拉 jar、看 `/sdcard`）。
- **成本约束（很重要）**：**车机每次 adb 安装都会中断当前 CarPlay 会话**，用户要重新连接。因此约定：**多改一次、少装一次**——把同一轮的多项修复合并成**一次构建+一次安装**（见 §5.1）。
- **性能**：车机 CPU 弱（i.MX6Q，无硬件 AAC 解码、无硬件 Opus 解码），一切"软件编解码"都要先算 CPU 账。

### 2.3 【进行中】当前唯一卡点：仪表专辑封面

**现象**（**事实**）：播放音乐（Apple Music / QQ 音乐都试过）时，仪表媒体卡片显示曲名/歌手/专辑/进度，**封面区域空白**；换曲也不出现。

**已经排除的可能**（每一步都有实证，**这些是真实修复，不是白干**）：

| 交付形式 | 厂商是否收到（日志证据） | 仪表是否画 |
|---|---|---|
| `content://com.shihab.diplay.hudtest.artwork/covers/<session>/<uuid>.jpg` + `grantUriPermission`（`grants=2 provider=true`） | ✅ 3 个不同 UUID | ❌ |
| `file:///storage/emulated/0/Android/data/<pkg>/files/cluster-artwork/…` | ✅ | ❌ |
| `file:///sdcard/DiPlay/cluster-artwork/<session>/<uuid>.jpg` | ✅ 36+6 次 | ❌ |
| `http://127.0.0.1:<port>/covers/<session>/<uuid>.jpg`（回环 HTTP） | ⏳ 未验（代码已就绪） | ⏳ |

**关键旁证**（**事实**）：

- 车机**自带的**"随心听"音乐应用，其封面在仪表上**能显示、且随曲切换**；它交给仪表的是 `http://y.gtimg.cn/music/photo_new/….jpg`（在线曲）与 `file:///sdcard/Music/mediacenter/images/<专辑>-<歌>-<歌手>.jpg`（本地曲）。
- 第 3 行那条 `/sdcard/DiPlay/…` 路径**确实可被别的进程读取**：`adb shell ls -l` 显示 `-rw-rw---- root sdcard_r`（与车机自带应用同款），`adb shell cat <路径> | wc -c` 能读出完整 31326 字节。
- **逆向参照实现 EasyPlay v71 发现**（**事实**，见 doc 52）：它在**本机这一类机型**（`sdk==19 && Freescale && CS11`）上**主动把封面通道切成"回环 HTTP"**，服务器 `bind(127.0.0.1, 0, backlog 4)`、路径 `/covers/<session>/<uuid>.jpg`。这强烈支持"回环 HTTP 是本机上的正解"。

**当前假设**（**推测**，有上述证据支持）：仪表的取图方**只对 `http://` 发起抓取**，`content://` / `file://` 只被记录不被加载。

**本轮已做的事**（**事实**）：

1. 实现了**回环 HTTP 图床**（进程内 `ServerSocket` 绑 `127.0.0.1` + 端口 0，只服务已登记的封面文件，完整 404 兜底，4 线程上限，流式发送）；
2. 加了一个**决定性实验开关** `debug.diplay.artwork_uri`：可把一个指定 URL 直接交给仪表（用于验证"取图方到底抓不抓我们给的 URI"）；
3. 修掉四个可能让 HTTP 档**静默失效**的缺陷（提交 `5051fef1`）：
   - **D1**：HTTP 服务原本随宿主 Activity 销毁而关闭（`onDestroy → detach() → close() → shutdown()`），而 CarPlay 会话比 Activity 活得久 ⇒ 仪表懒取图时可能是 `connection refused`，**而日志一切正常**。现改为**进程级单例**，只在会话真正结束时 `release()`。
   - **D2**：已交付的封面可能被 retention 回收（上限原为 4）⇒ 仪表握着的 URL 变 404。现改为**只统计未交付副本**、已交付的**永不回收**，上限 32。
   - **D3**：绑定失败会**静默**降级到 `file://`（本车已证伪）。现为 `Log.e` 并写明"降级到本 ROM 从未画出过的档"。
   - **缺仪器**：HTTP 服务原本一行日志都没有 ⇒ "仪表没来取"与"我们没记录"无法区分。现**每个请求一行**：`cluster artwork http request method=GET path=… status=200 bytes=…`。

### 3.3 核心文件与调用关系

**A. CarPlay 启动与会话编排（`shared/.../orchestration/CarPlayController.kt`）**

- 负责发现/连接 iPhone、建立 AirPlay 会话（RTSP 握手）、启动音频/视频/触控/麦克风通道、无线与有线的切换。
- 数据流（无线，**事实**）：`Wi-Fi（车机热点）` → `AirPlay 会话` → 视频 H.264 经 `ScreenStream` → `AndroidMediaSink`（MediaCodec 硬解）→ `TextureView` 上屏；音频 type 102（AAC-LC，AES-CBC 加密）→ `AudioRenderer` → `AudioTrack`；触控反向走 HID；麦克风上行 Opus → iAP2/AirPlay 语音流。

**B. 仪表集群桥接（`shared/.../media/VendorClusterBridge.kt`，本项目最核心的定制文件）**

这是**本项目的灵魂**：它通过**反射**调用厂商 **DIM** 接口（`com.ecarx.xui.adaptapi.diminteraction.DimInteraction`，类在 `/system/framework/ecarx.adapterapi.jar` 内），把导航与媒体数据推给仪表。要点：

- 对象获取：`DimInteraction.create(Context)` → `getNaviInteraction()` / `getMediaInteraction()`；
- 导航方法（与工厂导航**完全相同**的 8 个）：`updateTurnByTurnArrow(int)`、`updateNextGuidancePointName(String)`、`updateDistanceToNextGuidancePoint(int)`、`updateDistanceToDestination(int)`、`updateETA(int)`、`updateDriveDirection(int)`、`notifyTurnByTurnStarted()`、`notifyTurnByTurnStopped()`；
- 媒体方法：`updatePlaybackInfo(IPlaybackInfo)`、`updateCurrentSourceType(int)`、`updateCurrentProgress(long)`；
- 关键机制（**事实**）：
  - 反射必须**按重载匹配**（`VendorMethodMatcher`，同票优先 `EXACT > PRIMITIVE_PAIR > ASSIGNABLE`），否则会静默调不到（历史 bug，提交 `f77c179c`）；
  - 导航卡片遵循"**要么完整、要么清空**"（避免仪表显示 `0 m`/`<1min` 假数据），并带 **3 秒去抖**（重算路线时不清卡，提交 `d70aecf8`）；
  - 箭头 id 使用**工厂族 101–143**（提交 `d730d58c`），并可用 `debug.diplay.arrow` 属性热改；
  - 媒体封面走 `ClusterArtworkTransport`（四档交付：HTTP → file → content → 无）。
- 开关：持久化设置 `cluster_bridge_enabled`（**默认开**，无需 adb；调试可用 `debug.diplay.cluster` 覆盖）。

**C. 封面管线（`shared/.../media/`）**

| 文件 | 作用 |
|---|---|
| `ClusterArtworkTransport.kt` | 编码（JPEG 质量阶梯 88→62→45、最长边 ≤256px、1 B–1 MiB、每张新 UUID）、候选路径探测与交付、保留策略、`debug.diplay.artwork_uri` 覆盖 |
| `ClusterArtworkHttpServer.kt` | 回环 HTTP 图床（`ServerSocket` 绑 `127.0.0.1` 端口 0；进程级单例；会话结束才释放；每请求一行日志） |
| `common/.../ClusterArtworkProvider.kt` | `content://` 提供者（`authority = <applicationId>.artwork`），作为兜底 |
| `common/.../ClusterArtworkAssociation.kt` | "当前曲目身份 + 封面留存"状态机（解决"只有第一首有封面"） |

**D. 宿主层（`common/.../CarPlayHostActivity.kt`，约 4800 行）**

- 承载 CarPlay 画面的 `FrameLayout` + `TextureView` + **三指手势层**（`gestureLayer`）+ 可选的**四角圆角遮罩**（`CarPlayCornerMaskOverlay`，插在画面与手势层之间）；
- **手写的设置界面**（不是 XML 布局，是代码构建的 LinearLayout 菜单）：分类标题 + 开关/滑块行；
- 持久化统一走 `common/.../AirPlayPersistence.kt`。

**E. API-19 兼容层（**重要约定**）**

- ≥API 21 的调用必须放进专门类：`shared/.../transport/Api21Configuration.kt`、`shared/.../media/OpusEncoderSupport.kt`（内部 `Api21CodecList`）、`common/.../Api33Locale.kt` 等；

### 3.6 数据来源与格式

- **导航数据**：来自 iPhone（Apple 地图等）通过 AirPlay/iAP2 上报的路线指引；经本项目解析成"箭头语义 + 路名 + 距离 + 剩余时间"，再推给仪表。
- **媒体数据**：来自 iPhone 的 NowPlaying 元数据 + iAP2 封面文件传输（JPEG/PNG 原始字节，带上限 32 文件 / 256 KiB）。
- **仪表侧"权威日志"**（**事实**，判据来源）：厂商 DIM 服务（进程 `com.ecarx.dim_interaction`）会打印它**收到**的导航六元组，格式形如：
  ```
  <turnState>  <roadName>  <distanceToDestination>  <etaSeconds>  <null>  <speedLimit>
  例：10  新城路  494042  20640  null  1        （10 = 工厂族某个箭头 id）
  例：-1  前往路线  494302  20880  null  21      （-1 = 我们主动隐藏箭头槽位时）
  ```
  拿我们**发送**的值与这行**逐字对照**，是判断"桥接是否真的生效"最快的方法。

## 4. 关键决策记录（ADR 风格）

### ADR-1：只以 CS11（API 19）为兼容目标，平板仅做冒烟测试

- **决策**：所有兼容性取舍以车机为准；小米平板（Android 15）只用于"没有车机时验证功能是否还活着"。
- **背景**：车机是 API 19/Dalvik，平板是 SDK 35/ART，两者差异巨大；同时照顾两者会让代码充满分支。
- **备选与否决**：①"两边都支持"——被否，成本高且车机才是交付对象；②"只支持平板"——荒谬，平板不是交付对象。
- **后果**：代码里可以有"老系统专用路径"（如软件 Opus 兜底）；接手者**不要**为平板的异常行为改核心逻辑。

### ADR-2：手工移植参照实现（EasyPlay / HyLink），不合并上游

- **决策**：从反编译的参照实现里"读懂机制 → 自己写 → 带单元测试 → 提交"，**不做** git merge/rebase 上游。
- **背景**：上游 DiPlay 与我们的 fork 已大幅分叉；参照实现（EasyPlay v71、HyLink）是**闭源**的，只能逆向学习机制。
- **备选与否决**：直接合并上游——历史教训是冲突巨大、且上游没有本车机的定制。
- **后果**：每次移植都要写清"证据出处（文件:行号）"到 `docs/_digest/42…`、`52…` 这类文档里；`⚠️ 待确认`：上游若有关键安全修复，需要人工评估是否移植。

### ADR-3：仪表走 DIM 数据注入（路径 A），放弃"投屏/镜像"（路径 B）

- **决策**：仪表内容全部通过厂商 DIM 接口**按字段注入**；不做第二 display 投屏。
- **背景与证据**：`dumpsys display` 显示**全车只有一块 display**（`内置屏幕 1920x1080 BUILT_IN, mDisplayId=0`），仪表不是 Android 独立 display。
- **备选与否决**：用 `Presentation` 投到副屏——**物理上不可能**（没有副屏）；用截图镜像——成本高、且仪表还要吃厂商的私有渲染通道。
- **后果**：代码里的"仪表内容模式（alt-screen）"相关路径在本车是**永久空转**（如 `CarPlayClusterDisplay.Content`、安全区 px 化）；接手者不要在这上面花时间。

### ADR-4：箭头 id 使用"工厂导航族"（101–143），不用参照实现的旧族（1–45）

- **决策**：把 Apple 的机动类型映射到车机**原厂百度导航使用的整数 id 族**（左转 102、右转 103、左前/分支 104、右前/分支 105、掉头 106/107/108、直行 109、环岛 111、环岛出口 112、目的地 115、环岛左/右 141/142、环岛掉头 143）。
- **背景**：我们用 DIM 门面推箭头（整数 id），仪表自己决定图标与颜色；最初照搬参照实现 EasyPlay 的 1–45 族 ⇒ 实车箭头是**黄色且偏左**，而原厂导航是**白色**。
- **证据**：反编译车机自带百度导航（`_analysis/cs11_vendor/naviauto_src/.../com/baidu/a/a.java:30-87`）得到它的静态 id 表；实车换族后**箭头变白** ✅。
- **备选与否决**：保留 1–45 族——实车否证（颜色不对）；同时提供两族开关——被否，增加状态。
- **后果**：`debug.diplay.arrow` 属性保留用于上车扫 id；已知"渡轮"类在工厂族里没有对应图标，暂用直行 109（**待确认**是否需要别的处理）。

### ADR-5：导航卡片"要么完整、要么清空"，并带 3 秒去抖

- **决策**：只有当快照"可显示"（路线状态在允许集合内、箭头可映射、距离/时间在合理范围）才提交卡片；否则**清空**；但清空**延迟 3 秒**（去抖）。
- **背景**：仪表在收到不完整数据时会自己显示 `0 m`/`<1min` 之类的假值（观感差）；而路线重算时 iPhone 的快照会短暂不完整 ⇒ 若立即清空，仪表会"闪一下"。
- **证据**：实车日志显示每次重算都是"清卡 → 1.6 秒后重建"；参照实现有 `EMPTY_LIST_HIDE_NS = 3s` 的去抖而我们漏了（doc 46 §3/G5）。
- **反直觉细节**（**事实**）：苹果上报的状态字节 `3` **不是终点**，而是重算中继态（实车恒为 `5 → 3 → 1`，新路线开局也出现 3）。把它当终点会让闪烁从 1.6s 缩到 0.49s，**仍然看得见**。终态只认 `null`/`0`/`2`。
- **后果**：`cluster card held (incomplete 0.x/1.x s)` 与 `cluster card cleared (…)` 成为验收关键字。

### ADR-6：封面交付"四档"，回环 HTTP 为首选

- **决策**：封面以 `http://127.0.0.1:<port>/covers/<session>/<uuid>.jpg` 交付（首选），失败依次降级 `file://`、`content://`。
- **背景与证据链**：`content://`（带 grant）、应用沙箱 `file://`、正确的 `/sdcard/DiPlay/…` `file://` **三种交付厂商都收到了，仪表一张都没画**；而车机自带应用用 `http://` 的封面**能画**；参照实现 EasyPlay 在 `sdk==19 && Freescale && CS11` 的机型门禁下**主动选 HTTP**（doc 52）。
- **备选与否决**：继续调 `file://` 的路径/权限（已三次否证）；用 `Bitmap` 交付（**事实**：逆向表明交付路径上只有 `Uri`，没有 Bitmap/byte[]，HyLink 也一样）。
- **后果**：新增了一个进程内 HTTP 服务（生命周期、端口、越权防护都需维护）；并且**验证"取图方到底有没有来取"必须看新加的请求日志**。

### ADR-7：API-19 隔离约定 + 反射读隐藏 API + 守卫测试

- **决策**：所有 ≥API 21 的类/方法放进"版本持有者类"；所有隐藏 API 一律反射；加测试看守。
- **背景与证据**：API 19 上 `Math.floorDiv/floorMod(long,long)`（API 24）会抛 `NoSuchMethodError`，而 `catch(Exception)` **抓不到 `Error`** ⇒ 曾经是一个必然崩溃点（实车已确认修复）；Dalvik 还会在**类校验期**打印所有解析不到的引用（实车采集到约 100 条）。
- **备选与否决**：不隔离、直接调用——被实车风险否证；靠 lint——`android.jar` 检查覆盖不到 `java.*` 与 `Foo::class.java` 这类盲点（历史教训）。
- **后果**：见 §2.5/B 的剩余技术债清单（不影响功能，但约定应继续遵守）。

### ADR-8：能热调的都用"调试属性"，能持久的都用"设置项"

- **决策**：上车实验用系统属性（`debug.diplay.*`，熄火即失效）；必须跨点火保留的用持久化设置（如 `cluster_bridge_enabled`、屏幕四角圆角遮罩）。
- **背景**：历史教训——仪表推送开关最初是 adb 属性，一次点火后丢失（doc 38）。
- **后果**：接手者新增开关时**默认应做成设置项**；只有"一次性实验"才用属性。

### ADR-9：日志纪律（每次变化一行、每进程一次、不做逐帧刷屏）

- **决策**：状态变化才打日志；同一原因的告警每进程只打一次；判据关键字要在文档里写明。
- **背景**：历史上同一行日志被写两次（提交 `83d064b4`）；逐帧日志会淹没真正的判据。
- **后果**：验收依赖**精确关键字**（例如 `cluster artwork tier=http port=… uri=…`），所以**改日志措辞等于改验收判据**，必须同步更新 doc 28/50。

### ADR-10：OEM 图标通过 AirPlay `/info` 声明（不改 iOS 行为）

- **决策**：在 AirPlay 会话的 `/info` plist 里声明 `oemIconVisible=true` + `oemIconLabel` + `oemIcons[{imageData,widthPixels,heightPixels,prerendered}]`；图标可用设置项替换。
- **结果**：实车确认 iOS **显示了**这个图标——位置在 **CarPlay 主屏（应用列表里的"领克"磁贴）**，**不是**用户在别人车上看到的"侧边栏信号/电量那一行"。
- **结论**：侧边栏那个汽车图标属于 iOS 的连接状态指示，**与我们的声明无关**，不再投入（`⚠️ 待确认`：是否有别的 plist 字段能让它出现在侧边栏；目前无证据）。

## 5. 踩坑与注意事项

### 5.1 工作流级（最重要）

1. **一次安装 = 一次会话中断**：`adb install` 会杀掉应用并断开 CarPlay，用户必须重连。**约定：把同一轮的多项改动合并成一次构建 + 一次安装**。违反这条会消耗用户耐心（用户明确抱怨过）。
2. **提交纪律**：每个改动必须"先验证（单元测试 + 反向对照）→ 再提交"，提交信息要写清"现象、证据、决策、测试前后数字"。本仓库的提交信息普遍较长，这是刻意为之。
3. **文档纪律**：关键结论必须落到 `docs/_digest/`（不在 git 里，但它是项目记忆）。改了判据（日志关键字/字段名）必须同步改 doc 28/50。
4. **并行会话**：本仓库**可能被多个 AI 会话同时提交**（本轮就发生过：另一个会话提交了 `74d5ca89`、`585ee614`、`37a05abb`）。**开工前先 `git log --oneline -3` 与 `git status`**，只碰自己的文件，并在提交前重跑全量测试。

### 5.2 车机 adb 环境

5. **车机必须点火**才能 adb；`adb devices` 看不到就是没通电或 USB 未插好。
6. **车机 adb 会周期性重枚举**（`transport_id` 变化）⇒ 正在跑的 `adb logcat` 会**静默退出**。抓日志必须用"自愈循环"（见 §3.5 第 4 步）。现场脚本：`_live_probe.ps1`、`_live_sample.ps1`。
7. **API 19 的 `adb install` 不支持 `-g`**（会报 `Unknown option: -g`）；权限是安装期授予的，直接 `install -r -d` 即可。
8. **API 19 的 `content` 命令没有 `read` 子命令**（会打印 usage）；想验证"别的进程能否读某个路径"，用 `adb shell cat <路径> | busybox wc -c`（车机有 busybox）。

### 5.3 这台车机的存储是"非标准"的（**最容易踩**）

9. **`/storage/emulated/0` 在这台 ROM 上根本不存在**（**事实**：`ls -ld /storage/emulated/0` → `No such file or directory`）。真实的别名链是：
   ```
   /sdcard → /storage/emulated/legacy → /mnt/shell/emulated/0     （同一个卷，device 23）
   ```
   **但**：应用进程内部看到的 `Environment.getExternalStorageDirectory()` 会返回 `/storage/emulated/0`（这是**每个应用进程私有的挂载命名空间**），所以应用自己读写它没问题 ⇒ **极其容易写出"自检通过、别人读不到"的路径**。
   **规矩：凡是交给别的进程（例如仪表取图方）的路径，必须用 `/sdcard/…` 这种全局别名拼写，并且必须用"将要交付的那个字符串"回读校验。**
10. **应用私有的 `Android/data/<包名>/` 对别的应用不可读**（**事实**：`adb shell` 同时持有 `sdcard_r` 与 `sdcard_rw`，读该目录仍 `Permission denied`）。想给别人读，必须放**共享目录**（例如 `/sdcard/DiPlay/…` 或车机自带应用用的 `/sdcard/Music/mediacenter/images/`）。
11. **FUSE 的权限是"合成"的**：我们 `setReadable(true,false)` 可能返回 `false`（日志里 `chmod=false`），但 `ls -l` 会显示成 `-rw-rw---- root sdcard_r`——**和车机自带应用那些能用的文件一模一样**。所以**不要**把 `chmod=false` 当成失败；真正的判据是"另一个 uid 能否 `cat` 出来"。
12. **车机自带媒体的封面 URI 形态**（**事实**，可作为参照）：`http://y.gtimg.cn/music/photo_new/….jpg`（在线曲）与 `file:///sdcard/Music/mediacenter/images/<专辑>-<歌>-<歌手>.jpg`（本地曲）。

### 5.4 厂商 DIM 接口的隐藏规则

13. **`turnState` 只能取 1/2/3**；传 0 会抛 `RuntimeException("Navigation state is not correct.")`（厂商服务内部行为）。
14. **反射必须按重载匹配**：厂商的 setter 常有多组重载（`int` vs `Integer`、`long` vs `int`），随便取第一个会静默调不到（现象：日志显示"调用了"，但厂商侧没收到）。用 `VendorMethodMatcher` 的拟合排序。
15. **厂商日志是"上帝视角"**：进程 `com.ecarx.dim_interaction` 会把它**收到**的每个字段打出来（如 `albumCover2 = <Uri>`、导航六元组）。**"厂商收到了"≠"仪表画了"**——本轮封面就是在这一点上被骗了一整天。
16. **`updateDriveDirection(int)` 在厂商的 `NaviInteractionImpl` 里是空方法**（原厂导航会调它，但没有效果）；不要指望它改变仪表显示。
17. **仪表渲染方是车机的 HMI，不是我们的应用**：我们只能给整数 id / 字符串 / URI，颜色、位置、字形都由仪表决定。

### 5.5 API 19 / Dalvik 相关

18. **`Math.floorDiv/floorMod(long,long)` 是 API 24**，且**未被 desugar** ⇒ API 19 上抛 `NoSuchMethodError`；**`catch (Exception)` 抓不到 `Error`**（必须 `runCatching`/`catch (Throwable)`）。本仓库已在 `NtpClock` 里换成自写 `floorDivLong/floorModLong`，并从实车确认修复。
19. **Dalvik 在校验期就会打印"解析不到的方法/类"**（`I/dalvikvm: Could not find method … referenced from method …`），**这是信息而非崩溃**，只要该分支不被执行（或被执行时有守卫）。它反而是**最好的越界 API 审计工具**（比 lint 更准）。
20. **Robolectric 4.17 没有 API 19 的 `android-all`** ⇒ **4.4 的运行时行为无法在本地单测里验证**，只能靠实车；本地测试覆盖的是纯逻辑与 Robolectric 支持的较高 API。
21. **本 ROM 没有 MediaCodec 的 Opus 编码器**（`android.media.MediaCodec.createEncoderByType("audio/opus")` → `IOException: Failed to allocate component instance`）⇒ 代码会回退到 **native libopus**（正常路径），实车 `implementation=libopus` ✅。
22. **本 ROM 没有厂商 AAC 解码器**，只有 `OMX.google.aac.decoder`；硬件解码器只有视频（`OMX.Freescale.std.video_decoder.*`）。所以"优先厂商 AAC 解码器"这类优化在本车**无适用对象**。

### 5.6 构建与产物

23. **两个 Gradle 构建不能同时跑**：会报 `classes.jar: 另一个程序正在使用此文件`。并发开发时先 `.\gradlew.bat --stop`，或串行执行。
24. **`assembleStandaloneDebug` 必须给 `DIPLAY_AUTH_ASSETS_DIR`**（否则 `verifyStandaloneAuthentication` 失败）——这是**故意**的护栏，防止打出没有认证材料的包。
25. **别信"BUILD SUCCESSFUL in 2s"**：Gradle 可能认为"已是最新"，而产物其实是**上一次被中断写坏的文件**，安装时报 `INSTALL_FAILED_INVALID_APK`。**规矩：装包前先删旧产物再构建，并检查产物大小/条目结构（`4 dex / 2 so`、约 10–15 MB 都正常，取决于 dex 压缩方式）**（见 §5.7）。
26. **APK 大小会在 10.4 MB 与 15.5 MB 之间摆动**：同样内容，dex 是否压缩导致（**事实**，已核实条目结构相同）。**不要**用大小判断产物好坏，要看 `4 dex / 2 so / assets 3`。

### 5.7 具体的历史事故（避免重演）

27. **半成品 APK**：一次构建因文件锁失败，留下 10.74 MB 的坏包，`adb install` 报 `INSTALL_FAILED_INVALID_APK`；删产物重建（10.37 MB）后安装成功。
28. **音频每帧多 16 字节 0**：AEAD 的 tag 被算进明文长度 ⇒ 无线 type 102 卡顿的根因（提交 `13511e91` + 回归测试 `4953f50e`）。
29. **日志双写**：同一行写两遍，掩盖了真正的顺序（提交 `83d064b4`）。
30. **"假重连"**：打开/关闭设置菜单会触发一次不必要的重连（提交 `0a7383af`）。
31. **`git worktree` 删除失败（Windows 长路径）**：用 `cmd /c rd /s /q "\\?\<绝对路径>"`。
32. **MSYS/Git-Bash 环境**下跑 adb 命令需要 `MSYS2_ARG_CONV_EXCL='*'`，否则路径会被转换成 Windows 形式。

### 5.8 危险操作警告

33. **不要在车机上安装改过的第三方 APK**（用户红线）；不要把我们的包名伪装成系统应用。
34. **不要修改 `/system`**（日常运行不需要 root；调研究 root 是另一条已封存的线，见 doc 13/15）。
35. **不要 `git clean -fdx`**：`docs/` 不在 git 里，但工作区里还有大量逆向产物（`_analysis`）与日志（`_artifacts`），删掉等于毁掉证据。
36. **不要在没有反向对照的情况下改行为型代码**：本项目要求"改完把行为改回去，确认测试按预期失败"（见 §6.4 的"验收标准"）。

## 8. 自检：以"完全不了解项目的人"的视角重读

下面列出**重读后仍然无法直接执行/理解的地方**，并就地补充说明。接手者若还有其他疑问，请优先补进这一节。

**Q1：我到底要不要车机才能干活？**
要，但**只有实车验证**需要。日常开发（写代码、跑单测、构建 APK）**不需要车机**：单测在 PC 上跑，APK 可以构建出来备用。车机只用于"点火窗口"里的真机验证。

**Q2：车机不在我手上怎么办？**
小米平板（SDK 35）可以跑同一个 APK 做**功能冒烟**（安装命令相同，`abiFilters armeabi-v7a` 已包含 32 位库）。但**不要**以平板的行为推断车机行为——车机是 API 19，很多能力（display 数量、存储路径、媒体编解码器、DIM 服务）完全不同。平板验收单见 `docs/_digest/30-平板验收清单（无需车机）.md`。

**Q3：我要改"仪表上显示什么"，从哪下手？**
先读 `docs/_digest/46`（导航）与 `45`（媒体），再打开 `shared/.../media/VendorClusterBridge.kt`。所有"仪表字段 → 厂商方法"的映射、门控规则、日志关键字都在这个文件与它的测试里。**改日志措辞前先看 doc 28/50 是否把它当判据。**

**Q4：我怎么知道"厂商真的收到了"？**
四个层次，缺一不可：
1. 我们的 `DiPlay-Cluster` trace 行（我们**发出**了什么）；
2. 厂商进程 `DimInteractionImpl` 的 `args=[…] -> null` 行（厂商**调到了**实例方法）；
3. 厂商服务 `MediaDimInteraction`/`NavigationDimInteraction` 的字段行（厂商**收到了**值，例如 `albumCover2 = <Uri>`、导航六元组）；
4. **仪表上肉眼可见**（最终判据）。
**本轮封面的教训**：前 3 层全绿 ≠ 第 4 层出现。任何"只有 1–3 层证据"的结论都只能算**推测**。

**Q5："基线 923/3、590/6"里的失败要不要修？**
本轮不修（历史遗留，见 doc 34）。**规矩**是"不许让失败集变大"；如果你顺手修好了，请**减少**这两个数字并更新本文 §2.5 与 doc 34。

**Q6：为什么文档不在 git 里还能这么全？**
这是本项目的**历史约定**（文档写在 `docs/_digest/`，仓库里只放代码）。代价是：`git clone` 拿不到知识库；**好处**是文档可以随时写、不受提交纪律约束。接手者请继续遵守，别把文档挪进仓库（会引起大量噪声提交）。

**Q7：`docs/_digest` 里有编号重复（40、47 各两篇），是错误吗？**
不是错误，是历史追加（同一天写了两个主题，沿用同一编号）。**按文件名检索**，不要按编号假设唯一。

**Q8：我要不要管"另一个 AI 会话也在提交"？**
要，但只需三条纪律：开工前 `git log --oneline -3` + `git status`；只碰自己的文件；提交前重跑全量测试。目前分支 `cs11-api19` 上已出现过并行提交（`74d5ca89`、`585ee614`、`37a05abb`），均未互相覆盖。

**Q9：`debug.diplay.artwork_uri` 这个覆盖属性会污染正常流程吗？**
不会：它只在被设置时生效，且只在"下一次交付"时读取；`setprop <name> ''` 或熄火即清除。它存在的唯一目的是"一次点火验证取图方抓不抓 http"。

**Q10：封面要是最终证明"第三方永远拿不到封面"怎么办？**
那就把它作为**已知限制**记录到 doc 45/50 与用户可见的设置界面说明里，并把已实现的三档交付代码保留（因为车机自带应用与参照实现都证明了 HTTP 档在**别的**路径上可用，未来车机固件更新可能改变行为）。**这是产品选择，不是技术失败**——届时需要用户确认。
