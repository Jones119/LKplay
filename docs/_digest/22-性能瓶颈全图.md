## 0. 数据流全链 + 瓶颈标注（ASCII）

```
📱 iPhone 发送侧（AirPlay 加密流） ── ⚠️ 突发源（不可控）
│   视频=TCP+ChaCha20 · 音频=UDP · 触控=iAP 回程
│   持续 3–4.4Mbps；重绘突发更高 —— 大接收窗时"多兆突发灌链路，挤掉音频 UDP"
▼
🧵 USB 线缆 → 控制器中断 ─────────── 🔥 瓶颈#1（最大根因）【已修复 10×】
│   IRQ72 = 2,846,638 次全挤 CPU0（cpu1/2/3=0）→ 补位抖动 → URB 迟滞 → 手机 TX 队满丢包
│   修复：smp_affinity=e（迁 CPU1+2+3）→ 丢包 44–61/5s → 2–5/5s；Udp6InErrors 4.4→1.3/s
▼
📦 内核 cdc_ncm（usb1）+ IPv6/UDP6/TCP6 ─── 📍 丢包点A（链路级）
│   驱动层 0 丢（+23,636 包/60s）· IPv6 0 错 · UDP6 = 唯一窟窿 +217/60s（3.6/s）
│   双协议同损（TCP 重传 ~3%）= 链路级 1–3% 均匀损耗
│   死路：无 rx_max 参数 / 内核无 usbmon / 双方无 RTCP NACK
▼
🚪 应用接收层（ScreenStream / BufferedAudioStream） ─ 📍 丢包点B【已节流封边】
│   修复前：大接收窗 → 视频突发挤音频
│   修复：64KB rcvbuf + TCP_NODELAY → 发送端节拍化；仍 +246/90s ⇒ 反证根在更下层
▼
🔓 解密 ChaCha20-Poly1305 ────────── 🔥 瓶颈#2【已修复 -55%】
│   原：纯 Java(BC) = i.MX6 最大单一耗电源 → Conscrypt/BoringSSL 原生 AEAD
│   实测：4.5/s → 2.0/s（NATIVE_TEST +177/90s）
▼ 分流
├─ 🎬 视频：MediaCodec → VPU 硬解（✅非瓶颈）→ 渲染合成 ⚠️候选：SurfaceView+IPU overlay / 缓冲池零拷贝
├─ 🔊 音频：AudioTrack → 功放（✅ 原始流不修补）· 空闲零丢包达成 ≈0/60s
└─ 👆 触控回程：延迟 249ms → 84ms
▼
🖥️ 屏幕 / 扬声器
```

**CPU 平面（i.MX6 Quad 4×Cortex-A9）**：负载 7.65 → **3.01**（交互突发曾飙 ~8 ≈ 2× 超载）
· USB IRQ → CPU1+2+3 ｜ app taskset 0xd ｜ RPS=2 ｜ ksoftirqd -5 ｜ knobs：rmem 2M / backlog 4000 / rcvbuf 64KB

**对照组**：平板无线（Xiaomi Pad 6 Max 14）同一软件栈 = **零丢包**（3.5Mbps/35fps）→ 瓶颈在 CS11 的 USB/内核/CPU 平面，**不在协议栈**。

## 1. 瓶颈排行（按投入产出）

## 2. 丢包点现状

| 丢包点 | 位置 | 修复前 | 现在 |
|---|---|---|---|
| A | UDP6 socket（链路级） | 3.6/s（+217/60s） | 空闲 **≈0/s**，交互期单包级 |
| B | 应用侧缺包 | 14–21 包整段崩塌 | **miss=1 单包（8ms）**，23 事件/60s |
| C | USB 驱动层 | 0 | 0（从未丢过） |

滑动窗口对照（90s 粒度）：~600+ → 330（taskset）→ 217（RPS=2）→ **177（NATIVE，2.0/s）** 逐级压低。

## 3. 结论

- 三大头（内核调度 / 应用解密 / 链路突发）均已告破或封边；空闲态零丢包，交互态压至单包级。
- 剩余可动空间：**渲染路径**（IPU overlay、缓冲池/零拷贝）与**发送侧协商**（帧率/分辨率）——与编程语言无关（Rust 评估结论见当日讨论：收益上限低，不建议重构）。
- 全部调优为内存态，重启后用 `tools/cs11_recover.sh` / watchdog 重放。

## 4. 瓶颈定性（2026-10-07 复核修正版）

| 层 | 性质 | 证据 | 状态 |
|---|---|---|---|
| ① 放置/调度 | **不是算力**：IRQ 钉死 CPU0、优先级反转 | 同一颗 996MHz 芯片，仅迁移 IRQ = **10×** | ✅ 已修 |
| ② 热点实现 | **算力被浪费**：纯 Java ChaCha20 | 同芯片换 native AEAD = **-55%** | ✅ 已修 |
| ③ 交互残余（单包级） | **归因未定论**（原"平台硬约束"表述证据不足，降级） | 见下复核 | ⏳ 待 lossprobe 实测定性 |

### 4.1 复核记录（用户质疑"丢包时工作核是否满了"触发的重审）

- **方法论缺口**：全晚从未做过"丢包瞬间 × 逐核利用率"的相关采样。既有数据均为散点快照。
- **快照 A（丢包仍 2–4.5/s 的时代，RPS 测试期间）**：`CPU: 37.0% usr 29.6% sys 16.6% idle 9.2% irq 7.4% sirq`（aggregate 83% busy/16.6% idle，**未满**）；loadavg 5.59；最大单进程 = app 35.1%（单核口径），IRQ+sirq 合计 16.6%；ambient 车厂件（IHU_CarSignalService 5.5%、mediaserver 3.7%、surfaceflinger 3.7%…）≈15%。
- **快照 B（注入滑动 12s 期间）**：loadavg 8.12→8.33、可运行任务 5–16、app 28.5–40.9%。**但**：loadavg 含 D 状态且被测试注入进程（`input swipe`→app_process/adb shell）灌水；当轮未采聚合 CPU 行——该数字**不能**直接证明"核满"。
- **修正**：CPU 饱和（假设 A）**未被实锤**；快照 A 反而倾向"未饱和时也会丢"（支持 B/C 分量）。此前"爆发窗口 2× 超载 ⇒ 平台硬约束/时代天花板"表述**证据不足**，降级为待定。

### 4.2 残余三假设（待裁定）

| 假设 | 机理 | 判别特征 |
|---|---|---|
| A 单核瞬时饱和 | 网络核（CPU1）在突发峰被 IRQ+RPS 软中断打满 | 丢包片存在核 ≥90% |
| B 调度/中断延迟 | 不饱和也丢：ksoftirqd/URB 补位被同核更高优先级链延迟 | 丢包片各核 <75%，sirq/irq 有尖峰 |
| C 链路流控边界 | 手机 TX 突发 vs NCM/USB 节拍错配（CPU 无关） | 丢包片全核平稳，Udp6RcvbufErrors≈0 |

**裁定工具**：`tools/cs11_lossprobe.sh`（0.5s 粒度：逐核 busy/sirq/irq + Udp6InErrors/RcvbufErrors + loadavg）＋ `tools/lossprobe_summarize.py`（丢包片 × 逐核相关性判定，已合成数据自测）。下车日：开探针 + 注入滑动 90–120s，一次出结论。

### 4.3 与用户讨论的沉淀

- "单核性能不足"仍是**不完整近似**：修复主力（10×/-55%）均为"把同一颗芯用对"；4 核已在用；带宽余量 15–25×（23 §2.5）；频率已到规格上限。
- **蓝牙对照不成立但方向可取**：芯片"够不够"由任务决定——本项目稳态 1080p35 零丢包已证"够"；但蓝牙音乐不可作对照（码率低 10–30×、无逐帧解密、容忍缓冲大、可能由独立模块/TBox 承载）。残余问题的本质是**"最坏 1% 窗口的时序"**，不是"平均算力"。
- 定性结论以 §4.2 三假设的实测裁定为准，本图 §0 的"平台天花板"表述同步降级。
