## ① 总览（文字流程）

### A. 有线（USB）链路 —— 完全自研 userspace usbmuxd，不依赖系统服务

1. `CarPlayController.start()`（orchestration/CarPlayController.kt:411）：WIRED 时注册 USB 权限/附着广播接收器（:432-433），随后 `startMfi()`（:435）。
2. MFi 认证先行：`startMfi()`（:755）按 `MfiTarget` 选 LOCAL / USB_CH341 / I2C / REMOTE；通过后 `startPhone()`（:1063）→ `startIphone()`（:1665）。
3. 发现与授权：`checkIphoneAvailability()`（:1674）用 `UsbManager.deviceList` 按 Apple VID 0x05ac（可配 PID）过滤（transport/IphoneUsbHost.kt:96-97、48-54）；无设备则每 2 s 轮询（CarPlayController.kt:2628）。`requestPermission` 走系统对话框 + 自定义广播 action `${packageName}.IPHONE_USB_PERMISSION`（IphoneUsbHost.kt:100-106、282-290），并以 500 ms 轮询兜底 120 s（CarPlayController.kt:1757-1782）。
4. 触发 CarPlay 配置切换：若描述符里还没有完整 CarPlay 配置，发 Apple 私有 vendor 请求（`controlTransfer(0xc0, 0x52, 0, 4, 1字节, 1000ms)`，IphoneUsbHost.kt:141-166、315-319），随后 **主动 close 连接并等待重新枚举**（Android 无 sysfs 配置控制，注释见 :57-64）；`ACTION_USB_DEVICE_ATTACHED` 回环进入 `onIphoneAttached`（:1798），最多 2 次（:2631）。
5. 打开数据通路（`openDataPaths`，:1824）：
   - iAP2/USBMUX 管道：`openIap2UsbSession` → `setConfiguration`（失败容忍）+ `claimInterface` 抢占 USBMUX 接口（class ff/fe/02），端点优先 0x04(OUT)/0x85(IN)（IphoneUsbHost.kt:233-274；IphoneCarPlayConfiguration.kt:52-78）。
   - NCM：另起一次 `UsbManager.openDevice` → `NcmUsbBridge.open` 抢占 NCM 控制(02/0d)+数据(0a)接口并选 alt 1（transport/NcmUsbBridge.kt:301-373）。
6. `runStack()`（:1863）：在 bulk 管道上自建 **usbmux v2**（`Iap2UsbMuxHost`：version=2 握手、proto 0/2/6、magic 0xfeedface、16 位 seq/ack）→ **自己实现 lockdown**（`LockdownPairingClient` 配对、`LockdownPlistChannel` 4 字节长度前缀 XML plist、`LockdownTlsEngineFactory`+`TlsDuplexChannel` TLS）→ `StartSession`+`StartService com.apple.carkit.service`（LockdownCarKitClient.kt:25-105）→ 在 carkit 流上跑 iAP2 CSM（`Iap2Session.open`，:1972）。
7. 网络：`attachVpn`（:2378）绑定 `CarPlayVpnService`，`VpnService.Builder` 建 tun：`addAddress(fe80::2/64)` + `addRoute(fe80::/64)` + `addAllowedApplication(自己)`（network/CarPlayVpnService.kt:95-105），`Ipv6NcmBridge` 双向搬运 IPv6 包↔NCM 以太帧（network/Ipv6NcmBridge.kt:43-140）。
8. 控制：`Iap2WiredControlClient.run`（transport/Iap2WiredControlClient.kt:23-122）：Identification(1D00/1D01) → MFi 认证 → PowerSourceUpdate + 5 项订阅 → 收到 0x4300 CarPlayAvailability 即回 **0x4301 CarPlayStartSession**（携带 IPv6 地址/端口/deviceIdentifier/publicKey）。iPhone 随后来连 `fe80::2:<port>`，由 `CarPlayVpnService` 的 AirPlay 监听接受（CarPlayVpnService.kt:213-277）→ AirPlay 会话（07c 范围）。

### B. 无线链路（蓝牙引导 + Wi-Fi 隧道）

1. `startWireless()`（:1084）→ `runWireless()`（:1118）：建热点（P2P / LocalOnlyHotspot / 手动车机热点 / 同 LAN）→ 取 host 地址（优先带 scope 的 link-local IPv6，:1160-1171）→ `CarPlayVpnService.attachWireless` 在 AP 地址上开 AirPlay 监听（:1230-1248，不走 VPN）。
2. Bonjour（:1260-1280；network/CarPlayBonjour.kt）：注册 `_airplay._tcp`（TXT 含 deviceid/features/pk…，:82-94），发现并解析 `_carplay-ctrl._tcp`，对 iPhone 控制端口发 `GET /ctrl-int/1/connect`（:96-128、526-600）。wired 之前会先绑定接口级 mDNS（`useInterfaceMdns=true`，:1268）。
3. 蓝牙：从已配对设备里选 iPhone（:2145-2186）→ RFCOMM 连接 iAP2 UUID `00000000-deca-fade-deca-deafdecacafe`（:1292、:2619），15 s 超时在独立线程连接（:2188-2228）。
4. 蓝牙 iAP2 引导会话（`Iap2WirelessControlClient.run`，transport/Iap2WirelessControlClient.kt:23-227）：Identification（wireless 组件）→ MFi → 5 项订阅 → 收到 0x5702 回 **0x5703**（SSID/密码/信道/安全/BSSID）→ 收到 0x4300 回 **0x4301**（无线端点：SSID/passphrase/IP/端口/身份）→ iPhone 自行加入热点并发起 AirPlay TCP；随后 0x4e0e（transport identifier）到达时 **再次补发 0x5703**（最多 2 次，:176-206、:244-245）。
5. 交接（handoff）：AirPlay 会话收到 `disableBluetooth` 类命令（:2054-2056、:360-379）→ 布局 45 s 看门狗（:2629）→ 等待 AirPlay 媒体流内的 iAP2 type-130 隧道就绪（`media.setIapTunnelHandler(::startWirelessTunnelControl)` :1361；隧道控制 :1436-1505）→ 隧道 ready 后关闭蓝牙引导（:1596-1598）；无隧道时降级要求"已渲染过视频帧"（:1632-1649）。
6. 无线启动看门狗：FirstTcpWatchdog（orchestration/FirstTcpWatchdog.kt），StartSession 发出后 30 s 内无首个 AirPlay TCP 即失败（network/WirelessStartupPolicy.kt:9；CarPlayController.kt:1131-1148）。

## ③ 分阶段详细分析

### 3.1 Q1 · iPhone USB 接入全流程（关键结论：**自己实现 usbmuxd，直接 bulk 传输**）

- 检测：`UsbManager.deviceList` + `IphoneUsbMatcher`（Apple VID 0x05ac；不配置 PID 时接受所有 Apple 设备）transport/IphoneUsbHost.kt:26-54、:96-97。
- 权限：`requestPermission` + `PendingIntent.getBroadcast(action=${packageName}.IPHONE_USB_PERMISSION, FLAG_UPDATE_CURRENT or FLAG_IMMUTABLE)`（IphoneUsbHost.kt:100-106、:282-290）；另有 2 s 一次的设备轮询与 500 ms 权限轮询（CarPlayController.kt:2626-2628）。
- 配置切换：私有 vendor 请求使 iPhone 重枚举为 CarPlay 配置；Android 端无同步重枚举原语，必须"关闭连接→等 ATTACHED 广播"（IphoneUsbHost.kt:57-64、:141-166）。
- 接口占用：`setConfiguration(configuration)`（失败仅告警，:246-251）+ `claimInterface(usbMux, true)`（:264-267）。
- 接链方式：**不使用系统服务**；`Iap2UsbSession` 直接对 bulk OUT/IN 收发（写 :341-351；读用 `UsbRequest.queue(direct 65536B)` + `requestWait(timeout)`，超时返回 null 并 cancel/drain，:354-436），上层 `Iap2UsbMuxHost` 实现完整 usbmux v2 + 极简 TCP 栈（:34-547，：LOCKDOWN_PORT=62078 :267）。
- NCM 数据面虽走 USB 但独立于 mux：`NcmUsbBridge` 单帧 NTB16、`bulkTransfer` 写（session 未开始时被 NAK，返回 -1 允许重试，:69-77），读用单一持久异步 `UsbRequest` 以避免 JNI critical section 阻塞其它 USB 传输（注释 :44-48）。

### 3.2 Q2 · Lockdown 配对记录读写与管理

- 配对过程（transport/LockdownPairingClient.kt:27-171）：连 62078 → `SetValue UntrustedHostBUID` → 两次 `GetValue`（`DevicePublicKey` PKCS#1 PEM、`WiFiAddress`）→ 本地生成 → `Pair`（含 DeviceCertificate/HostCertificate/HostID/RootCertificate/SystemBUID + `ExtendedPairingErrors`，:110-123）→ 响应可带 `EscrowBag`（:74）；`PairingDialogResponsePending` 每 1 s 重连再试（:81-84、:195-208）。
- 记录生成（transport/LockdownPairRecord.kt:122-145、:167-290）：本地生成 RSA-2048 root+host 密钥，用手机上报的 DevicePublicKey 签发 device 证书；三张证书手工 DER 编码（空 DN、10 年期、SHA256withRSA，:222-290），PEM 输出。
- 内存/持久化：`PairedRecord`（LockdownPairingClient.kt:230-241）；控制器持有 `loadPairRecord/savePairRecord/clearPairRecord` 回调（CarPlayController.kt:161-163），当前实现是 SharedPreferences 存 16 进制 PEM（common/src/main/java/com/shilapi/xcertplay/AirPlayPersistence.kt:889-937）。
- 失效恢复：`com.apple.carkit.service` 打开报 InvalidPairRecord/InvalidHostID 时清记录重配（CarPlayController.kt:1916-1925、:2043-2052）。
- HostID/SystemBUID 为**每次进程随机 UUID**（:199-200），即每台车机/每次新配对各生成一套主机身份。
- TLS 身份：`LockdownTlsEngineFactory` 用 record 的 **root** 私钥+证书作为客户端身份（:28-51），不校验证书（trust-all，:90-97）；TLS 握手在 `TlsDuplexChannel.open` 内先完成（TlsDuplexChannel.kt:400-428），并通过 `LockdownPlistChannel.detach()` 在同一 TCP 连接上原地升级（LockdownCarKitClient.kt:51-55）。

### 3.3 Q3 · NCM/VPN/网络栈

- VpnService：`CarPlayVpnService`（network/CarPlayVpnService.kt）由 Activity 先 `VpnService.prepare` 拿授权（common/.../CarPlayHostActivity.kt:658；`prepare` 封装 :356-357），控制器 `bindService` 后 `attach(ncm,…)`（CarPlayController.kt:2378-2420）。
- tun 参数：地址 `fe80::2/64`、路由仅 `fe80::/64`、session "xcertplay CarPlay"、MTU 1500、`setBlocking(true)`、`addAllowedApplication(自己)`（CarPlayVpnService.kt:95-105）。
- 数据桥：`Ipv6NcmBridge` 两线程——NCM→tun 剥 Ethernet II 头写 14 字节偏移后的 IPv6（:63-89）；tun→NCM 补以太头，目的地多播用 33:33 映射、否则用从入站帧学到的 peer MAC（:91-140）；NA 缺 Target Link-Layer 选项时补写并重算 ICMPv6 校验（EthernetIpv6Codec.kt:74-112）。
- 无线模式**不建 VPN**：只 `attachWireless` 在 AP 地址上开 TCP 监听（CarPlayVpnService.kt:129-158）。
- 监听端口：按实际绑定端口对外通告（`boundPort()` :173-174，配置端口被占时自动换，`AirPlayPortSelector`）。

### 3.4 Q4 · 无线路径（蓝牙握手 + Wi-Fi/Bonjour）与热点后端

- 热点后端 4 种（CarPlayRuntimeConfig.kt:21-26；选择点 CarPlayController.kt:2088-2107）：
  - `WIFI_P2P`：Wi-Fi Direct 组，默认；支持指定信道（docs/SMOOTH_WIRELESS.md:9-19）。
  - `LOCAL_ONLY_HOTSPOT`：应用自有 LOHS，读实际接口/频率后才对外通告（network/LocalOnlyHotspotManager.kt:50-145；SDK≥36 走 configured hotspot 反射，:189-211）。
  - `MANUAL`：车机自带热点，反射读 `getSoftApConfiguration`/旧 `getWifiApConfiguration` 校验 SSID 并取信道/安全（network/ManualHotspotManager.kt:26-155、:242-311）。
  - `EXISTING_WIFI`：同 LAN，不动系统配置，仅选唯一一条非 VPN 的 Wi-Fi 网络（network/ExistingWifiManager.kt:58-146）。
  - 可选 `CarHotspotTethering` 打开车机热点（App 直调或 ADB 兜底），见 CarPlayController.kt:2058-2081 与 docs/CONNECTION_SETUP.md:91-110。
- 蓝牙流程见 ①.B；RFCOMM UUID 与连接细节：CarPlayController.kt:1292、:2188-2228、:2619；不在主线程。
- 无线确认证据链：`FirstTcpWatchdog`（30 s）+ `WirelessConnectionProof`（**认证 + 已渲染帧**双条件才确认）orchestration/WirelessConnectionProof.kt:11-62、CarPlayController.kt:1157-1159、:1540-1551。
- 交接与降级：见 ①.B 第 5 点；`WirelessActiveFallback` 状态单独上报（:1641-1644）。
- 文档要点：热点自动加入依赖 AP 信标里的 Apple vendor IE（docs/WIRELESS_HOTSPOT_JOIN.md:43-57），并非本 App 单方面可解决；本地热点选项已从 App 移除（docs/LOCAL_HOTSPOT_TEST.md:1）；无线诊断字段表见 docs/WIRELESS_DIAGNOSTICS.md:5-21。

### 3.5 Q5 · 会话状态机 / 重连 / 错误恢复

- 阶段机：`Phase{IDLE,MFI,WIRELESS,IPHONE,REENUMERATION,DATAPATHS,CONTROL}`（CarPlayController.kt:176）+ 对外 `CarPlayStatus`（:105-137，可用于 UI 步骤与错误显示）；`onStatus` 统一由 mainHandler 下发并去重（:2551-2561）。
- 代际（generation）隔离：无线 `wirelessGeneration`（:265）与 `isStaleWirelessRun`（:2136-2137）使旧协程/线程结果全部作废；USB 侧 `availabilityPollGeneration/permissionPollGeneration`（:205-206、:1758-1762）。
- 重连入口：`reconnectMfi()`（:439-443）、`reconnectIphone()`（:446-455，无线走 `restartWireless` :1101-1116，有线重跑 `startIphone`）；USB 断线依赖 ATTACHED 广播+2 s 轮询重新授权（:1798-1806）。
- 超时/失败：`fail()`（:2499-2513）转 `CarPlayStatus.Failed`（可带 wifiResetRequired / WirelessStartupFailure）；配对 5 min（:2622）、权限轮询 120 s（:2627）、VPN 绑定 10 s（:2623）、控制环 5 min/位置场景 24 h（:2624-2625）、无线交接 45 s（:2629）、RFCOMM 15 s（:2630）。
- 关闭：`close()`（:585-649）在专用线程按序释放 CSM/USBMUX/VPN/NCM/MFi/位置，并 `awaitClosed`（:727-736）。
- 有线 IO 诊断：`ConnectionIoDiagnostics`（orchestration/ConnectionIoDiagnostics.kt）只记计数与时延；`tracedCarkit` 还把每次 TLS 写切成 256 B（CarPlayController.kt:1935-1971，注释为诊断证书传输停顿）。

### 3.6 其他在本链路上的观察

- MFi：四种后端；CH341 路径探测地址 0x10/0x11、读 0x00/0x01/0x02/0x30/0x50 寄存器挑选"带 accessory 证书"的地址（CarPlayController.kt:923-1049）；Linux `/dev/i2c-N` 需系统开放设备权限（transport/LinuxI2cTransport.kt:6-11）。
- iAP2 内容：有线识别声明 `USBHostTransport`+接口号；无线声明蓝牙 MAC(组件17)+SSID(组件24)（transport/Iap2IdentificationClient.kt:214-291）；有线/无线都声明 0xaa01/0xaa03 认证与 NowPlaying/RouteGuidance/Power/Communications 等消息集（:300-339）。
- 诊断彩蛋：有线建链时会额外开 `com.apple.syslog_relay` 抓 2 分钟手机日志（过滤 accessoryd/iap2d/CarPlay 关键字）——实验室用途（CarPlayController.kt:1884-1915），产品化/移植时应删除或置开关。
- ADB 通道：`LocalAdb` 仅支持明文 127.0.0.1:5555（不支持 TLS 配对，:112-124；docs/WIRELESS_HOTSPOT_JOIN.md:120-125），用途是 BYD 车辆功能与 WifiScanPause；CS11 是否开放 5555 **待验证**。

## ④ CS11 适配观察

### 4.1 判定总纲

DiPlay 的 USB 链路是**自研 usbmuxd + 自研 lockdown**，API 上大量依赖 Android 5.0+ 的 USB 配置 API（见 4.4），在 API 19 上**无法原样运行**；而 CS11 系统自带 usbmuxd（抽象 socket `@com.carbit.usbmuxd`，标准 plist 协议，ListDevices/ReadPairRecord 实测可用，Connect 端口需 swap16）恰好覆盖了这层。因此推荐路线：**用系统 usbmuxd 替换 DiPlay 的 USB 接入与 mux 层，保留其 lockdown 之上的全部协议/媒体栈**。

### 4.2 可复用（与 API 级别无关，建议直接移植）

- `LockdownPlistChannel`（纯 `BlockingDuplexByteStream` 之上，transport/LockdownPlistChannel.kt:32-36）——只要给它一个能到 62078 的字节流即可，与载体无关。
- `LockdownPairingClient`、`LockdownPairRecord(Generator)`、`LockdownTlsEngineFactory`、`TlsDuplexChannel`、`LockdownCarKitClient`（全部接口化，除 `java.util.Base64` 见 4.4）。
- iAP2 全栈（LinkEngine/CSM/Identification/Location/VehicleStatus/FileTransfer）与 `BluetoothRfcommDuplexStream`。
- `NcmUsbBridge`/`Ntb16Codec`/`EthernetIpv6Codec`/`Ipv6NcmBridge`/`CarPlayVpnService` 架构——前提是**应用仍能拿到 iPhone 的 NCM 接口**（见 4.5 未决问题）。
- 状态机/看门狗/诊断类（orchestration 全部小文件）。

### 4.3 可被 CS11 系统 usbmuxd 替代/简化（Q6）

| DiPlay 现状 | CS11 可替代方式 | 备注 |
| --- | --- | --- |
| `IphoneUsbHost`（发现/权限/0x52 重枚举/claim） | 系统 usbmuxd 已管理设备；App 侧不再需要 UsbManager 权限流与重枚举（这是当前 4.4 中最大的 API19 阻塞） | 需确认 usbmuxd 是否已把 iPhone 切到 CarPlay 配置（**待验证**） |
| `Iap2UsbMuxHost` + `UsbMuxFrameBuffer`（自研 usbmux v2+TCP） | 全新写一个 `BlockingDuplexByteStream`：连抽象 socket → plist 协议 `Connect(PortNumber=62078)`（注意 **swap16**），得到到 lockdown 的流 | 思路：让现有 `LockdownPlistChannel` 直接套在该流上，其余上层零改动 |
| `CarPlayController` 中 USB 分支（`startIphone/checkIphoneAvailability/requestIphonePermission/beginReenumeration/openDataPaths/runStack` 的 mux 段，:1665-2032） | 替换为"打开 socket → 建 mux 流 → 进入既有配对/StartSession 流程" | `runStack` 中 1871 之后逻辑基本可保留 |
| 配对（Pair + 证书生成） | 可先用 `ReadPairRecord` 读系统既有配对记录以**跳过 Pair 弹窗**；字段需映射（HostID/SystemBUID/WiFiMACAddress/DeviceCertificate/HostCertificate/HostPrivateKey/RootCertificate/RootPrivateKey ↔ `LockdownPairRecord`，DevicePublicKey 需另取，**待验证**） | 若沿用系统密钥，TLS 客户端身份即系统 root 身份，`LockdownTlsEngineFactory` 可直接喂入 |
| NCM 数据面（`NcmUsbBridge` claim 接口） | **待验证**：若系统侧不代管 NCM，则仍需自研；若 usbmuxd/系统 CarPlay 同时占着整机，App 无法再 claim | 见 ⑤ |

**B. 有 SDK 门禁、低版本安全**：`Build.VERSION_CODES.TIRAMISU` 下的 `registerReceiver(...,RECEIVER_NOT_EXPORTED)` 与 `getParcelableExtra(Class)`（IphoneUsbHost.kt:296-312、Ch341UsbHost.kt:132-137）——编译常量内联，运行期不进分支，可保留。

**C. 需注意的语义差异（不是 API 缺失）**：
- `addAllowedApplication` 删除后：tun 只路由 `fe80::/64`，影响面被限制在 link-local IPv6，可接受；需实机回归（**待验证**）。
- USB 异步读在 19 上只有无参 `requestWait()`（阻塞等待，且会吞掉多端点事件）；DiPlay 依赖的 `requestWait(long)` 超时语义（IphoneUsbHost.kt:354-436、NcmUsbBridge.kt:220-263）需改写（例如"读线程阻塞在 `requestWait()` + 由 close 取消"或退回 `bulkTransfer` 同步读），否则 `close()` 无法从阻塞中唤醒。**这是即便自研 USB 路径也要先解决的第二个阻塞点**（第一是 setConfiguration/setInterface）。
- TLS：`TlsDuplexChannel` 只启用 TLSv1.2/1.3（TlsDuplexChannel.kt:392），Android 4.4 的 Conscrypt 对 SSLEngine 客户端 TLS1.2 支持情况 **待验证**（必要时降级适配或复用系统 usbmuxd 的既有信任通道）。
- 已核查无风险（未列入上表）：Kotlin stdlib 的 `getOrDefault/forEach/buildSet/sumOf` 等（KT-10403 替代品，非 Java 8 平台默认方法）；`java.util.ArrayDeque`、`StandardCharsets`（API 19 齐全）；`PendingIntent` 之外的 Intent/Broadcast 用法均兼容。

### 4.5 适配决策建议（依 4.2/4.3）

1. 新建 `SystemUsbmuxLockdownStream`（socket→plist Connect(swap16)）作为 `BlockingDuplexByteStream` 实现；有线链路改走：socket → lockdown（既有类）→ carkit → iAP2 → NCM/VPN。
2. 保留自研 usbmux 作为**后备**（若 socket 权限/SELinux 不允许，或 usbmuxd 不处理 0x52 重枚举）。
3. API19 统一替换：Base64→`android.util.Base64`；`noBackupFilesDir`→`filesDir` 子目录；`getSystemService(Class)`→字符串常量版；`java.time`→`SimpleDateFormat`；VpnService flags 按 SDK 拼装。
4. 删除 `syslog_relay` 实验室抓取（CarPlayController.kt:1884-1915）以减少对系统 lockdown 的额外占用与 2 分钟线程。

## ⑤ 未决问题（需在 CS11 上实测）

1. **usbmuxd socket 可访问性**：App UID 连接 `@com.carbit.usbmuxd` 是否被 SELinux/权限允许？（背景仅证明 shell 实测可用）— 用一个最小 probe App 或先 `adb shell` 验证 socket 属主/模式。
2. **配置切换归属**：iPhone 插入后，`/sys/bus/usb/devices/*/bConfigurationValue` 是否已是 CarPlay 配置？若否，谁负责发 0x52？系统侧是否需要在 CarPlay 模式前先跑系统 App？
3. **ReadPairRecord 字段完整性**：能否取到 HostPrivateKey/RootPrivateKey（决定能否跳过 Pair 弹窗）；DevicePublicKey 由谁补。
4. **NCM 共存**：usbmuxd 持有设备时，App 还能否 claim NCM control/data 接口（Android 多 open 行为）？若不能，有线 AirPlay 的网络通道需要改用系统网卡（是否存在 usb0/ncm* netdev？）。
5. **Android 4.4 TLS 1.2 via SSLEngine** 是否可用（lockdown TLS 必须）。
6. **MFi 通道**：CS11 是否有可复用 MFi 协处理器（`/dev/i2c-*` 权限）、还是必须外挂 CH341；这决定有线/无线能否通过 iAP2 认证（0xaa01/0xaa03）。
7. **蓝牙私有栈**：nFore 栈是否支持 App 侧 RFCOMM `createRfcommSocketToServiceRecord` 到 iAP2 UUID（无线路径前置条件）。
8. **本地热点/同 LAN** 在 CS11（4.4 + 车机固件）上的可用性：MANUAL 模式读 AP 配置的反射路径、`ExistingWifiManager` 的 `NetworkCallback` 替代（19 无 NetworkCallback，需轮询）。
9. `LocalAdb`（127.0.0.1:5555 明文）在 CS11 是否开放（影响 WifiScanPause 与系统级动作）。
